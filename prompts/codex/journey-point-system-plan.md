# Codex 작업 지시서

## 작업 이름

리디파인 포인트 시스템 기능개발문서 작성

## 목표

프로젝트 리디파인 디스코드 봇에 자체 리디파인 포인트 시스템을 도입하기 위한 기능개발문서를 작성한다.

MEE6와 리디파인 봇의 역할을 분리한다.

MEE6는 포인트, EXP, 레벨업 운영에 사용하지 않는다.

리디파인 봇은 FAQ, 온보딩, 민감 질문 알림, 리디파인 포인트, 체크인, 미션, 인증, 상점, 교환, 로그, 운영자 관리 기능을 담당한다.

이번 작업에서는 실제 포인트 기능을 구현하지 않는다.

코드, 데이터, Slash Command 구조는 변경하지 않는다.

문서만 추가하거나 docs/README.md 링크만 수정한다.

## 중요 주의사항

- src/*.js 파일은 수정하지 않는다.
- src/deploy-commands.js는 수정하지 않는다.
- data/*.json 파일은 수정하지 않는다.
- package.json, package-lock.json은 수정하지 않는다.
- .env, .env.example은 수정하지 않는다.
- 실제 Discord 역할, 채널, 권한 설정은 변경하지 않는다.
- Railway, GitHub 설정은 변경하지 않는다.
- npm run deploy는 실행하지 않는다.
- git commit, git push는 하지 않는다.
- 리디파인 포인트를 현금으로 환급하거나 외부 재화로 교환할 수 있는 것처럼 표현하지 않는다.
- 청년동 포인트 전환은 운영진 관리 하에 청년동 내부 사용처로 제한되는 방식으로 설명한다.
- 포인트 경쟁, 순위 압박, 참여 강요처럼 보이는 표현은 피한다.

---

## 1. 문서 목적

아래 내용을 포함한다.

- 리디파인 디스코드 봇에 자체 리디파인 포인트 시스템을 도입하기 위한 기능개발문서라고 설명한다.
- 실제 구현 전 운영 원칙, 명령어 범위, 데이터 구조, 교환 흐름, 운영자 처리 흐름을 정리한다고 명시한다.
- 이 문서는 구현 지시서가 아니라 기능개발 전 기준 문서라고 설명한다.

## 2. 기본 방향

아래 내용을 포함한다.

- MEE6는 포인트, EXP, 레벨업 운영에 사용하지 않는다.
- MEE6 관련 명령어, 랭킹, 레벨 안내는 참여자 운영 흐름에서 제외한다.
- 리디파인 봇은 한글 명령어 중심으로 운영한다.
- 포인트 명칭은 임시로 “리디파인 포인트”로 한다.
- 리디파인 포인트는 참여를 강제하기 위한 장치가 아니라, 청년동 공간 방문과 프로그램 참여를 가볍게 돕는 동기부여 장치다.
- 포인트와 랭킹이 부담이나 경쟁이 되지 않도록 운영한다.

- 포인트, EXP, 레벨, 랭킹 운영에는 사용하지 않음

## 4. 청년동 포인트 전환 방향

아래 내용을 명확히 정리한다.

- 리디파인 봇은 청년동 포인트 지급 사이트와 직접 연동하지 않는다.
- 참여자는 리디파인 포인트를 사용해 청년동 포인트 전환을 신청할 수 있다.
- /교환 신청 시 리디파인 포인트는 자동 차감된다.
- 교환 신청은 pending 상태로 기록된다.
- 운영자 채널에 청년동 포인트 지급 요청이 자동으로 올라간다.
- 운영자가 청년동 포인트 지급 사이트에서 실제 포인트를 지급한다.
- 지급 후 운영자가 /교환관리로 지급 완료 처리한다.
- 지급이 불가능한 경우 취소 처리하고 리디파인 포인트 환불 로그를 남긴다.
- 청년동 포인트는 청년동 내부에서 정한 사용처에서만 사용할 수 있다.
- 예시 사용처는 벤딩머신, 프린트 카드 충전 등이다.
- 현금 환급, 외부 재화 교환, 타인 양도처럼 보이는 운영은 하지 않는다.

- 체크인, 미션, 인증은 날짜 기준, 중복 지급 방지, 인증 승인 로직이 필요하므로 후순위다.

## 8. 리디파인 포인트 지급 기준 초안

포인트 지급 가능 활동을 정리한다.

- 체크인
- 오늘의 미션
- 회고 작성
- 퀴즈 참여
- 프로그램 참여 인증
- 운영진 수동 지급
- 특별 이벤트 참여

주의사항을 함께 작성한다.

- 과도한 경쟁을 유발하지 않는다.
- 참여자의 속도 차이를 존중한다.
- 포인트를 참여 강제 장치로 쓰지 않는다.
- 운영진이 지급 기준을 사전에 공지한다.
- 하루 또는 주간 적립 상한을 둘 수 있다.

- 청년동 포인트 전환권 100P
- 청년동 포인트 전환권 300P

주의사항을 함께 작성한다.

- 실제 항목, 비용, 재고, 월 한도는 운영진이 확정한다.
- 청년동 내부 사용처로 제한한다.
- 운영 상황에 따라 보류, 취소, 환불 가능하다.
- 포인트가 현금처럼 보이지 않도록 표현에 주의한다.

---

## 10. 교환 상태값

상태값을 정리한다.

- pending: 신청 완료 / 리디파인 포인트 차감됨 / 청년동 포인트 지급 대기
- completed: 운영자가 청년동 포인트 실제 지급 완료
- cancelled: 지급 불가 또는 오류로 취소
- refunded: 취소 후 리디파인 포인트 환불 완료

MVP에서는 pending, completed, cancelled를 우선 사용하고, 환불은 transaction log로 남기는 방향을 제안한다.

---

## 11. 교환 흐름

청년동 포인트 전환 흐름을 단계별로 정리한다.

1. 참여자가 /상점 확인
2. 참여자가 /교환으로 청년동 포인트 전환권 선택
3. 봇이 리디파인 포인트 잔액 확인
4. 잔액이 충분하면 리디파인 포인트 자동 차감
5. 교환 신청 pending 생성
6. 운영자 채널에 지급 요청 알림
7. 운영자가 청년동 포인트 지급 사이트에서 실제 지급
8. 운영자가 /교환관리로 completed 처리
9. 로그에 완료 기록

취소/환불 흐름도 단계별로 정리한다.

1. 운영자가 지급 불가 또는 오류 확인
2. /교환관리로 cancelled 처리
3. 차감된 리디파인 포인트 환불 처리
4. refund transaction 기록
5. 참여자에게 필요 시 안내

## 13. 저장 방식 후보

각 방식의 장단점을 정리한다.

- JSON 파일 기반
- SQLite
- PostgreSQL
- Google Sheets 연동

권장 방향을 포함한다.

- 설계와 로컬 MVP는 JSON 구조로 시작할 수 있다.
- 실제 참여자 운영 전에는 영속 저장소 검토가 필요하다.
- 포인트는 정산과 이력이 중요하므로 단순 파일 저장만으로 운영할 경우 백업과 동시성 문제가 있을 수 있다.
- 청년동 운영과 정산 편의성을 고려하면 Google Sheets 또는 DB 연동을 검토할 수 있다.
- Railway 운영 환경에서는 PostgreSQL 또는 외부 스프레드시트 연동도 후보가 될 수 있다.

## 14. 운영자 채널 알림 설계

아래 내용을 포함한다.

- /교환 신청 발생 시 운영자 채널 알림
- 신청자 표시 방식은 개인정보 최소화

## 15. 로그/정산 원칙

아래 내용을 포함한다.

- 모든 지급, 차감, 교환, 환불은 transaction log로 남긴다.
- 로그는 삭제보다 취소/정정 기록을 남기는 방식이 좋다.
- 운영자 수동 지급/차감도 반드시 사유를 남긴다.
- 추후 CSV 또는 Google Sheets 내보내기 가능성을 고려한다.
- 날짜, 타입, 사유, 관련 신청 ID를 저장한다.
- 월별 또는 프로그램 종료 시 정산 가능하도록 설계한다.
