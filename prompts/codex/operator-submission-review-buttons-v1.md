# Codex 작업 지시서

## 작업 이름

운영자 미션 인증 검토 버튼 v1

## 목표

현재 리디파인 디스코드 봇은 미션 인증 제출이 들어오면 운영자 채널에 검토 알림이 오지만, 운영자가 제출 ID를 복사해서 `/인증관리 제출id:... 처리:승인` 또는 `/인증관리 제출id:... 처리:반려`를 직접 입력해야 한다.

이 방식은 실제 운영에서 너무 번거롭다.

이번 작업의 목표는 **미션 인증 검토 알림 카드에 [승인하고 포인트 지급] / [반려하기] 버튼을 추가해서, 운영자가 버튼만 눌러 처리할 수 있게 만드는 것**이다.

## 현재 전제

- 현재 main 브랜치의 최신 코드를 기준으로 작업한다.
- 기존 Slash Command 구조는 유지한다.
- 새 Slash Command는 추가하지 않는다.
- `/인증관리` 명령어는 fallback 용도로 유지한다.
- 기존 미션 인증 제출 흐름은 유지한다.
- 기존 사진/영상 인증 반응 처리 흐름도 유지한다.
- `data/*.local.json` 파일은 수정하거나 커밋하지 않는다.
- 비밀키, 토큰, 채널 ID 실제값은 코드에 넣지 않는다.

## 핵심 요구사항

### 1. 미션 인증 검토 알림 카드에 버튼 추가

`sendMissionSubmissionReviewAlert` 또는 관련 알림 생성 흐름을 수정해서, 운영자 채널에 오는 “미션 인증 검토 요청” 메시지에 아래 버튼을 붙인다.

- 승인하고 포인트 지급
- 반려하기

버튼 customId 예시:

- `operator_submission_approve:<submissionId>`
- `operator_submission_reject:<submissionId>`

버튼 label은 운영자가 바로 이해할 수 있게 한국어로 작성한다.

예시:

- `승인하고 포인트 지급`
- `반려하기`

### 2. 버튼 클릭 처리 추가

`interactionCreate` 핸들러에서 위 customId를 감지해 처리한다.

처리 조건:

- 운영자 권한이 있는 사람만 누를 수 있어야 한다.
- 기존 `isOperator` 또는 동일한 권한 판별 로직을 사용한다.
- 권한이 없으면 ephemeral 응답으로 “운영진만 처리할 수 있어요.” 정도로 안내한다.

승인 처리:

- `pointsRepository.approveSubmissionById(submissionId, reviewer, note)` 또는 기존 repository 메서드를 사용한다.
- 승인되면 해당 참여자에게 포인트가 지급되어야 한다.
- 원본 검토 알림 메시지는 처리 완료 상태가 보이도록 수정한다.
- 버튼은 비활성화하거나 제거한다.
- 운영자에게는 ephemeral로 “승인 완료 / 지급 포인트 / 참여자”를 알려준다.
- 참여자에게 DM 알림을 보내는 기존 방식이 있다면 재사용한다.
- DM 발송 실패는 전체 흐름을 깨지 않게 조용히 처리한다.

반려 처리:

- `pointsRepository.rejectSubmissionById(submissionId, reviewer, note)` 또는 기존 repository 메서드를 사용한다.
- 포인트는 지급하지 않는다.
- 원본 검토 알림 메시지는 반려 완료 상태가 보이도록 수정한다.
- 버튼은 비활성화하거나 제거한다.
- 운영자에게는 ephemeral로 “반려 완료”를 알려준다.
- 참여자 DM 알림은 가능하면 보내되, 실패해도 전체 흐름이 깨지지 않게 처리한다.

중복 처리:

- 이미 승인/반려된 제출을 다시 버튼으로 처리하려고 하면 에러가 나지 않게 한다.
- “이미 처리된 인증 제출이에요.”라고 ephemeral 안내한다.
- 원본 메시지 버튼은 비활성화하거나 상태를 갱신한다.

### 3. 검토 알림 문구 정리

현재 검토 알림에 `/인증관리 제출id:...` 안내가 길게 들어가 있다면, 버튼 방식이 우선임을 안내한다.

권장 문구:

```txt
아래 버튼으로 바로 처리할 수 있어요.
문제가 있으면 /인증관리 명령어로 직접 처리할 수 있어요.
```

기존 제출 ID는 운영 확인용으로는 남겨도 되지만, 운영자가 반드시 복사해야 하는 느낌은 줄인다.

### 4. /운영현황과 /admin 데이터 기준 통일

현재 `/admin`은 example/test/demo 성격의 데이터를 제외하는데, `/운영현황`은 예시 데이터가 포함되어 숫자가 다르게 보일 수 있다.

다음 중 안전한 방식으로 정리한다.

우선순위 1:

- `/운영현황`도 `/admin`과 동일하게 example/test/demo/sample/예시성 레코드를 제외한다.

우선순위 2:

- 어렵다면 `/운영현황`에 “예시 데이터가 포함될 수 있음” 또는 “실제 운영 데이터 기준” 표시를 명확히 한다.

가능하면 두 화면의 숫자 기준이 같아야 한다.

### 5. 미션 인증 채널 안내 문구 보강

사진/영상 인증은 Discord 모달에 첨부파일을 넣기 어렵기 때문에, 안내 문구를 다음 방향으로 정리한다.

- 글 인증: `/인증` 또는 미션 선택 후 모달 제출 가능
- 사진/영상 인증: 미션 인증 채널에 사진/영상 업로드 권장
- 운영자가 확인 후 정해진 반응 이모지로 승인하면 포인트 지급

기존 문구가 있다면 너무 길지 않게 짧고 명확하게 수정한다.

### 6. 환경변수 안내 문서 보강

README 또는 운영 가이드 문서에 아래 환경변수 설명을 추가하거나 보강한다.

```env
ACTIVITY_REVIEW_CHANNEL_ID=미션_인증_검토_로그_채널_ID
POINT_REDEEM_CHANNEL_ID=포인트_교환_로그_채널_ID
LOG_CHANNEL_ID=기본_봇_질문_로그_채널_ID
```

설명:

- `ACTIVITY_REVIEW_CHANNEL_ID`: 미션 인증 검토 요청, 승인/반려 로그, 반응 승인 로그가 모이는 채널
- `POINT_REDEEM_CHANNEL_ID`: 포인트 교환 신청 알림 채널
- `LOG_CHANNEL_ID`: 답변 실패 질문, 기본 fallback 로그 채널

### 7. 테스트

기존 테스트를 깨뜨리지 않는다.

가능한 경우 아래를 실행한다.

```bash
npm run check:release
```

그리고 현재 프로젝트에 존재하는 관련 테스트 스크립트가 있으면 함께 실행한다.

예시:

```bash
node scripts/test-participant-ux-flow.js
node scripts/test-admin-dashboard-flow.js
node scripts/test-reaction-approval-flow.js
```

없는 테스트 파일이 있으면 새로 만들지 말고 넘어가도 된다.

가능하면 이번 작업에 맞는 간단한 smoke test를 추가한다.

테스트에서 확인할 것:

- 미션 인증 제출 후 검토 알림에 승인/반려 버튼이 붙는지
- 승인 버튼으로 포인트가 지급되는지
- 반려 버튼으로 포인트가 지급되지 않는지
- 이미 처리된 제출을 다시 누르면 친절한 안내가 나오는지
- 운영자가 아닌 사람이 버튼을 누르면 처리되지 않는지
- `/운영현황`과 `/admin`의 주요 숫자 기준이 크게 어긋나지 않는지

## 완료 후 요약

작업이 끝나면 아래 내용을 요약한다.

- 변경한 파일 목록
- 미션 인증 검토 버튼 동작 방식
- `/운영현황`과 `/admin` 데이터 기준 정리 여부
- 환경변수 안내 보강 여부
- 실행한 테스트와 결과
- `npm run deploy`가 필요한지 여부

## 주의

- 이번 작업은 Slash Command를 새로 추가하지 않는다.
- 따라서 원칙적으로 `npm run deploy`는 필요하지 않다.
- 단, 기존 Slash Command 옵션 자체를 변경했다면 그때만 `npm run deploy` 필요 여부를 명확히 알려준다.
- `data/*.local.json` 파일은 커밋하지 않는다.
