# 미니게임 콘텐츠 풀 확장 + 고정 정답 완화 계획

이 문서는 미니게임 개선 1순위 "콘텐츠 풀 확장 + 고정 정답 완화"의 구현 계획입니다. 새 세션에서 이 문서만 보고 작업을 시작할 수 있도록 배경과 결정 사항을 함께 정리합니다.

## 1. 배경과 목표

미니게임 허브 9종은 결과가 `(userId, 날짜)` 결정적 해시(`deterministicNumber`)로 정해지는 건전한 구조지만, 재방문 참여자 기준으로 두 가지 약점이 있습니다.

- **콘텐츠 바닥**: 이모지 기억력 패턴 3개, 초성 퀴즈 3개뿐이라 며칠만 참여해도 전부 외웁니다 (`src/minigameData.js`).
- **고정 정답**: 리디파인 탐험은 장소별 보상이 고정(숲길 3P / 도서관 5P / 광장 0P)이고, 세 칸 탐험도 탐험지별 유리 조합(예: 새벽 시장+접힌 지도+말 걸기=10P)이 코드에 고정되어 있어, 학습된 참여자는 항상 같은 선택으로 최대 보상을 받습니다. 게임이 아니라 버튼 절차가 됩니다.

목표: **신규 데이터 추가와 날짜 시드 셔플만으로, 데이터 구조·보상 정책·버튼 체계를 바꾸지 않고 재방문 재미를 회복**합니다.

## 2. 방식 결정 (대안 비교)

| 방식 | 판단 |
|---|---|
| **데이터 배열 확장 + 날짜별 시드 셔플 (채택)** | `minigameData.js`·`minigameResults.js` 수정만으로 완결. 기존 `deterministicNumber` 재사용, 저장 포맷·customId·보상 캡 전부 불변 |
| 진짜 난수 사용 | 같은 날 재클릭 시 결과가 바뀌어 "하루 1회 확정" 원칙과 충돌. 기존 결정적 설계를 깨므로 기각 |
| 신규 게임 추가 | 버튼 customId·허브 화면·문서·테스트가 모두 늘어나는 별도 규모 작업. 이번 범위에서 제외 |
| 보상 수치 상향 | 하루 40P 캡 안에서 인플레만 유발. 재미 문제의 원인이 아니므로 기각 |

## 3. 설계

### 3-1. 콘텐츠 풀 확장 (데이터만 추가)

- `MEMORY_PATTERNS`: 3개 → **12개**. 각 패턴은 이모지 3개, 패턴 간 중복 없음(오답 보기가 다른 패턴에서 나오므로 서로 구분 가능해야 함).
- `INITIAL_QUIZZES`: 3개 → **12개**. 3지선다 유지, `answer`가 `choices`에 반드시 포함. 어휘는 리디파인 운영 어휘(체크인, 미션, 상점 등)와 참여자가 아는 일상어 중심, 기존과 같은 쉬운 난이도 유지.
- 선택 로직(`createMemoryDetail`, `createInitialDetail`)은 이미 배열 길이 기반이라 **코드 수정 없이 데이터만 추가**하면 됩니다.

### 3-2. 리디파인 탐험: 보상 날짜 셔플

- `EXPLORE_PLACES`에서 `reward` 고정값을 제거하고, `createExploreResult`가 `(userId, dateString)` 시드로 보상 집합 `{0P, 3P, 5P}`를 세 장소에 순열 배정합니다(6가지 순열 중 해시 선택).
- 결과 메시지는 장소 고정 문구 대신 **보상 등급별 문구**(`EXPLORE_REWARD_MESSAGES`: 0P/3P/5P별 2~3종)에서 시드로 선택합니다. 장소 라벨(숲길/도서관/광장)은 유지.
- 효과: "오늘 나의 행운 장소"가 사람마다·날마다 달라져 정답 공유가 무의미해집니다. 기대 보상은 항상 (0+3+5)/3 ≈ 2.7P — **기존에 도서관만 누르던 참여자 기준으로는 하향**이며, 이것이 의도된 변경입니다(6절 주의사항 참고).

### 3-3. 세 칸 탐험: 유리 조합 날짜 셔플

- `ROGUE_PATHS`의 고정 `favoredItem` / `favoredExit` 필드를 제거하고, `createRogueResult`가 `(userId, dateString, pathKey)` 시드로 그날의 유리 장비·유리 행동을 계산합니다.
- 보상 구간(일치 0개=3P, 1개=5P, 2개=10P), 스토리 텍스트, 3단계 진행 화면은 전부 불변. 중간 단계 화면(`minigamePayloads.js`)은 유리 조합을 노출하지 않으므로 수정 불필요.
- `createExploreResult` / `createRogueResult`는 이미 호출부(`minigameInteractions.js`)에서 `userId`·`dateString`을 받고 있어(현재는 무시) **함수 시그니처와 호출부 변경이 없습니다**.

### 3-4. 바꾸지 않는 것

- 하루 확정 4회 / 보상 합계 40P 캡, 중복 지급 차단, 0P도 기록되는 규칙 (`pointsRepository.js` 무변경)
- 버튼 customId 체계, 허브/상세 화면 구성 (`minigameRows.js`, `minigamePayloads.js` 무변경 또는 미수정)
- 슬래시 명령 스키마 (`deploy-commands.js` 무변경 → `npm run deploy` 불필요)
- 카드/가위바위보/주사위/숫자/문/기억력/초성의 보상 수치와 판정 로직

## 4. 수정 대상 파일

| 파일 | 변경 내용 |
|---|---|
| `src/minigameData.js` | ① `MEMORY_PATTERNS` 12개로 확장 ② `INITIAL_QUIZZES` 12개로 확장 ③ `EXPLORE_PLACES`에서 `reward`/`message` 제거, 라벨만 유지 + `EXPLORE_REWARD_MESSAGES` 신설 ④ `ROGUE_PATHS`에서 `favoredItem`/`favoredExit` 제거 |
| `src/minigameResults.js` | ① `createExploreResult`가 시드 기반 순열 배정 + 보상별 메시지 사용 ② `createRogueResult`가 시드 기반 유리 조합 계산. 두 함수 모두 기존에 받던 `userId`/`dateString` 인자를 실제로 사용 |
| `scripts/test-minigame-results.js` **(신규)** | 모듈 스모크 테스트 (아래 6절) |
| `scripts/check-release.js` | 신규 테스트 문법 검사 + 스모크 실행 등록 |
| `docs/minigame-hub-guide.md` | 리디파인 탐험·세 칸 탐험 규칙에 "행운 장소/유리 조합은 사람마다·날마다 달라진다" 1~2줄 반영, 기억력·초성 문항 수 언급 갱신(있는 경우) |

**건드리지 않는 것**: `deploy-commands.js`, `pointsRepository.js`, `minigameInteractions.js`, `minigameRows.js`, `minigamePayloads.js`, 포인트 거래 저장 포맷(`relatedType`/`relatedId` 규칙 불변).

## 5. 동작 규칙

- 같은 `(userId, 날짜, 선택)` 입력은 항상 같은 결과 — 기존 결정적 설계 유지. 하루 1회 확정·중복 차단 규칙과 계속 정합.
- 탐험 보상은 매일 `{0, 3, 5}` 정확히 한 번씩 세 장소에 배정. 특정 장소가 구조적으로 유리하지 않음.
- 세 칸 탐험 유리 조합은 사용자·날짜·탐험지별로 독립 결정. 최저 3P 보장(기존과 동일)이므로 완주하면 항상 무언가는 받는 감각 유지.
- 참여자 간 정답 공유가 무의미해짐(시드에 userId 포함). 운영 공지 불필요 — 게임 설명 문구는 원래 보상 위치를 안내하지 않았음.

## 6. 테스트 방법

`scripts/test-minigame-results.js` (신규, 모듈 테스트 — Discord 클라이언트 불필요):

1. **데이터 무결성**: `MEMORY_PATTERNS` 12개·각 3이모지·상호 중복 없음, `INITIAL_QUIZZES` 12개·3지선다·`answer ∈ choices`, `EXPLORE_REWARD_MESSAGES`에 0/3/5 키 존재
2. **결정성**: 같은 `(userId, dateString, 선택)`으로 `createExploreResult`/`createRogueResult` 2회 호출 시 결과 동일
3. **셔플 동작**: 고정 userId로 날짜 30개를 돌렸을 때 ① 같은 장소의 탐험 보상이 2가지 이상 등장 ② 세 칸 탐험 유리 조합(10P가 나오는 item/exit 쌍)이 2가지 이상 등장 — 고정 정답이 사라졌음을 직접 검증
4. **보상 범위**: 하루 안에서 세 장소 보상의 합이 항상 8(0+3+5), 세 칸 탐험 결과가 항상 {3, 5, 10} 중 하나
5. **기억력/초성 회전**: 서로 다른 userId·날짜 샘플에서 3개 초과 종류의 패턴/퀴즈가 실제로 등장

회귀: `node scripts/test-minigame-hub-flow.js`(기존 단언은 버튼 ID·텍스트 패턴 기반이라 통과 예상, 깨지면 문구 단언만 갱신) + `npm run check:release` 전체 통과.

수동 검증(선택): 테스트 서버 미니게임 채널에서 탐험·세 칸 탐험 각 1회, 기억력·초성 화면에 새 문항이 뜨는지 확인.

## 7. 롤백 방법

- 단일 브랜치/PR(`feat/minigame-content-refresh`) → `git revert` 한 번으로 복구.
- 데이터 구조·저장 포맷·env 변경이 전혀 없으므로 롤백 시 데이터 조치 불필요. 이미 지급된 포인트 거래는 기존 규칙과 동일한 형태라 그대로 유효.

## 8. 주의사항

- **기대 보상 하향이 의도된 변경임을 인지할 것**: 정답을 학습한 참여자는 탐험에서 항상 5P, 세 칸 탐험에서 항상 10P를 받았지만, 셔플 후 기대값은 각각 약 2.7P / 약 4.7P입니다. 하루 40P 캡을 채우기 약간 어려워지며, 이는 "버튼 절차화" 문제를 되돌리는 목적에 부합합니다. 운영진이 참여자 문의를 받을 수 있으므로 가이드 문서에 한 줄 반영합니다.
- 초성 퀴즈 신규 문항은 정답이 명확하고 오답이 억지스럽지 않아야 합니다(참여자를 틀리게 만드는 게 목적이 아님). 민감하거나 평가적인 어휘 금지 — 기존 Korean copy 톤(차분·직접) 유지.
- 이모지 패턴은 Discord 버튼 라벨에서 깨지지 않는 표준 이모지만 사용합니다(기존 패턴과 같은 계열).
