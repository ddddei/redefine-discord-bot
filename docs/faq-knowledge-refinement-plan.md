# FAQ/Knowledge 응답 품질 점검 리포트

이 문서는 현재 `data/faq.json`, `data/knowledge.json`, `data/test-questions.json`을 읽고 `/질문` 응답 품질 개선 후보를 정리한 점검 리포트입니다. 실제 FAQ/Knowledge 데이터는 수정하지 않았으며, 다음 데이터 정리 작업의 기준 자료로 사용합니다.

## 1. 현재 FAQ/Knowledge 구조 요약

- `data/faq.json`
  - 현재 111개 항목입니다.
  - 각 항목은 `keywords`, `question`, `answer` 구조입니다.
  - `/질문`에서 가장 먼저 검색됩니다.
  - 짧은 사용자 질문에 바로 답하고 다음 행동을 안내하는 용도입니다.
- `data/knowledge.json`
  - 현재 76개 항목입니다.
  - 각 항목은 `id`, `title`, `keywords`, `summary`, `content` 구조입니다.
  - FAQ에서 답을 찾지 못했을 때 보조로 검색됩니다.
  - 프로그램 구조, 운영 원칙, 활동 배경처럼 설명이 필요한 내용을 담습니다.
- `data/test-questions.json`
  - 현재 22개 카테고리의 점검 질문 묶음입니다.
  - 데이터 수정 후 `npm run test:questions`로 FAQ, Knowledge, Fallback 매칭을 확인하는 용도입니다.

현재 검색 흐름은 FAQ 우선입니다. FAQ 매칭 점수가 기준보다 낮을 때만 Knowledge가 검색되므로, FAQ에 넓은 keyword가 많으면 Knowledge에 더 적합한 질문도 FAQ에서 먼저 잡힐 수 있습니다.

## 2. FAQ와 Knowledge의 역할 구분

FAQ는 짧은 즉답을 담당하는 것이 좋습니다.

- 결석, 지각, 불참, 중간 퇴장
- 문의 위치, 운영진 연락, 급한 문의 구분
- DM, 캡처, 신고, 채널 사용 예절
- 미션, 출석, 포인트, 랭킹
- 눈팅, 이모지 반응, 마이크/카메라 부담
- 참여 중단, 탈퇴, 잠시 쉬기

Knowledge는 넓은 설명을 담당하는 것이 좋습니다.

- 리디파인 전체 소개와 참여 대상
- 16주 여정, 72시간 온보딩, OT 전후 흐름
- 경험트랙과 Redefine Lab의 배경 설명
- Redefine Day, 상시 프로그램, 측정과 설문
- 디스코드 운영 원칙, 개인정보와 안전
- 정신건강·위기 상황에서 봇과 운영진이 할 수 있는 일의 한계

권장 기준은 "사용자가 바로 행동해야 하는가"입니다. 바로 행동해야 하면 FAQ, 배경과 원칙을 이해해야 하면 Knowledge가 더 적합합니다.

## 3. 중복 가능성이 있는 주제 후보

다음 주제는 FAQ와 Knowledge 양쪽에 모두 있고, 역할을 더 선명하게 나누면 응답 품질이 좋아질 수 있습니다.

| 주제 | 현재 상태 | 정리 방향 |
| --- | --- | --- |
| 72시간 온보딩 | FAQ에 즉답형 항목이 많고 Knowledge에 단계별 설명이 있음 | FAQ는 "무엇부터 하면 되는지"만 짧게 답하고, 단계별 의미는 Knowledge로 유지 |
| 온보딩 역할/채널 공개 | FAQ와 Knowledge가 모두 역할명, 채널 차이를 다룸 | FAQ는 내 역할/보이는 채널 질문에 답하고, Knowledge는 권한 공개 원칙 설명 |
| TRPG | FAQ에 "무엇인가요/처음이어도 괜찮나요", Knowledge에 상세 설명이 있음 | FAQ는 안심 답변, Knowledge는 캐릭터·선택·룰 설명 |
| Redefine Lab | FAQ에 각 Lab 즉답, Knowledge에 상세 설명과 이동 가능성 설명이 있음 | FAQ는 Lab 이름 설명, Knowledge는 여러 Lab 이동과 부담 완화 원칙 |
| 미션/포인트/랭킹 | FAQ에 실무 안내, Knowledge에 의미와 부담 완화 설명이 있음 | FAQ는 사용법, Knowledge는 경쟁 강요가 아니라는 취지 설명 |
| 익명고민채널 | FAQ에 사용법, Knowledge에 사용 원칙이 있음 | FAQ는 사용 가능 여부, Knowledge는 공개 범위와 민감 내용 처리 원칙 |
| 개인정보/캡처/공유 | FAQ와 Knowledge 모두 안전 원칙을 다룸 | FAQ는 "해도 되는지" 즉답, Knowledge는 원칙과 이유 설명 |
| 참여 중단/탈퇴 | FAQ에 행동 안내, Knowledge에 중단·쉬기 설명이 있음 | FAQ는 연락 방법, Knowledge는 상황별 선택지 설명 |

## 4. keywords가 너무 넓어 엉뚱하게 매칭될 수 있는 후보

아래 keyword는 단독으로는 의미가 넓어서 다른 질문을 끌어올 수 있습니다. 삭제가 필요하다는 뜻은 아니며, 더 구체적인 표현과 함께 점검해야 할 후보입니다.

- FAQ 쪽 넓은 keyword 후보
  - `처음`, `입장`, `시작`, `부담`, `활동`, `문의`, `질문`, `소개`, `대상`, `일정`, `시간`, `장소`, `확정`, `선정`, `합격`, `중간`, `게임`, `랭킹`, `포인트`, `상담`, `긴급`
- Knowledge 쪽 넓은 keyword 후보
  - `뭐야`, `무엇`, `소개`, `목적`, `대상`, `누가`, `공지`, `문의`, `판단`, `구조`, `일정`, `단계`, `말`, `몸`, `선택`, `부담`, `고민`, `신청`, `OT`, `공연`, `가족`, `친구`, `측정`

실제 오매칭 후보로는 다음 질문들이 확인되었습니다.

- `중간에 트랙을 바꿀 수 있나요`
  - 현재 `중간에 나가야 할 때는 어떻게 하나요?` FAQ로 잡힐 수 있습니다.
  - `중간` keyword가 조퇴 맥락과 트랙 변경 맥락을 섞을 수 있습니다.
- `낭독극이랑 무용극 중에 못 고르겠어요`
  - 현재 `무용극은 무엇인가요?` FAQ로 먼저 잡힐 수 있습니다.
  - 선택 부담 질문은 Knowledge의 `경험트랙 선택이 부담될 때`로 유도하는 편이 자연스럽습니다.
- `Lab은 하나만 해야 하나요`
  - 현재 `Redefine Lab은 무엇인가요?` FAQ로 잡힐 수 있습니다.
  - Lab 이동 가능성은 Knowledge의 `여러 Lab을 드나들 수 있다는 안내`가 더 적합합니다.
- `나중에 들어와도 되나요`
  - 현재 `이름표나 색상을 바로 골라야 하나요?` FAQ로 잡힐 수 있습니다.
  - "나중에"가 이름표 선택 지연인지, 늦은 입장인지, 프로그램 합류 시점인지 불명확합니다.
- `개인정보 동의는 어디까지 해야 하나요`
  - 현재 `개인정보를 어디까지 말해야 하나요?` FAQ로 잡힐 수 있습니다.
  - 참여동의/개인정보 공개 범위/운영 동의는 분리하는 편이 안전합니다.

## 5. fallback으로 빠질 가능성이 높은 질문 후보

현재 데이터 기준으로 다음 질문은 Fallback이 되거나, 의도와 다른 항목에 매칭될 가능성이 있습니다.

- 선정/합류 흐름
  - `선정 결과는 어디서 확인해요`
  - `대기자도 들어올 수 있나요`
  - `나중에 합류해도 되나요`
- Lab 이동과 병행
  - `여러 랩을 동시에 해도 돼요?`
  - `랩을 중간에 바꾸고 싶어요`
- 전문기관/상담 연계
  - `상담 받을 수 있는 기관을 알려주세요`
  - `병원에 가야 할지 모르겠어요`
  - `외부 도움을 받을 수 있나요`
- 커뮤니티 관계와 안전
  - `친구가 같은 서버에 있으면 불편해요`
  - `DM으로 계속 연락이 와요`
  - `캡처를 운영진에게 보내도 되나요`
- 참여 지속 조건
  - `활동을 안 하면 강퇴되나요`
  - `며칠 동안 접속을 못 하면 어떻게 되나요`
- 운영 세부사항
  - `노트북이 꼭 필요한가요`
  - `교통비 지원 있나요`
  - `식사는 제공되나요`

운영 세부사항은 실제 정책이 확정되지 않았다면 Fallback으로 남겨 운영진 확인을 유도하는 편이 안전합니다.

## 6. 온보딩 관련 보강 후보

온보딩 데이터는 이미 많은 편이지만, 사용자가 실제로 헷갈릴 만한 질문을 더 세분화하면 좋습니다.

- 입장 직후
  - `처음 들어왔는데 채널이 너무 많아요`
  - `공지부터 봐야 하나요`
  - `참여동의 먼저 해야 하나요`
- 역할과 공개 범위
  - `왜 친구랑 보이는 채널이 달라요`
  - `내 역할은 누가 정하나요`
  - `역할을 바꿀 수 있나요`
- 72시간 활동 부담
  - `72시간 안에 아무것도 못 하면 어떻게 돼요`
  - `온보딩 기간에 매일 접속해야 하나요`
  - `조용히 있다가 OT에 가도 되나요`
- OT 전후
  - `OT에 못 가면 탈락인가요`
  - `OT 전에 준비물이 있나요`
  - `OT 이후에는 무엇이 달라지나요`

특히 `OT에 못 가면 탈락인가요`는 현재 결석 불이익 FAQ로 잡힐 수 있습니다. 결석 일반 안내와 OT 불참 안내를 분리할지 검토하는 것이 좋습니다.

## 7. 민감 질문/위기 표현 처리 시 주의할 점

민감 질문은 답변 정확도보다 안전한 연결이 우선입니다.

- 봇은 상담, 진단, 치료, 의료 판단을 대신하지 않는다고 명확히 안내해야 합니다.
- `죽고 싶`, `자해`, `위험한 마음`, `극단`, `위기` 같은 표현은 차분하게 운영진 또는 즉시 도움을 받을 수 있는 사람/기관으로 연결해야 합니다.
- 사용자를 평가하거나 문제 삼는 표현은 피해야 합니다.
- 익명고민채널에 민감 내용을 남기는 경우에도, 긴급하거나 안전 우려가 있는 상황은 운영진 확인이 필요할 수 있음을 안내해야 합니다.
- 다른 참여자의 위기 표현을 본 경우에는 공개 채팅에서 해결하려 하지 말고 운영진에게 알리도록 안내하는 항목이 필요합니다.
- 전문기관/상담기관/병원 관련 질문은 현재 Fallback 가능성이 있으므로, 정책이 정해져 있다면 Knowledge 보강 후보로 두는 것이 좋습니다.

권장 톤은 "혼자 감당하지 않아도 된다", "봇이 판단하지 않는다", "운영진 또는 전문 도움으로 연결한다"입니다.

### 테스트 질문 보강 v1 반영 메모

이전 테스트 질문 보강 v1에서는 실제 FAQ/Knowledge 본문은 수정하지 않았습니다. 오매칭/누락 후보를 `data/test-questions.json`에 먼저 반영했으며, 다음 단계는 테스트 결과를 보고 FAQ keyword와 Knowledge 표현을 좁게 조정하는 것이었습니다.

### 매칭 개선 v1 반영 메모

이번 v1에서는 트랙 선택 부담, Lab 선택/병행, 72시간 온보딩 지연, 개인정보 동의 범위, 역할별 채널 공개, OT 참여 부담처럼 명확한 오매칭 후보를 좁게 조정했습니다. 특히 `중간`과 `나중에`처럼 문맥이 넓은 keyword가 조퇴/이름표 선택과 트랙 변경/늦은 합류를 섞지 않도록 정리했습니다.

아직 운영진 확인이 필요한 주제는 선정 결과, 대기자, 늦은 합류, 교통비, 식사, 준비물, OT 불참 세부 기준, 개인정보 동의의 정확한 범위입니다. 다음 단계에서는 실제 참여자 질문 로그를 보고 FAQ로 짧게 답할 항목과 Knowledge로 넓게 설명할 항목을 추가로 분리해야 합니다.

## 9. 실제 data/*.json 수정 시 권장 순서

1. `data/test-questions.json`에 오매칭/누락 후보 질문을 먼저 추가합니다.
2. `npm run test:questions`로 현재 실패 양상을 기록합니다.
3. FAQ에서 넓은 keyword를 줄이거나 더 구체적인 표현으로 바꿉니다.
4. Knowledge의 설명형 항목에 누락된 표현을 보강합니다.
5. FAQ와 Knowledge가 같은 주제를 다룰 때 FAQ는 짧게, Knowledge는 원칙과 배경 중심으로 정리합니다.
6. 민감 질문은 운영진이 확인한 문구를 기준으로 수정합니다.
7. `npm run validate:data`와 `npm run test:questions`를 실행합니다.
8. 마지막으로 실제 Discord에서 `/질문` 주요 사례를 수동 확인합니다.

한 번에 많은 항목을 고치기보다, 온보딩, 트랙/Lab, 민감 질문, 운영 세부사항처럼 묶음을 나누어 수정하는 편이 원인 추적에 유리합니다.

## 10. Codex에 맡겨도 되는 작업과 사람이 확인해야 하는 작업

Codex에 맡겨도 되는 작업:

- `test-questions.json`에 점검 질문 후보 추가
- FAQ/Knowledge keyword 중복과 넓은 keyword 목록 추출
- 오매칭 후보를 재현하고 전후 매칭 결과 비교
- FAQ는 짧은 답변, Knowledge는 설명형 답변이 되도록 초안 정리
- `npm run validate:data`, `npm run test:questions`, `npm run check:release` 실행 및 결과 요약

사람이 확인해야 하는 작업:

- 참여 확정, 선정 결과, 대기자, 중도 합류 같은 운영 정책
- 교통비, 식사, 준비물, 장소, 일정 변경 등 실제 운영 세부사항
- 위기 표현, 자해·자살 언급, 전문기관 연계 문구
- 개인정보 동의, 익명고민채널 공개 범위, 캡처 제출 가능 여부
- 운영진이 실제로 감당할 수 있는 문의 응답 범위와 응답 시간

특히 민감 질문과 운영 정책은 데이터에 넣기 전에 운영진 문구로 확정해야 합니다. Codex는 초안과 검증은 도울 수 있지만, 최종 기준 확정은 사람이 해야 합니다.
