# 운영 전 자동 점검 리포트

작성 기준: `main` 브랜치 현재 작업트리 기준입니다. 로컬 `main`, `origin/main`, `HEAD`는 모두 `59462c4a4ec2ee7f4446f052ebe6a75ff16f2cd5`를 가리키고 있습니다.

이 문서는 코드 동작을 변경하지 않고, 현재 리디파인 디스코드 봇의 개발/운영 준비 상태를 점검하기 위한 운영 전 분석 리포트입니다. 실제 Discord 역할/권한, Railway, GitHub Actions, 환경변수, API Key, 배포 설정은 이 문서 작성 과정에서 변경하지 않았습니다.

## 1. 현재 구현된 봇 기능 요약

### `/안내`

- 처음 온 참여자에게 리디파인 디스코드 공간의 기본 사용 흐름을 안내합니다.
- 모든 채널을 한 번에 보지 않아도 된다는 점, 역할에 따라 보이는 채널이 다를 수 있다는 점을 설명합니다.
- `/채널안내`, `/질문` 사용 예시를 함께 제공합니다.
- 현재는 사용자 역할별 개인화 없이 공통 안내를 반환합니다.

### `/채널안내`

- `data/channels.json`을 읽어 주요 채널과 카테고리별 설명을 Discord Embed로 보여줍니다.
- 채널 안내 데이터 로드 실패 시 fallback 채널 안내를 사용합니다.
- 현재는 실제 Discord 권한 상태를 조회하지 않으며, 참여자 역할별로 보이는 채널을 다르게 안내하지 않습니다.

### `/질문`

- 사용자가 입력한 질문을 먼저 `data/faq.json`에서 검색합니다.
- FAQ 매칭이 없으면 `data/knowledge.json`에서 Knowledge 항목을 검색합니다.
- FAQ/Knowledge 모두 매칭되지 않으면 운영진 확인이 필요하다는 fallback 안내를 ephemeral 응답으로 제공합니다.
- 검색은 정규화, 토큰, 문자열 포함, 2글자 character pair 유사도를 조합한 로컬 매칭 방식입니다.
- 현재 데이터 규모는 FAQ 111개, Knowledge 76개입니다.

### `/리디`

- `/리디 도움`: 사용 가능한 주요 명령어와 봇 사용법을 안내합니다.
- `/리디 일정`: 일정은 최신 공지와 운영진 안내를 기준으로 확인하라고 안내합니다.
- `/리디 규칙`: 존댓말, 개인정보/캡처 공유 금지, 혐오/차별/스팸 제한 등 커뮤니티 약속을 안내합니다.
- `/리디 문의`: 문의 채널과 운영진 확인이 필요한 상황을 안내합니다.

### `/공지`

- 운영진이 복사해 사용할 수 있는 공지 템플릿을 ephemeral Embed로 보여줍니다.
- Slash Command 정의상 `ManageMessages` 권한을 기본 요구 권한으로 설정합니다.
- 선택지는 일정안내, 봇사용안내, 참여리마인드, 문의안내, 준비물, 결석안내, 입장안내, 온보딩24/48/72시간, 역할전환안내, 온보딩연장안내입니다.
- 실제 출력 문안은 `data/notices.json`의 12개 템플릿을 사용합니다.

### 미응답 질문 로그

- `/질문`에서 FAQ/Knowledge 답변을 찾지 못하면 `LOG_CHANNEL_ID`가 설정된 경우 해당 채널에 로그를 보냅니다.
- 로그에는 질문 내용과 KST 기준 시간이 포함됩니다.
- 사용자 이름, 사용자 ID, 채널 ID 같은 식별자는 기록하지 않는 구조입니다.
- 로그 채널 접근 권한과 봇 메시지 전송 권한은 실제 Discord 서버에서 별도로 확인해야 합니다.

### AI fallback mock 구조

- `src/ai.js`에 실제 API 호출 없는 mock fallback 구조가 준비되어 있습니다.
- 기본값은 꺼진 상태이며, `AI_ENABLED=true`와 `AI_PROVIDER=mock`이 함께 설정된 경우에만 mock 응답을 반환합니다.
- OpenAI/Gemini provider는 아직 구현되어 있지 않습니다.
- 자해, 개인정보, 폭력, 위기 표현 등 민감 키워드가 포함되면 AI fallback을 사용하지 않고 기존 운영진 확인 흐름으로 갑니다.
- 현재 구조는 실제 AI 연동 전 안전한 실험용 단계로 보는 것이 적절합니다.

## 3. 운영 전 남은 작업

- 실제 Discord 역할 생성: 운영진, 봇, 참여자, 온보딩-천천히, 온보딩-기본, 온보딩-활동 역할을 서버에 생성하거나 기존 역할과 매핑해야 합니다.
- 채널 권한 세팅: 공통 채널, 온보딩 역할별 채널, 운영진 전용 채널의 보기/쓰기 권한을 수동으로 설정해야 합니다.
- 테스트 계정으로 역할별 채널 확인: 각 온보딩 역할, 참여자, 일반 계정, 운영진 계정에서 보이는 채널을 실제로 확인해야 합니다.
- `/공지` 템플릿 최종 확인: 12개 공지 템플릿의 날짜, 채널명, 링크, 운영진 안내 기준이 실제 운영 상황과 맞는지 확인해야 합니다.
- Railway/GitHub Actions 확인: Railway Online, Deploy Logs, GitHub Actions CI 성공 여부는 실제 서비스 화면에서 확인해야 합니다.
- 참여자 입장 전 최종 점검: `release-checklist.md`와 `onboarding-operation-runbook.md` 기준으로 봇 명령어, 로그 채널, 공지 고정, 운영진 대응 문구를 최종 확인해야 합니다.

## 4. 자동화로 맡기기 좋은 작업

- 문서 정리: 운영 문서 간 중복, 링크, 용어, 체크리스트 순서를 정리하는 작업은 자동화에 적합합니다.
- 체크리스트 보강: `release-checklist.md`, `operation-guide.md`, `onboarding-operation-runbook.md`의 누락 항목 후보를 정리할 수 있습니다.
- FAQ/Knowledge 중복 점검: FAQ는 즉답, Knowledge는 넓은 설명이라는 기준으로 중복 주제를 찾아낼 수 있습니다.
- 테스트 질문 보강: 운영 중 들어올 만한 질문을 `data/test-questions.json` 후보로 정리할 수 있습니다.
- 운영 메시지 정리: 공지문, DM 템플릿, 문의 대응 문구의 톤과 용어를 일관되게 다듬을 수 있습니다.
- GitHub Issues 후보 정리: 남은 작업을 이슈 제목, 목적, 위험도, 수정 예상 파일 단위로 정리할 수 있습니다.

## 5. 자동화에 맡기면 위험한 작업

- `.env` 수정: 실제 토큰, 서버 ID, 로그 채널 ID가 포함될 수 있어 자동화가 직접 수정하면 위험합니다.
- 실제 Discord 권한 변경: 역할/채널 권한은 참여자 노출 범위와 직결되므로 운영자가 테스트 계정으로 직접 확인해야 합니다.
- `npm run deploy`: Slash Command 등록은 실제 Discord 서버 상태를 바꾸므로 명령어 구조 변경과 운영진 승인 후 실행해야 합니다.
- API key 추가: OpenAI/Gemini 등 실제 API Key는 Railway Variables 또는 로컬 `.env`에서 운영자가 직접 관리해야 합니다.
- 참여자 개인정보 처리: 선발 명단, 설문, DM, 익명고민, 식별자 처리는 자동 요약/복사 대상에서 제외하는 것이 안전합니다.
- 민감 질문 자동 응답: 위기 표현, 자해/자살, 개인정보, 타인 특정, 신고성 내용은 자동 답변보다 운영진 확인이 우선입니다.
- 대규모 코드 리팩터링: 운영 직전에는 검증 범위가 커지고 예기치 않은 회귀가 생길 수 있으므로 좁은 변경만 검토해야 합니다.

## 6. 다음 개발 후보 우선순위

1. 역할 기반 `/안내` 개인화
   - 참여자의 온보딩 역할에 따라 처음 볼 안내, 문의 유도, 활동 채널 안내를 다르게 제공하는 기능입니다.
   - 실제 Discord 역할명 확정과 권한 세팅 후 진행하는 것이 안전합니다.

2. 역할 기반 `/채널안내` 개인화
   - 현재 실제로 볼 수 있거나 역할별로 권장되는 채널만 우선 안내하도록 개선하는 기능입니다.
   - 잘못 구현하면 보이지 않아야 할 채널명을 노출할 수 있어 권한 설계 확정 후 진행해야 합니다.

3. 운영진용 `/점검` 명령어
   - 봇 응답, 데이터 로드, 로그 채널 접근 가능 여부 등을 운영진이 Discord 안에서 확인하는 명령어입니다.
   - 운영진 전용 권한과 ephemeral 응답을 전제로 설계해야 합니다.

4. 역할 기반 미응답 질문 로그 개선
   - 미응답 질문 로그에 개인정보 없이 역할 그룹 정도의 운영 맥락을 붙일지 검토하는 기능입니다.
   - 역할 정보도 민감하게 해석될 수 있으므로 최소 기록 원칙을 우선해야 합니다.

5. AI fallback mock 테스트 가이드
   - `AI_ENABLED=true`, `AI_PROVIDER=mock` 상태에서 어떤 질문이 mock 응답으로 가고 어떤 질문이 차단되는지 문서화합니다.
   - 실제 API 없이 안전하게 fallback 흐름을 검증할 수 있습니다.

6. 실제 AI API 연동
   - FAQ/Knowledge 실패 시에만 API를 보조적으로 호출하는 기능입니다.
   - 비용, 민감정보, 로그, timeout, provider 설정, 운영 중 끄는 방법까지 준비된 뒤 마지막 단계로 진행해야 합니다.

## 7. 내일 바로 진행하기 좋은 작업 3개

### 1. Discord 역할/채널 수동 점검표 확정

- 목적: 실제 서버에서 역할 생성과 채널 권한 세팅을 빠뜨리지 않도록 체크리스트를 확정합니다.
- 위험도: 낮음. 문서 정리 중심이며 실제 권한 변경은 운영자가 별도로 수행합니다.
- 수정 예상 파일: `docs/discord-permission-setup-guide.md`, `docs/release-checklist.md`
- 실행 전 확인할 것: 실제 사용할 역할명, 운영진 전용 채널명, 공통 공개 채널명을 운영진이 확정했는지 확인합니다.
- Codex에 맡겨도 되는지: 가능합니다. 단, 실제 Discord 권한 변경은 Codex에 맡기지 않는 것이 안전합니다.

### 2. `/공지` 템플릿 최종 문안 리뷰

- 목적: 참여자 입장 전 게시할 공지 문구가 실제 일정, 채널명, 운영 방식과 맞는지 검토합니다.
- 위험도: 낮음~중간. 문안 수정은 안전하지만 잘못된 일정/링크를 단정하면 운영 혼선이 생길 수 있습니다.
- 수정 예상 파일: `data/notices.json`, `docs/participant-notice-pack.md`, `docs/onboarding-message-pack.md`
- 실행 전 확인할 것: 확정 일정, 공지 게시 채널, 문의 채널, 운영진이 사용할 실제 링크/표현을 확인합니다.
- Codex에 맡겨도 되는지: 초안 정리와 중복 점검은 가능합니다. 실제 일정, 링크, 채널명 최종 확정은 운영자가 확인해야 합니다.

### 3. FAQ/Knowledge 중복 및 fallback 질문 보강 후보 정리

- 목적: `/질문` 응답 품질을 높이고 운영 시작 후 `#봇-질문로그` 부담을 줄입니다.
- 위험도: 중간. 데이터 수정은 봇 답변에 직접 영향을 주므로 테스트가 필요합니다.
- 수정 예상 파일: `docs/knowledge-audit.md`, `data/faq.json`, `data/knowledge.json`, `data/test-questions.json`
- 실행 전 확인할 것: FAQ는 짧은 즉답, Knowledge는 넓은 설명이라는 기준과 민감 질문 처리 원칙을 확인합니다.
- Codex에 맡겨도 되는지: 후보 목록 작성과 테스트 질문 제안은 가능합니다. 실제 데이터 반영 시 `npm run validate:data`와 `npm run test:questions`가 필요합니다.

## 종합 판단

현재 봇은 운영 전 기본 안내, FAQ/Knowledge 응답, 채널 안내, 공지 템플릿, 미응답 질문 로그, AI fallback mock 준비까지 갖춘 상태입니다. 운영 문서도 릴리즈 체크, 평시 운영, 72시간 온보딩, 권한 수동 세팅, 공지/응대 문구, 문제 상황 대응, API/RAG 설계까지 폭넓게 준비되어 있습니다.

남은 핵심 리스크는 코드보다 실제 운영 환경 확인에 있습니다. 특히 Discord 역할/채널 권한, 테스트 계정 검증, Railway/GitHub Actions 상태, `/공지` 문안의 실제 운영 정보 반영은 자동화가 대신 확정하기 어렵습니다. 운영 직전에는 코드 변경보다 수동 권한 점검과 공지 문안 확정을 우선하는 것이 안전합니다.
