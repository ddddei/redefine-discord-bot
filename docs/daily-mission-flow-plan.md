# 매일/오늘의 미션 UX 재정리 계획

이 문서는 리디파인 디스코드 봇의 미션 UX를 매일 반복되는 생활 습관 미션, 오늘의 활동 미션, 게릴라/특별 미션으로 나누어 정리하기 위한 설계 초안입니다. 실제 코드, Slash Command, 운영 데이터, 환경변수는 변경하지 않습니다.

## 1. 현재 문제점

현재 봇에는 `/미션`, `/인증`, `/미션관리`, `/인증관리`, 미션 인증 채널 반응 승인 흐름이 함께 존재합니다. 이 구조는 운영자가 특정 기간에 여는 게릴라 미션, 특별 이벤트, 일회성 프로그램 인증처럼 미션 ID와 조건을 명확히 구분해야 하는 경우에는 유용합니다.

하지만 매일 반복되는 생활 습관 미션과 사진 인증 미션에는 다음 부담이 큽니다.

- 참여자가 매번 `/미션`에서 미션을 찾거나 미션 ID를 이해해야 합니다.
- 사진이나 짧은 글을 올리는 단순 인증에도 `/인증` 제출 흐름이 필요하다고 느낄 수 있습니다.
- 운영자는 반복 미션을 계속 `/미션관리`로 새로 만들거나 상태를 바꾸는 것처럼 운영하게 됩니다.
- 같은 날 여러 번 인증을 올릴 수 있는 자연스러운 참여 방식과 포인트 1회 지급 기준이 분리되어 있지 않습니다.
- `/admin`은 현재 읽기 전용이라 운영자가 미션 템플릿과 오늘의 미션 상태를 한눈에 조정할 수 없습니다.

따라서 반복형 미션은 "명령어로 미션을 찾아 제출"하는 UX가 아니라 "정해진 채널에 올리면 접수되고, 운영자가 승인하면 하루 1회 지급"되는 UX를 기본값으로 둡니다.

## 2. 새 미션 유형 정의

| 유형 | 목적 | 참여자 진입점 | 인증 접수 방식 | 포인트 지급 기준 | 기존 명령어 관계 |
| --- | --- | --- | --- | --- | --- |
| 매일 습관 미션 | 매일 반복되는 작은 생활 기록, 체크인, 루틴 형성 | `#오늘의-미션` 안내와 채널 업로드 | 글, 사진, 짧은 기록 메시지 자동 접수 후보 | 미션당/사용자당/하루 1회 | `/미션`, `/인증` 없이 참여 가능 |
| 오늘의 활동 미션 | 운영자가 그날 고르는 활동, 사진 인증, 참여 후기 | `#오늘의-미션` 오늘 공지와 채널 업로드 | 해당 날짜 활성 미션에 자동 연결 | 미션당/사용자당/하루 1회 | `/미션`, `/인증` 없이 참여 가능 |
| 게릴라/특별 미션 | 일회성 이벤트, 기간 한정, 복잡한 조건, 특정 프로그램 인증 | `/미션` 목록, 운영자 공지 | `/인증` 또는 기존 미션 인증 채널 | 미션 설정의 기간/횟수 기준 | 기존 `/미션`, `/인증`, `/미션관리` 유지 |

### 2.1 매일 습관 미션

매일 반복되는 행동을 가볍게 기록하는 미션입니다. 예시는 오늘 상태 남기기, 물 마시기 기록, 짧은 산책 사진, 책상 정리 사진처럼 운영자가 매일 열어둘 수 있는 항목입니다.

핵심 원칙:

- 참여자는 미션 ID를 알 필요가 없습니다.
- `#오늘의-미션`에 글이나 사진을 올리면 인증 접수 후보가 됩니다.
- 중복 제출은 막지 않습니다. 다만 승인 지급은 같은 미션 기준 하루 1회만 허용합니다.
- 미션은 경쟁 과제가 아니라 생활 리듬을 돕는 선택형 활동으로 안내합니다.

### 2.2 오늘의 활동 미션

운영자가 특정 날짜에 선택해 여는 활동형 미션입니다. 예시는 오늘의 사진 인증, 오늘의 질문 답하기, 프로그램 참여 후기, 오늘의 응원 댓글 남기기입니다.

핵심 원칙:

- 운영자는 미리 만든 템플릿 중 하나를 오늘의 미션으로 활성화합니다.
- 참여자는 오늘 활성화된 미션명을 보고 채널에 인증을 올립니다.
- 접수 시점에는 여러 제출을 허용하고, 승인 시 지급 중복만 막습니다.
- 여러 오늘의 활동 미션이 동시에 열릴 수 있으나 MVP에서는 하루 1~3개 정도를 권장합니다.

### 2.3 게릴라/특별 미션

기존 `/미션`, `/인증`, `/미션관리` 흐름을 계속 사용하는 미션입니다. 기간, 대상, 조건, 인증 기준이 복잡하거나 운영자가 명시적인 미션 ID를 관리해야 하는 경우에 사용합니다.

예시:

- 특정 프로그램 참여 인증
- 기간 한정 이벤트
- 선착순 또는 팀 단위 미션
- 운영자 메모와 반려 사유가 중요한 인증
- 채널 업로드만으로 어떤 미션인지 판단하기 어려운 제출

## 3. 참여자 흐름

### 3.1 매일 습관 미션

1. 운영자가 `#오늘의-미션`에 오늘 열려 있는 습관 미션을 안내합니다.
2. 참여자는 같은 채널에 글, 사진, 영상 중 필요한 방식으로 인증을 올립니다.
3. 봇은 메시지를 인증 접수 후보로 기록합니다.
4. 운영자는 메시지를 확인하고 승인 반응 또는 후속 승인 UI로 승인합니다.
5. 승인되면 해당 미션의 포인트가 지급됩니다.
6. 이미 같은 날 같은 미션으로 포인트를 받은 참여자의 추가 제출은 기록만 남기고 추가 지급하지 않습니다.

참여자 안내 원칙:

- "미션 ID를 입력하세요"보다 "오늘의 미션 채널에 올려 주세요"를 우선합니다.
- 여러 번 올려도 괜찮지만 포인트는 하루 1회만 지급된다고 안내합니다.
- 민감한 개인정보, 얼굴, 주소, 연락처가 드러나는 사진은 피하도록 안내합니다.

### 3.2 오늘의 활동 미션

1. 운영자가 오늘의 활동 미션 템플릿을 활성화합니다.
2. `#오늘의-미션`에 오늘의 미션명, 인증 방법, 지급 포인트, 지급 제한이 공지됩니다.
3. 참여자는 미션 ID 없이 채널에 글이나 사진을 올립니다.
4. 봇은 오늘 활성화된 활동 미션과 메시지를 연결합니다.
5. 운영자가 승인하면 포인트를 지급합니다.
6. 같은 사용자가 같은 날짜에 같은 활동 미션으로 이미 승인된 경우 추가 지급하지 않습니다.

여러 미션이 동시에 활성화된 경우:

- MVP에서는 운영자가 공지 문구로 참여자가 고를 수 있게 합니다.
- 봇이 자동 분류하기 어려우면 운영자 승인 화면에서 대상 미션을 선택하게 합니다.
- 장기적으로는 메시지 스레드, 버튼, 드롭다운, `/admin` 선택 UI로 보완합니다.

### 3.3 게릴라/특별 미션

1. 운영자가 기존 `/미션관리`로 미션을 만들거나 활성화합니다.
2. 참여자는 `/미션`에서 참여 가능한 미션을 확인합니다.
3. 필요하면 `/인증`으로 제출하거나 운영자가 안내한 채널에 인증을 올립니다.
4. 운영자는 `/인증관리` 또는 반응 승인 흐름으로 처리합니다.

이 흐름은 삭제하지 않습니다. 단순 반복 미션에는 기본 진입점으로 쓰지 않고, 복잡한 조건이 있는 미션의 fallback으로 유지합니다.

## 4. 운영자 흐름

### 4.1 현재 명령어 중심 운영의 한계

운영자가 매일 반복 미션을 새로 만들고 활성화하는 방식은 운영 부담이 큽니다. 미션명, 설명, 포인트, 날짜, 인증 필요 여부를 매번 입력하면 실수가 늘고, 같은 미션이 여러 형태로 중복 생성될 수 있습니다.

### 4.2 템플릿 기반 운영 방향

운영자는 기본 미션 템플릿을 미리 만들어두고, 매일 필요한 템플릿만 선택해 활성화합니다.

권장 흐름:

1. 운영 전 기본 템플릿을 준비합니다.
2. 운영자는 오늘 사용할 템플릿을 선택합니다.
3. 날짜, 포인트, 인증 방식, 공개 문구를 필요할 때만 조정합니다.
4. 활성화하면 `#오늘의-미션` 공지 후보가 생성됩니다.
5. 참여자 제출은 채널 메시지 기반으로 접수됩니다.
6. 운영자는 제출 목록을 보고 승인/반려합니다.
7. 승인 시 중복 지급 기준을 확인한 뒤 포인트를 지급합니다.

### 4.3 기본 템플릿 예시

| 템플릿 키 | 유형 | 제목 | 기본 포인트 | 인증 방식 | 지급 제한 |
| --- | --- | --- | ---: | --- | --- |
| `daily_checkin` | 매일 습관 미션 | 오늘 상태 남기기 | 10P | 짧은 글 | 하루 1회 |
| `daily_photo` | 매일 습관 미션 | 오늘의 사진 기록 | 20P | 사진 또는 영상 | 하루 1회 |
| `daily_routine` | 매일 습관 미션 | 작은 루틴 인증 | 15P | 글 또는 사진 | 하루 1회 |
| `today_reflection` | 오늘의 활동 미션 | 오늘의 회고 남기기 | 30P | 글 | 하루 1회 |
| `today_activity_photo` | 오늘의 활동 미션 | 활동 사진 인증 | 30P | 사진 또는 영상 | 하루 1회 |
| `special_event` | 게릴라/특별 미션 | 특별 미션 | 운영자 지정 | 공지별 지정 | 미션별 지정 |

## 5. 데이터 구조 초안

아래 구조는 설계 초안입니다. 실제 구현 시 기존 `missions`, `submissions`, `reactionApprovals`, `pointTransactions`와의 호환성을 우선합니다.

### 5.1 미션 템플릿

```json
{
  "missionTemplates": [
    {
      "id": "template_daily_checkin",
      "key": "daily_checkin",
      "type": "daily_habit",
      "title": "오늘 상태 남기기",
      "description": "오늘의 상태를 짧게 기록합니다.",
      "defaultRewardPoints": 10,
      "submissionMode": "channel_message",
      "allowedAttachmentTypes": ["text"],
      "rewardLimit": {
        "scope": "mission_per_user_per_day",
        "maxRewards": 1,
        "timezone": "Asia/Seoul"
      },
      "status": "active"
    }
  ]
}
```

### 5.2 일자별 활성 미션

```json
{
  "dailyMissionActivations": [
    {
      "id": "activation_YYYYMMDD_daily_checkin",
      "templateId": "template_daily_checkin",
      "type": "daily_habit",
      "activeDate": "YYYY-MM-DD",
      "title": "오늘 상태 남기기",
      "rewardPoints": 10,
      "submissionChannelRef": "today_mission_channel",
      "status": "active",
      "createdBy": "operator",
      "createdAt": "ISO-8601 timestamp"
    }
  ]
}
```

실제 채널 ID를 문서나 샘플 데이터에 넣지 않고, 구현에서는 환경변수 또는 채널 설정 참조명으로 연결합니다.

### 5.3 채널 메시지 기반 제출

```json
{
  "dailyMissionSubmissions": [
    {
      "id": "daily_submission_generated_id",
      "activationId": "activation_YYYYMMDD_daily_checkin",
      "templateId": "template_daily_checkin",
      "userId": "discord_user_id",
      "messageId": "discord_message_id",
      "channelRef": "today_mission_channel",
      "contentSummary": "operator-visible minimal summary",
      "attachmentCount": 1,
      "status": "pending",
      "submittedAt": "ISO-8601 timestamp",
      "reviewedAt": null,
      "reviewedBy": null,
      "rewardTransactionId": null,
      "duplicateRewardBlocked": false
    }
  ]
}
```

문서의 `discord_user_id`, `discord_message_id`는 필드 의미를 설명하기 위한 자리표시자입니다. 실제 ID를 문서에 적지 않습니다.

### 5.4 중복 지급 키

```json
{
  "rewardDeduplicationKeys": [
    {
      "key": "template_daily_checkin:YYYY-MM-DD:discord_user_id",
      "templateId": "template_daily_checkin",
      "activationId": "activation_YYYYMMDD_daily_checkin",
      "userId": "discord_user_id",
      "rewardedAt": "ISO-8601 timestamp",
      "transactionId": "point_transaction_id"
    }
  ]
}
```

중복 제출은 허용하지만 중복 지급은 이 키로 방지합니다. 기존 구현과 연결할 때는 `pointTransactions.relatedType`, `relatedId`, `reactionApprovals.transactionId` 같은 기존 참조와 함께 사용할 수 있습니다.

## 6. 단계별 MVP 구현 순서

### 1단계. 문서와 운영 기준 확정

- 매일 습관 미션, 오늘의 활동 미션, 게릴라/특별 미션의 용어를 확정합니다.
- `#오늘의-미션`을 반복 미션의 기본 참여 채널로 정리합니다.
- 반복 미션은 미션 ID 없이 참여할 수 있다는 원칙을 운영 문구에 반영합니다.
- 중복 제출 허용, 포인트 하루 1회 지급 기준을 공지 문구로 확정합니다.

### 2단계. 기존 반응 승인 흐름 재해석

- 현재 미션 인증 채널 반응 승인 흐름을 매일/오늘의 미션 접수 기반으로 확장합니다.
- 승인 시 메시지와 활성 미션을 연결하는 방식을 정합니다.
- 지급 전 중복 지급 키를 확인합니다.
- `/미션`, `/인증`은 게릴라/특별 미션 fallback으로 유지합니다.

### 3단계. 템플릿 저장 구조 추가

- 기본 미션 템플릿 저장 구조를 추가합니다.
- 운영자가 매일 새 미션을 만드는 대신 템플릿을 활성화할 수 있게 합니다.
- 초기에는 Discord 명령어 또는 운영자 설정 파일 기반으로 시작할 수 있으나, 참여자에게는 미션 ID 입력을 요구하지 않습니다.

### 4단계. 오늘의 미션 활성화 구조 추가

- 날짜별 활성 미션을 별도 기록합니다.
- 오늘 활성화된 미션을 `#오늘의-미션` 공지와 연결합니다.
- 여러 미션이 동시에 열릴 때 운영자가 승인 시 대상 미션을 고를 수 있게 합니다.

### 5단계. 운영자 검토 UX 정리

- 운영자는 채널 메시지 제출, `/인증` 제출, 반응 승인 기록을 구분해 볼 수 있어야 합니다.
- 승인 화면에는 이미 지급된 동일 날짜/동일 미션 여부를 보여줍니다.
- 중복 지급 차단 시 "접수는 되었지만 이미 오늘 지급된 미션"으로 기록합니다.

### 6단계. 관리자 웹 대시보드 확장

- `/admin`에서 미션 템플릿 목록을 봅니다.
- 오늘의 미션 활성화/비활성화를 조정합니다.
- 포인트, 인증 방식, 공지 문구를 수정합니다.
- 오늘 접수된 제출과 지급 상태를 확인합니다.
- 장기적으로 승인/반려까지 웹에서 처리할 수 있게 하되, 초기에는 읽기 전용 또는 제한된 설정 변경부터 시작합니다.

## 7. 기존 기능과의 관계

### 7.1 유지할 기능

- `/미션`: 게릴라/특별 미션, 복잡한 조건 미션, 명시적 미션 선택이 필요한 경우 계속 사용합니다.
- `/인증`: 채널 업로드가 어렵거나 특정 미션 ID에 직접 제출해야 하는 경우의 보조 흐름으로 유지합니다.
- `/미션관리`: 특별 미션 생성, 상태 변경, 기존 운영 데이터 관리에 계속 사용합니다.
- `/인증관리`: `/인증`으로 들어온 제출 승인/반려에 계속 사용합니다.
- 미션 인증 채널 반응 승인: 매일/오늘의 미션 승인 UX의 기반으로 재사용합니다.

### 7.2 역할을 줄일 기능

- 반복 미션 참여에서 `/미션` 목록 확인을 필수로 만들지 않습니다.
- 반복 미션 참여에서 `/인증 미션:...` 입력을 기본값으로 두지 않습니다.
- 운영자가 매일 같은 미션을 `/미션관리 작업:추가`로 새로 만드는 운영을 권장하지 않습니다.

### 7.3 호환성 원칙

- 기존 `missions`, `submissions`, `pointTransactions` 감사 로그는 유지합니다.
- 새 반복 미션 구조도 포인트 지급 내역을 기존 포인트 로그에서 추적할 수 있어야 합니다.
- 기존 데이터와 충돌하지 않도록 새 유형 필드나 별도 컬렉션을 단계적으로 도입합니다.
- 운영자가 기존 명령어로 만든 특별 미션은 새 반복 미션 템플릿과 섞이지 않게 유형을 명확히 표시합니다.

## 8. 관리자 웹 대시보드 방향

장기적으로 `/admin`은 읽기 전용 상태 확인을 넘어 반복 미션 운영 콘솔로 확장할 수 있습니다. 단, 초기 MVP의 읽기 전용 원칙과 보안 범위를 유지하면서 단계적으로 확장합니다.

### 8.1 템플릿 관리

- 기본 미션 템플릿 목록 보기
- 템플릿별 유형, 기본 포인트, 인증 방식, 지급 제한 보기
- 템플릿 활성/비활성 상태 보기
- 후속 단계에서 템플릿 생성, 수정, 숨김 처리 지원

### 8.2 오늘의 미션 등록

- 날짜별 오늘의 미션 목록 보기
- 템플릿 선택으로 오늘의 미션 활성화
- 공지 문구 미리보기
- `#오늘의-미션` 공지 발행 전 확인

### 8.3 활성화/비활성화

- 오늘 열려 있는 미션 상태 확인
- 운영 중단이 필요한 미션 비활성화
- 종료된 오늘의 미션 이력 확인
- 반복 자동 활성화는 운영 안정화 이후 검토

### 8.4 포인트 설정

- 템플릿 기본 포인트와 오늘 적용 포인트 구분
- 하루 1회 지급 제한 표시
- 중복 지급 차단 이력 표시
- 포인트 변경 시 기존 승인 기록과 감사 로그를 보존

### 8.5 제출 검토

- 오늘 접수된 글/사진 인증 목록 보기
- 제출자, 제출 시각, 연결된 미션, 지급 가능 여부 표시
- 이미 지급된 중복 제출은 "추가 지급 없음"으로 표시
- 후속 단계에서 승인/반려 액션을 웹에서 처리

## 9. 운영 문구 기준

참여자에게는 아래 원칙으로 안내합니다.

```txt
오늘의 미션은 #오늘의-미션 채널에 글이나 사진을 올리면 접수됩니다.
미션 ID를 외우거나 명령어로 제출하지 않아도 됩니다.
여러 번 올릴 수 있지만 포인트는 같은 미션 기준 하루 1회만 지급됩니다.
운영자가 확인하고 승인하면 포인트가 반영됩니다.
```

운영자에게는 아래 원칙으로 안내합니다.

```txt
반복 미션은 매일 새로 만들기보다 템플릿을 선택해 활성화합니다.
참여자 제출은 채널 메시지 기준으로 먼저 접수하고, 승인 시 중복 지급 여부를 확인합니다.
/미션, /인증, /미션관리 흐름은 특별 미션과 예외 처리용으로 유지합니다.
```
