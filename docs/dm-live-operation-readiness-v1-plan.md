# 참여자 DM 실운영 준비 v1 계획서 — 리허설·안전 대응·자동 보존·리디파인 맞춤 연습

**상태: 코드 구현 완료, 실계정·Railway 운영자 QA 대기.** [운영 데이터 안전화 v1](production-data-safety-v1-plan.md)을 선행 적용했으며 리허설 결과는 [실계정 리허설 가이드](dm-chat-live-rehearsal-guide.md)에 기록합니다.

기존 [DM 대화 완성 운영판 계획서](dm-chat-complete-plan.md)는 서버 멤버 제한, 사용량 제한, OpenAI 타임아웃, 로그 보존·삭제, 6종 연습 시나리오, 운영자 가시성을 구현 완료했습니다. 이번 계획은 같은 기능을 다시 만드는 작업이 아닙니다. 실제 리디파인 참여자가 DM을 사용하기 전에 운영자와 테스트 참여자가 전체 흐름을 리허설하고, 장기 운영에 필요한 자동 정리·확인 큐·리디파인 맞춤 연습을 보강하는 작업입니다.

## 0. 선행조건

다음 조건을 충족하기 전에는 실제 참여자에게 `DM_CHAT_ENABLED=true`를 적용하지 않습니다.

1. `production-data-safety-v1`의 빈 환경 초기화와 영속 경로가 완료됨
2. Railway 재배포 후 `dm-chat-logs.local.json` 유지가 확인됨
3. 운영진 전용 `DM_CHAT_LOG_CHANNEL_ID`와 `SAFETY_ALERT_CHANNEL_ID` 접근 권한 확인
4. 운영 책임자와 긴급 상황 내부 연락 방법 확정
5. 첫 안내문·보존 기간·삭제 요청 창구 최종 확인
6. 실제 사용할 OpenAI 모델과 월 비용 한도 결정

## 1. 원칙과 범위

### 1.1 DM 기능의 역할

- 짧은 일상 대화와 의사표현을 연습하는 보조 기능입니다.
- 상담, 진단, 치료, 위기 개입을 대신하지 않습니다.
- 참여자의 상태를 점수화하거나 위험도를 자동 확정하지 않습니다.
- 키워드 감지는 운영자 확인 신호일 뿐 판단 결과가 아닙니다.
- 운영자가 참가자인 척 AI 대화에 몰래 개입하는 기능은 만들지 않습니다.

### 1.2 이번 작업의 100%와 150%

| 구분 | 범위 |
| --- | --- |
| 100% 실운영 필수 | 실계정 리허설, 안내문 검증, 안전 알림 확인 큐, 보존 정리 자동화, 장애·비용 중단 기준, 운영 런북 갱신 |
| 150% 콘텐츠 | 리디파인 상황 맞춤 연습 팩, 회고 문구 개선, 운영 데이터 기반 콘텐츠 보완 |

## 2. 작업 A — 실계정 리허설 패키지

### 2.1 테스트 역할

- 일반 참여자 계정 1개
- 비서버 사용자 계정 1개
- DM 차단 계정 1개
- 운영자 계정 1개
- 안전 알림을 확인할 책임 운영자 1명

실제 참여자 개인정보를 사용하지 않고 테스트용 문장과 계정을 사용합니다.

### 2.2 리허설 시나리오

필수 시나리오를 문서와 체크리스트로 고정합니다.

1. 첫 DM과 기록·열람·보존 안내
2. 일반 대화 3턴과 타이핑 표시
3. `연습 메뉴` → 시나리오 시작 → `연습 끝`
4. `새로 시작` 후 이전 history 제외
5. `오늘 연습 정리`
6. 일일 제한 도달
7. 분당 연속 전송 제한
8. 2,000자 초과 응답 분할
9. OpenAI 타임아웃·오류
10. 입력 민감 표현 감지
11. 출력 민감 표현 차단
12. 비멤버 1회 안내 후 침묵
13. 참여자 삭제 요청 dry-run·apply
14. Railway 재배포 후 기록 유지
15. `/운영현황`과 `/admin` 통계 일치

### 2.3 QA 기록 형식

각 시나리오는 다음을 기록합니다.

- 실행일·환경·테스트 역할
- 기대 결과
- 실제 결과
- 참여자 화면 문구
- 운영 로그·안전 알림 결과
- 개인정보 노출 여부
- 통과/실패/확인 대기
- 후속 작업

테스트 DM 원문 전체를 GitHub Issue나 문서에 붙이지 않고 필요한 최소 재현 문장만 남깁니다.

## 3. 작업 B — 첫 안내와 동의 이해도 개선

첫 안내문은 법률 동의서처럼 길게 만들지 않되 다음이 분명해야 합니다.

- AI와 대화한다는 점
- 대화가 기록된다는 점
- 운영진이 안전·운영 목적으로 확인할 수 있다는 점
- 기본 보존 기간과 삭제 요청 가능
- 긴급 상황이나 상담을 대신하지 않는다는 점
- `연습 메뉴`, `새로 시작`, `연습 끝` 사용법

리허설 참여자 2명 이상에게 다음 질문으로 이해도를 확인합니다.

1. 누구와 대화한다고 이해했는가
2. 기록을 누가 볼 수 있다고 이해했는가
3. 삭제를 원할 때 어떻게 해야 한다고 이해했는가
4. 급하거나 위험한 상황에서 무엇을 해야 한다고 이해했는가

이해가 갈린 문장만 수정하며, 안내문을 반복적으로 늘리지 않습니다.

## 4. 작업 C — 안전 알림 확인 큐

현재 안전 알림은 채널과 로그에 남지만, 운영자가 확인했는지 별도 상태가 없습니다. 실제 운영에서는 자동 판단이 아니라 사람의 확인 완료 여부가 중요합니다.

### 4.1 최소 상태

- `pending`: 운영자 확인 필요
- `reviewed`: 운영자가 로그와 상황을 확인함
- `followUp`: 추가 연락 또는 내부 논의 필요
- `closed`: 필요한 조치와 기록 완료

상태는 참여자에게 노출하지 않으며, 참여자의 심리 상태를 의미하지 않습니다. 단순한 운영 처리 상태입니다.

### 4.2 운영자 화면

우선 Discord `/운영현황 종류:DM대화` 또는 기존 운영 허브 버튼으로 다음을 제공합니다.

- 미확인 안전 알림 수
- 최근 미확인 알림의 사용자 ID·발생 시각·input/output 구분
- 원문 전체 대신 필요한 최소 미리보기
- 상세 로그 확인 위치
- 확인/후속/종료 처리

관리자 웹은 읽기 전용 원칙을 유지합니다. 웹에서 상태 변경은 이번 범위에 포함하지 않습니다.

### 4.3 중복과 개인정보

- 같은 메시지·로그 ID의 중복 큐 생성 방지
- `matchedKeyword`는 참여자 화면과 admin API에 노출하지 않음
- 운영 로그 채널 외부 전송 금지
- 안전 알림 삭제 요청과 운영상 보존 근거는 기존 180일 정책과 일치시킴

## 5. 작업 D — 로그 보존 정리 자동화

현재 정리 스크립트의 월 1회 수동 실행을 유지하면서, 실운영 누락을 줄이기 위한 보수적 자동화를 추가합니다.

### 5.1 제안 방식

- 기본값 비활성화: `DM_CHAT_CLEANUP_AUTO_ENABLED=false`
- 실행 주기: 매주 1회 KST 지정 요일·시각
- 자동 실행도 기존 cleanup 함수와 같은 기준 사용
- 적용 전 정리 대상 수를 계산하고 로컬 백업 사본 생성
- 성공·실패·삭제 건수만 운영 채널에 전송
- 메시지 원문과 사용자 목록은 알림 본문에 포함하지 않음

### 5.2 안전장치

- 같은 주 중복 실행 방지 상태 저장
- 보존 일수가 0이면 자동 정리 건너뜀
- 로그 파일 파싱 오류 시 원본 변경 금지
- 백업 사본 생성 실패 시 삭제 금지
- 한 번에 예상보다 큰 비율이 삭제되면 적용 중단 후 운영자 확인
- 수동 `dry-run`과 `--user` 삭제 기능 유지

자동 정리를 Railway Cron 별도 서비스로 할지 봇 프로세스 내부 스케줄러로 할지는 구현 전 결정합니다. **제안 기본값은 기존 자동 백업과 같은 봇 프로세스 스케줄러**이며, 단일 인스턴스 운영을 전제로 합니다.

## 6. 작업 E — 비용·장애 운영 기준

### 6.1 비용 가시성

현재 토큰 합계를 다음 기준으로 확장합니다.

- 오늘/최근 7일 입력·출력 토큰
- AI 성공·실패·타임아웃 수
- 일일 제한·버스트 제한 도달 수
- 모델명은 운영자 화면에서만 표시
- 금액 자동 환산은 단가 변경 위험 때문에 선택 기능으로 두거나 제외

### 6.2 중단 기준

다음 운영 기준을 문서화합니다.

- 10분 내 AI 오류 5회 이상: 신규 AI 응답 일시 중단 검토
- 안전 출력 감지 반복: 모델·프롬프트 확인 전 일시 중단
- 예상 사용량 급증: 일일 제한 하향 또는 DM 기능 일시 비활성화
- 로그 저장 실패: AI 호출보다 기록·안전 경로를 우선하고 DM 기능 중단
- OpenAI 장애 중에도 고정 안내와 운영자 문의 경로 제공

자동 중단(circuit breaker)을 넣을 경우 운영자가 명시적으로 복구할 수 있어야 하며, 재시작만으로 무조건 풀리지 않도록 상태 저장 여부를 검토합니다.

## 7. 작업 F — 리디파인 맞춤 연습 팩 (150%)

기존 6종을 유지하고, 실제 프로그램에서 반복될 가능성이 높은 상황을 추가합니다.

| 시나리오 | 목적 | 금지할 전개 |
| --- | --- | --- |
| 모임 첫날 인사 | 처음 만난 참여자에게 짧게 말 걸기 | 친밀감 강요, 연락처 요구 |
| 오늘은 쉬고 싶다고 말하기 | 활동 부담을 짧게 전달 | 죄책감 유발, 참여 압박 |
| 지각·결석 알리기 | 운영진에게 상황 전달 | 자세한 사유 강요 |
| DM 제안 거절하기 | 개인 연락이나 만남을 정중히 거절 | 상대의 보복·조롱 전개 |
| 경험트랙 의견 말하기 | 원하는 활동과 어려움을 표현 | 발표 점수·평가 |
| 도움 요청하기 | 운영진에게 필요한 도움을 구체화 | 상담·의료 판단 대신하기 |

각 시나리오는 3~5턴 안에 마무리할 수 있고, 사용자의 문장을 평가·등급화하지 않습니다. 실제 운영 데이터의 원문을 학습 자료처럼 복사하지 않고, 운영자가 익명화해 승인한 반복 상황만 콘텐츠 후보로 사용합니다.

## 8. 작업 G — 운영 런북과 대응 문구

`dm-chat-operation-guide.md`를 다음 기준으로 갱신합니다.

1. DM 활성화 전 선행조건
2. 첫날·첫 주·주간 운영 루틴
3. 안전 알림 확인 큐 처리
4. 참여자에게 연락할 때 사용할 차분한 기본 문구
5. 연락하지 않고 내부 확인만 하는 경우
6. 삭제 요청 접수·확인·처리·회신
7. 자동 보존 정리 성공/실패 확인
8. OpenAI 장애·비용 급증 시 중단과 복구

긴급 연락처와 외부 전문기관 정보는 운영진이 최신 공식 정보로 별도 확정하며, 코드나 고정 응답에 임의로 추가하지 않습니다.

## 11. 수동 QA와 완료 판정

### 11.1 필수 수동 QA

- 2절의 15개 리허설 시나리오 수행
- 참여자 관점 안내 이해도 확인 2명 이상
- 운영자 2명이 같은 안전 알림 큐를 처리했을 때 중복·충돌 확인
- 실제 Railway 로그·Volume·재배포 확인
- Discord 모바일 앱에서 DM 문구와 분할 메시지 확인
- OpenAI 실제 모델로 안전하지 않은 출력이 전달되지 않는지 제한된 테스트

### 11.2 완료 판정

- P0/P1 자동 테스트 전체 통과
- 리허설 실패 항목 0건 또는 운영 전 차단 목록으로 명확히 분리
- 운영 책임자가 안전 알림 SOP와 삭제 요청 절차를 확인
- 월 사용량 한도와 중단 권한자 확정
- 실제 참여자 활성화 날짜와 단계적 공개 범위 결정

처음부터 60명 전체에 열기보다 운영진·내부 테스트 → 소수 참여자 → 전체 참여자의 3단계 공개를 권장합니다.

## 12. 커밋·배포·롤백

권장 커밋 구분:

1. 리허설 문서와 안내 이해도 기준
2. 안전 알림 확인 큐
3. 보존 정리 자동화
4. 비용·장애 가시성
5. 맞춤 시나리오 팩
6. 테스트·런북·환경변수

- Slash Command choice 또는 옵션을 변경하면 `npm run deploy`가 필요합니다.
- DM 기능은 신규 env를 설정하기 전까지 기존처럼 비활성 또는 기존 동작을 유지해야 합니다.
- 롤백 시 `DM_CHAT_ENABLED=false`로 참여자 AI 응답을 먼저 중단하고 로그·안전 알림 데이터는 보존합니다.
- 큐나 자동 정리 스키마는 구코드가 읽지 못해도 기존 DM 로그 자체를 손상시키지 않도록 별도 파일 또는 관용 필드로 저장합니다.
