# DM 대화 운영 런북

이 문서만 보고 신규 운영자가 DM 대화 연습 기능을 활성화하고, 일상적으로 운영하고, 사고에 대응할 수 있도록 정리한 절차입니다. 기능 자체의 설계/결정 배경은 [dm-chat-mvp-plan.md](dm-chat-mvp-plan.md), [dm-chat-complete-plan.md](dm-chat-complete-plan.md)를 참고하세요.

## 1. 활성화 절차

### 1.1 env 체크리스트

| 변수 | 기본값 | 필수 여부 |
| --- | --- | --- |
| `DM_CHAT_ENABLED` | `false` | 필수(켜야 동작) |
| `AI_ENABLED` | `false` | 필수 |
| `AI_PROVIDER` | `none` | 필수(`openai` 또는 `mock`) |
| `AI_MODEL` | (없음) | `AI_PROVIDER=openai`일 때 필수 |
| `OPENAI_API_KEY` | (없음) | `AI_PROVIDER=openai`일 때 필수 |
| `DM_CHAT_LOG_CHANNEL_ID` | (없음) | 강력 권장(없으면 `LOG_CHANNEL_ID` fallback) |
| `SAFETY_ALERT_CHANNEL_ID` | (없음) | 강력 권장(없으면 DM 로그 채널 → `LOG_CHANNEL_ID`) |
| `GUILD_ID` | (없음) | `DM_CHAT_MEMBER_ONLY` 사용 시 필수 |
| `DM_CHAT_MEMBER_ONLY` | `true` | 선택(끄려면 `false`) |
| `DM_CHAT_BURST_LIMIT_PER_MINUTE` | `5` | 선택 |
| `DM_CHAT_DAILY_LIMIT` | `30` | 선택 |
| `DM_CHAT_RETENTION_DAYS` | `90` | 선택 |
| `SAFETY_ALERT_THROTTLE_MINUTES` | `10` | 선택 |

### 1.2 Railway 설정

1. Railway 프로젝트 → 서비스 → Variables에서 위 표의 값을 입력합니다.
2. `GUILD_ID`가 리디파인 실제 서버 ID인지 확인합니다(`DM_CHAT_MEMBER_ONLY` 사용 전제).
3. 값 저장 후 서비스가 재배포될 때까지 기다립니다.
4. slash command 스키마는 이번 변경으로 바뀌지 않았으므로 `npm run deploy`는 필요하지 않습니다.

### 1.3 테스트 계정 확인 (5단계)

1. 테스트 계정(서버 멤버)으로 봇에게 DM을 보내 첫 안내(보존 기간·연습 사용법 포함)를 받는지 확인합니다.
2. 평범한 메시지를 보내 AI 응답이 오는지 확인합니다.
3. `연습 메뉴`를 보내 6종 시나리오 목록이 오는지 확인합니다.
4. 민감 키워드(예: 팀 내부 합의된 테스트 문구)를 보내 AI가 호출되지 않고 안전 안내 + 운영진 알림이 오는지 확인합니다.
5. (가능하면) 비멤버 테스트 계정으로 DM을 보내 1회 안내 후 침묵하는지 확인합니다.

## 2. 일상 운영

- `/운영현황 종류:DM대화`로 오늘 대화 사용자 수, user/assistant 메시지 수, 안전 감지(입력/출력), 오류 수, 오늘 토큰 사용량(입력/출력)을 확인합니다.
- `/admin`의 DM 대화 로그 섹션에서 사용자 ID, 안전 감지 여부, 개수로 필터링해 최근 대화를 읽기 전용으로 확인합니다. `matchedKeyword`와 토큰은 노출되지 않습니다.
- 주간 점검 항목:
  - [ ] 안전 알림이 최근 1주 내 비정상적으로 많지 않은지 확인
  - [ ] 오류 로그 수가 급증하지 않았는지 확인 (§7 장애 대응과 연결)
  - [ ] 오늘 토큰 사용량이 예상 범위인지 확인
  - [ ] 비멤버 DM 시도가 반복되는 계정이 있는지(로그로 간접 확인)

## 3. 안전 알림 대응 SOP

1. **알림 수신**: `SAFETY_ALERT_CHANNEL_ID`(또는 fallback 채널)에서 "DM 안전 확인 필요" embed를 받습니다.
2. **로그 확인**: 참가자 표시명/ID, 감지 유형, 심각도, DM 내용 일부를 확인합니다. 같은 사용자의 반복 감지는 `SAFETY_ALERT_THROTTLE_MINUTES`(기본 10분) 동안 알림이 묶일 수 있으니, 로그 채널(전량 기록)도 함께 확인합니다.
3. **판단 기준**: 감지는 키워드 기반이며 자동 판단이 아닙니다. 알림이 왔다고 곧바로 위기 상황으로 단정하지 않고, 대화 맥락을 함께 봅니다.
4. **참여자 연락 원칙**: 필요하다고 판단되면 운영진이 직접, 차분하고 존중하는 톤으로 연락합니다. 봇이 대신 상담하거나 판단하지 않습니다.
5. **긴급 상황 연락 체계**: (운영진 내부 결정 칸 — 실제 연락 체계는 이 문서 밖 내부 문서/채널에 기록하고 여기에는 채널 ID나 개인 연락처를 적지 않습니다.)
6. **기록 방법**: 별도 조치가 필요했다면 운영진 내부 기록(스프레드시트 등)에 남깁니다. DM 로그 자체는 수정하지 않습니다.

## 4. 삭제 요청 처리

1. **접수**: 참여자 또는 보호자가 삭제를 요청하면 요청 채널/DM에 기록을 남깁니다.
2. **신원 확인**: 요청자의 Discord ID를 확인합니다(다른 사람의 데이터를 실수로 지우지 않도록).
3. **실행**:
   ```bash
   node scripts/cleanup-dm-chat-logs.js --user <discordId>
   # 출력 확인 후 문제 없으면
   node scripts/cleanup-dm-chat-logs.js --user <discordId> --apply
   ```
   `--apply`는 실행 전 `dm-chat-logs.backup-<타임스탬프>.json` 백업 사본을 자동 생성한 뒤 해당 사용자의 messages, notices, historyResets, activeScenarios를 모두 제거합니다.
4. **회신 문구 예시** (백업 한계 고지 포함):
   > 요청하신 DM 대화 기록을 삭제했어요. 다만 삭제 직전 안전을 위해 만든 백업 사본에는 일정 기간 데이터가 남아 있을 수 있어, 완전한 삭제는 아니라는 점을 안내드려요. 추가로 궁금한 점이 있으면 말씀해 주세요.
5. 백업 사본은 로컬 파일(커밋 대상 아님)이며, 별도 보관 규정에 따라 주기적으로 정리합니다.

## 5. 보존 정리 루틴 (월 1회 권장)

1. `node scripts/cleanup-dm-chat-logs.js`로 dry-run을 실행해 제거 대상 건수를 확인합니다.
2. 건수가 예상 범위인지 확인합니다 (급격히 많으면 `DM_CHAT_RETENTION_DAYS` 설정이나 로그 누적 상태를 먼저 점검).
3. 이상이 없으면 `node scripts/cleanup-dm-chat-logs.js --apply`로 적용합니다.
4. 적용 후 안내된 백업 사본 경로를 기록해 둡니다.
5. 자동 스케줄링은 하지 않습니다(사고 시 복구 창구를 남기기 위한 보수적 선택, v2 이후 검토).

## 6. 비용·한도 조정

- `/운영현황 종류:DM대화`의 "오늘 토큰: 입력 X · 출력 Y" 줄로 오늘 사용량을 확인합니다. 금액 환산은 자동으로 하지 않으므로, 모델 단가는 OpenAI Platform의 Pricing 페이지에서 직접 확인합니다.
- `DM_CHAT_DAILY_LIMIT`(기본 30): 참여자별 하루 대화 상한입니다. 남용이 의심되면 낮추고, 정상 사용에 지장이 있으면 높이거나 `0`으로 해제합니다.
- `AI_MAX_TOKENS`(기본 500, 최대 1000): 응답 길이/비용에 직접 영향을 줍니다. 응답이 자주 2,000자 분할 전송되면 낮추는 것을 고려합니다.
- `DM_CHAT_BURST_LIMIT_PER_MINUTE`(기본 5): 짧은 시간 내 과다 호출을 막는 안전장치입니다. 정상 사용자가 자주 걸린다면 값을 올립니다.

## 7. 장애 대응

- **OpenAI 오류 경고**: 전역 기준으로 10분 내 5회 이상 AI 응답 생성이 실패하면 안전/로그 채널에 "DM 대화 AI 응답 오류 경고" embed가 옵니다(10분 스로틀, 반복 발송되지 않음). OpenAI Status 페이지에서 장애 여부를 확인합니다.
- **일시 중단**: 장애가 확인되면 Railway Variables에서 `AI_ENABLED=false`로 설정합니다. 이 경우에도 DM 수신 기록과 안전 감지·알림은 그대로 유지되며, 참여자에게는 준비 중 안내가 나갑니다.
- **복구 확인**: 장애가 해소되면 `AI_ENABLED=true`로 되돌리고, 테스트 계정으로 정상 응답을 재확인합니다(§1.3 5단계 반복).

## 8. 금칙

- `/admin`에 DM 관련 쓰기 기능을 추가하지 않습니다(읽기 전용 원칙 유지).
- `matchedKeyword`, 토큰, 실제 채널 ID를 대시보드·운영 문서·캡처에 남기지 않습니다.
- DM 로그 JSON 파일을 직접 열어 수정하지 않습니다. 모든 정리·삭제는 `scripts/cleanup-dm-chat-logs.js`를 통해서만 수행합니다.
- 시나리오·리캡 응답에 평가·점수·등급 표현을 넣지 않습니다.
