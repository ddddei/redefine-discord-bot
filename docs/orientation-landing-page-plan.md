# 리디파인 오리엔테이션 랜딩페이지 계획서

리디파인 오리엔테이션에서 전체 프로그램, 트랙, 랩을 소개하고 참여자가 현장에서 트랙/랩을 선택할 수 있게 만드는 랜딩페이지 계획입니다. Typeform처럼 개별 제출만 받는 방식보다, 참여자와 운영진이 선택 현황을 함께 확인할 수 있는 공개 허브를 목표로 합니다.

이 문서는 구현 전 기준 문서입니다. 실제 페이지와 API를 만들기 전 [AGENTS.md](../AGENTS.md), [src/AGENTS.md](../src/AGENTS.md), [docs/README.md](README.md), 루트 [DESIGN.md](../DESIGN.md)를 먼저 읽어 주세요.

## 0. 결정 요약

- 랜딩페이지를 오리엔테이션의 메인 허브로 둔다.
- Typeform식 선택 흐름은 페이지 안의 짧은 선택 폼으로 흡수한다.
- 참여자는 프로그램 소개, 트랙/랩 설명, 현재 선택 현황, 다음 행동을 한 화면 흐름으로 확인한다.
- 운영진은 실시간 선택 수, 미선택자, 정원 초과 위험, 변경 이력을 확인한다.
- 공식 기록은 서버 저장소나 외부 시트 중 하나로 보존하되, 참여자 화면에는 필요한 집계만 보여준다.
- 2026-07-13 프론트 v1은 본명과 전화번호로 선택을 받는 정적 페이지로 먼저 구현한다. 공식 저장소와 정원은 추후 확정한다.

## 1. 목적과 성공 기준

### 참여자 목적

참여자는 오리엔테이션 중 다음 질문에 빠르게 답할 수 있어야 합니다.

- 리디파인은 어떤 흐름으로 진행되는가?
- 각 트랙은 무엇을 하는 곳인가?
- 각 랩은 어떤 방식으로 참여하는가?
- 지금 사람들이 어떤 트랙/랩을 선택하고 있는가?
- 나는 무엇을 선택했고, 언제까지 바꿀 수 있는가?

### 운영진 목적

운영진은 현장에서 다음을 즉시 확인할 수 있어야 합니다.

- 트랙별 선택 인원과 비율
- 랩별 선택 인원과 비율
- 정원 또는 권장 인원을 넘는 항목
- 아직 선택하지 않은 참여자
- 중복 제출 또는 닉네임 불일치 의심 건
- 최종 마감 후 내보내기 가능한 선택 결과

### 완료 기준

- 모바일 기준으로 QR 접속 후 30초 안에 트랙/랩 설명과 선택 CTA를 찾을 수 있다.
- 선택 제출 후 본인의 선택 상태가 즉시 보인다.
- 다른 참여자의 개인정보 없이 전체 선택 현황이 실시간 또는 준실시간으로 보인다.
- 운영진이 선택 결과를 CSV 또는 JSON으로 내보낼 수 있다.
- 잘못된 코드, 중복 제출, 마감 이후 제출, 네트워크 오류 상태가 안내된다.

## 3. 권장 사용자 흐름

### 참여자 흐름

1. 오리엔테이션 현장에서 QR 또는 Discord 공지 링크로 접속한다.
2. 첫 화면에서 오늘의 흐름과 선택 마감 시간을 확인한다.
3. 트랙 카드에서 각 트랙의 목적, 적합한 참여자, 결과물을 비교한다.
4. 랩 카드에서 진행 방식과 분위기를 비교한다.
5. 본인 식별 정보를 입력한다.
6. 트랙 1개와 랩 1개를 선택한다.
7. 제출 후 본인의 선택 상태와 변경 가능 여부를 확인한다.
8. 전체 현황에서 현재 분포를 확인한다.

### 운영진 흐름

1. 페이지 또는 운영 링크에서 실시간 현황을 연다.
2. 트랙/랩별 쏠림과 미선택자를 확인한다.
3. 오리엔테이션 진행 중 특정 트랙/랩 설명을 보강한다.
4. 마감 시 선택을 잠근다.
5. 결과를 내보내 후 Discord 공지나 후속 운영 문서에 반영한다.

## 4. 정보 구조

### 첫 화면

- 리디파인 오리엔테이션 제목
- 한 문장 설명: "오늘은 리디파인의 흐름을 이해하고, 내가 참여할 트랙과 랩을 고르는 시간입니다."
- 진행 상태: 소개 중, 선택 열림, 선택 마감 임박, 선택 마감
- 주요 CTA: "트랙/랩 선택하기"
- 보조 CTA: "현재 선택 현황 보기"

### 프로그램 소개

- 전체 기간과 큰 흐름
- 오리엔테이션 이후 무엇이 이어지는지
- 참여 강도에 대한 안내
- 부담을 낮추는 문구: 선택은 평가가 아니라 시작점을 고르는 과정이라는 점을 명확히 한다.

### 트랙 소개

각 트랙 카드는 같은 구조를 사용합니다.

- 트랙명
- 한 줄 요약
- 이런 사람에게 잘 맞음
- 주요 활동
- 기대 결과물 또는 경험
- 권장 인원 또는 정원
- 현재 선택 수

### 랩 소개

각 랩 카드는 같은 구조를 사용합니다.

- 랩명
- 한 줄 요약
- 진행 방식
- 필요한 준비 수준
- 분위기
- 현재 선택 수

### 선택 폼

- 본명
- 전화번호
- 트랙 선택
- 랩 선택
- 선택 변경 안내
- 개인정보 최소 수집 안내

### 실시간 현황

- 트랙별 막대 그래프
- 랩별 막대 그래프
- 전체 제출 수
- 마지막 갱신 시간
- 정원 초과 또는 쏠림 경고

## 5. 데이터와 중복 방지

### 최소 데이터 모델

```json
{
  "selectionId": "uuid",
  "name": "참여자 본명",
  "phone": "01012345678",
  "trackId": "track-a",
  "labId": "lab-1",
  "submittedAt": "2026-07-13T12:00:00.000Z",
  "updatedAt": "2026-07-13T12:05:00.000Z"
}
```

### 중복 방지 옵션

권장 순서는 아래와 같습니다.

| 방식 | 장점 | 단점 | 권장도 |
| --- | --- | --- | --- |
| 운영진 배포 코드 | 빠르고 단순함, 현장 운영에 적합 | 코드 배포 준비 필요 | 높음 |
| Discord 닉네임 입력 | 구현이 가장 쉬움 | 오타와 중복 가능성 있음 | 중간 |
| Discord OAuth | 중복 방지가 가장 강함 | 구현 비용과 설정 부담 큼 | 후속 |
| Typeform 병행 | 익숙하고 백업이 쉬움 | 실시간 경험이 약함 | 보조 |

현장 v1은 Discord 연결이 어려운 참여자를 고려해 본명과 전화번호로 시작합니다. 같은 전화번호로 다시 제출하면 기존 선택을 변경하는 방식으로 운영합니다. Discord 연결, 운영진 배포 코드, OAuth는 후속 보강 옵션입니다.

## 6. 기술 방향

현재 레포는 CommonJS Node 20 기반이며, 별도 프론트엔드 빌드 없이 `public/` 정적 파일을 서버에서 제공하는 구조입니다. v1은 이 구조를 유지하는 것이 좋습니다.

### 권장 파일 구조

```text
public/orientation/
+-- index.html
+-- styles.css
`-- app.js

src/
+-- orientationApi.js
`-- orientationRepository.js

data/
+-- orientation-selections.example.json
`-- orientation-selections.local.json
```

### 권장 API

| 엔드포인트 | 동작 |
| --- | --- |
| `GET /orientation` | 정적 랜딩페이지 |
| `GET /orientation/api/state` | 트랙/랩 목록, 선택 가능 상태, 집계 |
| `POST /orientation/api/selections` | 선택 제출 또는 변경 |
| `GET /orientation/api/admin/export` | 운영진 전용 결과 내보내기 |
| `POST /orientation/api/admin/close` | 운영진 전용 선택 마감 |

운영진 전용 API는 기존 admin 대시보드의 env/token gate 원칙을 따른다. 공개 API 응답에는 개인 식별 원문을 노출하지 않는다.

## 7. 디자인 방향

루트 `DESIGN.md`의 차분하고 직접적인 리디파인 톤을 유지하되, 이번 페이지는 게임 UI보다 오리엔테이션 안내와 선택 경험에 가깝습니다. 따라서 "조용한 운영실"보다 조금 더 밝고 환영하는 오리엔테이션 보드로 확장합니다.

### 분위기

- 낯선 선택을 쉽게 만드는 차분한 안내
- 비교가 쉬운 카드 구조
- 선택 결과가 즉시 반영되는 작은 현장감
- 순위나 경쟁처럼 보이지 않는 집계 표현

### 시각 원칙

- 카드 반경은 과하게 둥글게 하지 않고 8px 안팎을 기본으로 한다.
- 버튼은 눌렀을 때 즉시 반응한다.
- 선택 현황은 랭킹이 아니라 분포로 표현한다.
- 색상은 트랙 구분에만 사용하고, 사람을 평가하는 색상처럼 보이지 않게 한다.
- 애니메이션은 선택 완료, 갱신, 패널 전환처럼 상태 이해를 돕는 곳에만 사용한다.
- reduced-motion 환경에서는 이동 애니메이션을 줄이고 opacity 중심으로 전환한다.

### Emil Kowalski skills 참고 지점

[emilkowalski/skills](https://github.com/emilkowalski/skills)는 버튼 피드백, 전환 타이밍, 애니메이션 목적성, 인터랙션 polish 점검에 참고합니다. 구현 시에는 아래 기준을 적용합니다.

- 버튼 active 상태에 미세한 scale 피드백을 준다.
- UI 애니메이션은 대체로 300ms 아래로 유지한다.
- 등장 요소는 `scale(0)`에서 시작하지 않는다.
- 반복적으로 보는 요소에는 장식 애니메이션을 넣지 않는다.
- transform과 opacity 중심으로 움직인다.

## 8. 카피 원칙

- "선택"은 평가가 아니라 현재 관심사를 고르는 일로 설명한다.
- 트랙/랩 설명은 어렵거나 있어 보이는 말보다, 참여자가 자기 상황에 대입할 수 있는 말로 쓴다.
- 정원 초과나 쏠림은 경고처럼 보이지 않게 "운영진이 분포를 확인 중입니다" 정도로 안내한다.
- 미선택자는 재촉하지 않고 "아직 선택하지 않았다면 천천히 살펴본 뒤 선택해 주세요"로 안내한다.

### 예시 문구

```text
오늘 선택은 최종 평가가 아닙니다.
지금 가장 궁금한 방향을 고르고, 이후 운영진 안내에 따라 조정할 수 있습니다.
```

```text
현재 선택 현황은 함께 방향을 확인하기 위한 참고 자료입니다.
특정 트랙이 더 좋거나 우선이라는 뜻은 아닙니다.
```

## 9. 접근성과 개인정보

- 모든 선택 컨트롤은 키보드로 조작 가능해야 한다.
- 폼 오류는 색상만으로 표시하지 않는다.
- 제출 성공과 실패는 화면 텍스트로 명확히 알린다.
- 공개 현황에는 개별 이름을 노출하지 않는다.
- 운영진 내보내기에는 필요한 최소 정보만 포함한다.
- QR 현장 사용을 고려해 모바일에서 글자 크기와 터치 영역을 충분히 확보한다.
