# test:questions 결과 기반 잔여 오매칭 점검 리포트

## 1. 문서 목적

이 문서는 FAQ/Knowledge 매칭 개선 v1 이후 `npm run test:questions` 결과를 기준으로 아직 남아 있는 오매칭, 애매한 매칭, 의도적 Fallback 후보를 정리하기 위한 점검 문서입니다.

이번 문서는 실제 FAQ, Knowledge, test-questions 데이터를 수정하지 않고, 현재 매칭 결과를 운영 관점에서 해석해 다음 데이터 수정 순서를 정리하는 데 목적이 있습니다.

## 2. 전체 결과 요약

`npm run test:questions` 실행 결과는 다음과 같습니다.

- 전체 질문 수: 153
- FAQ 매칭 수: 136
- Knowledge 매칭 수: 7
- Fallback 수: 10

FAQ로 잘 잡힌 질문은 처음 입장, 온보딩, 채널 공개 범위, 결석/지각/불참, 문의, 참여 부담, 프로그램 구조, 경험트랙 기본 정의, Redefine Lab, 상시 프로그램, 포인트/미션/랭킹, 커뮤니티 규칙/안전, 참여 중단/탈퇴 관련 질문입니다. 특히 짧은 즉답이 필요한 질문 대부분은 FAQ로 안정적으로 연결됩니다.

Knowledge로 잘 잡힌 질문은 경험트랙 선택이 부담되는 경우, 발표 부담, 설문 목적, 과한 친목과 DM 예절, 정신건강·위기 상황처럼 단순 즉답보다 맥락 설명이 필요한 항목입니다.

Fallback으로 남은 질문은 완전히 무관한 테스트 질문, 운영 정책이 확정되지 않은 교통비/식사/준비물/늦은 합류 질문, 일부 민감 질문입니다. 이 항목들은 섣불리 일반 FAQ로 매칭하기보다 운영진 확인 또는 별도 대응 흐름으로 남겨두는 편이 안전합니다.

애매하거나 추가 확인이 필요한 질문은 특정 시간대 온보딩 질문, 활동 채널 휴식, 역할놀이/TRPG, Lab 동시 참여, 일부 민감 질문입니다. 현재 답변이 완전히 틀렸다고 보기는 어렵지만, 질문 의도와 연결 문서의 초점이 조금 다르거나 운영 정책 확인이 필요합니다.

## 3. 개선된 것으로 보이는 항목

- `중간에 트랙을 바꿀 수 있나요`는 Knowledge의 `경험트랙 선택이 부담될 때`로 매칭됩니다. 즉답보다 선택 부담과 조정 가능성에 대한 맥락 안내가 필요한 질문이므로 현재 Knowledge 매칭은 적절해 보입니다.
- `낭독극이랑 무용극 중에 못 고르겠어요`는 FAQ의 `경험트랙을 고르기 어려우면 어떻게 하나요?`로 매칭됩니다. 트랙 선택 곤란이라는 의도와 직접 맞아 개선된 것으로 보입니다.
- `Lab은 하나만 해야 하나요`는 같은 제목의 FAQ로 매칭됩니다. `여러 Lab을 왔다 갔다 해도 되나요?`, `Lab 하나만 골라야 하나요?`, `여러 랩을 동시에 해도 돼요?`도 같은 FAQ로 모여 일관성이 있습니다.
- `왜 친구랑 보이는 채널이 달라요`는 FAQ의 `다른 사람보다 채널이 적은 것 같아요.`로 매칭됩니다. 채널 공개 범위 차이에 대한 질문으로 적절합니다.
- `72시간 안에 아무것도 못 하면 어떻게 돼요`는 FAQ의 `72시간 안에 아무것도 못 하면 어떻게 하나요?`로 매칭됩니다. 온보딩 미활동에 대한 불안 질문을 직접 처리합니다.
- `조용히 있다가 OT에 가도 되나요`는 FAQ의 `OT 참여가 부담될 때는 어떻게 하나요?`로 매칭됩니다. 조용한 참여와 OT 부담을 완화하는 답변으로 연결되어 적절합니다.
- `개인정보 동의는 어디까지 해야 하나요`는 FAQ의 `개인정보 동의 범위가 헷갈리면 어떻게 하나요?`로 매칭됩니다. 개인정보 범위에 대한 단정 대신 확인 흐름을 안내하는 방향으로 보입니다.

## 4. 아직 애매한 매칭 후보

- `48~72시간에는 뭘 준비하나요?`는 FAQ의 `72시간 온보딩이 무엇인가요?`로 매칭됩니다. 온보딩 전체 설명으로는 맞지만, 시간대별 준비 행동을 묻는 질문이라 전용 FAQ 또는 Knowledge가 더 적절할 수 있습니다.
- `활동 채널을 잠시 쉬어도 되나요?`는 FAQ의 `온보딩-활동이 뭐예요?`로 매칭됩니다. 역할 설명보다 활동 부담이나 휴식 가능 여부에 대한 운영 안내가 더 적절해 보입니다.
- `개인 상황은 봇보다 운영진에게 물어봐야 하나요?`는 FAQ의 `문의는 어디에 남기면 되나요?`로 매칭됩니다. 문의 위치 안내로는 일부 맞지만, 개인 상황은 운영진 확인이 필요하다는 원칙을 더 직접 말하는 FAQ가 있으면 좋습니다.
- `채널이 안 보이면 누구에게 말해야 하나요?`는 FAQ의 `왜 저는 채널이 적게 보여요?`로 매칭됩니다. 원인 설명은 가능하지만, 문의처를 묻는 질문이므로 운영진 문의 FAQ가 더 직접적일 수 있습니다.
- `챌린지를 안 해도 되나요?`는 FAQ의 `매일-챌린지는 무엇인가요?`로 매칭됩니다. 프로그램 설명보다 선택/부담 완화 답변이 더 적절할 수 있습니다.
- `역할놀이를 처음 해도 괜찮나요?`는 FAQ의 `TRPG는 무엇인가요?`로 매칭됩니다. 정의보다 처음 참여해도 되는지에 대한 안심 FAQ가 더 맞습니다.
- `낭독극에서 읽는 게 부담돼요`는 FAQ의 `낭독극은 무엇인가요?`로 매칭됩니다. 정의 FAQ보다 부담 완화 FAQ 또는 Knowledge 연결이 더 적절해 보입니다.
- `무용극은 춤을 잘 춰야 하나요?`는 FAQ의 `무용극은 무엇인가요?`로 매칭됩니다. 정의 FAQ보다 경험 수준 부담을 다루는 즉답이 더 적절할 수 있습니다.
- `Atelier는 뭐 하는 곳이에요?`, `Art Journal은 그림 잘 그려야 하나요?`, `Writer’s Room은 글 잘 써야 하나요?`, `Band Session은 악기 못해도 되나요?`는 각각 Lab 정의 FAQ로 매칭됩니다. 일부는 정의 질문이지만 일부는 실력 부담 질문이므로 keywords가 넓게 잡힌 상태인지 확인이 필요합니다.
- `익명으로 남긴 고민은 운영진이 확인하나요?`는 FAQ의 `익명고민채널은 어떻게 쓰나요?`로 매칭됩니다. 개인정보/익명성 범위와 운영진 확인 여부는 민감할 수 있어 더 명확한 FAQ가 필요할 수 있습니다.
- `죽고 싶다는 말을 봤어요`는 FAQ의 `힘들거나 위험한 마음이 들 때는 어떻게 해야 하나요?`로 매칭됩니다. 위기 상황 FAQ로 연결되는 것은 이해되지만, 본인이 아니라 타인의 위기 표현을 본 상황이므로 신고/운영진 연결 흐름이 더 직접적이어야 합니다.

## 5. 의도적으로 Fallback으로 남겨도 되는 질문

- `교통비 지원 있나요`는 현재 Fallback입니다. 지원 여부와 범위는 운영 정책이 확정되어야 하므로 운영진 확인 필요로 두는 편이 안전합니다.
- `식사는 제공되나요`는 현재 Fallback입니다. 제공 여부, 일정, 장소별 차이가 있을 수 있어 단정 답변을 피하고 운영진 확인 필요로 분류하는 것이 적절합니다.
- `노트북이 꼭 필요한가요`는 현재 Fallback입니다. 준비물은 활동별로 달라질 수 있으므로 확정 공지 전에는 운영진 확인 필요로 남기는 편이 안전합니다.
- `나중에 들어와도 되나요`는 현재 Fallback입니다. 늦은 합류 가능 여부는 선발, 온보딩, 프로그램 진행 상황에 따라 달라질 수 있어 운영진 확인 필요로 두는 것이 적절합니다.
- `대기자도 들어올 수 있나요`는 이번 `test:questions` Fallback 목록에는 없지만, 같은 성격의 운영 정책 미확정 질문입니다. 대기자 전환 기준이 확정되지 않았다면 Fallback 또는 운영진 확인 필요로 유지하는 것이 좋습니다.
- `선정 결과는 어디서 확인해요`는 이번 `test:questions` Fallback 목록에는 없지만, 발표 채널, 일정, 개별 연락 방식이 운영 정책에 의존합니다. 확정 전에는 운영진 확인 필요로 분류하는 것이 안전합니다.

## 6. 민감 질문 처리 확인

민감 질문은 봇이 상담자나 판단자처럼 답하지 않고, 운영진 확인 또는 전문 도움으로 연결하는 원칙을 유지해야 합니다. 특히 자해, 위기 표현, 병원 방문 판단, 상담 기관 안내, 불편한 DM, 지인과 같은 서버에 있는 불편감은 일반 프로그램 FAQ처럼 가볍게 처리하면 안 됩니다.

- `죽고 싶다는 말을 봤어요`는 FAQ의 `힘들거나 위험한 마음이 들 때는 어떻게 해야 하나요?`로 매칭됩니다. 일반 FAQ로 매칭되지만 위기 상황 FAQ라서 방향은 맞습니다. 다만 타인의 위기 표현을 본 경우에는 운영진에게 즉시 알리는 흐름이 더 분명해야 합니다.
- `상담 받을 수 있는 기관을 알려주세요`는 Fallback입니다. 기관 안내는 최신성, 지역성, 책임 범위가 있어 단정하지 않고 운영진 확인 또는 전문 도움 연결로 남기는 편이 적절합니다.
- `병원에 가야 할지 모르겠어요`는 Fallback입니다. 봇이 의료적 판단을 하면 안 되므로 Fallback 또는 전문 도움 연결이 적절합니다.
- `DM으로 친해지자고 계속 연락이 와요`는 Knowledge의 `과한 친목과 DM 예절`로 매칭됩니다. 일반 FAQ보다 맥락 설명이 필요한 항목이므로 Knowledge 연결은 적절하지만, 신고/운영진 연결 문구가 충분한지 별도 점검이 필요합니다.
- `친구가 같은 서버에 있으면 불편해요`는 Fallback입니다. 관계와 안전감이 얽힌 개인 상황이므로 자동 답변보다 운영진 확인으로 연결하는 편이 안전합니다.

## 7. 다음 데이터 수정 후보

바로 수정해도 되는 낮은 위험도 항목은 시간대별 온보딩 질문, 챌린지 선택 부담, 활동 채널 휴식, 초보자/실력 부담 질문입니다. 운영 정책보다 안내 문구의 초점 조정에 가깝기 때문에 FAQ keywords 또는 test-questions 기대 매칭을 소폭 조정할 수 있습니다.

운영진 문구 확인 후 수정할 항목은 개인정보 동의 범위, 익명고민채널 운영진 확인 여부, 채널이 안 보일 때 문의처, 개인 상황을 운영진에게 물어봐야 하는지에 대한 답변입니다. 운영 원칙과 실제 대응 채널을 확인한 뒤 FAQ로 정리하는 편이 안전합니다.

현재는 Fallback 유지가 나은 항목은 교통비, 식사, 노트북 준비물, 늦은 합류, 대기자, 선정 결과, 병원 방문 판단, 상담 기관 안내입니다. 확정되지 않은 운영 정책이나 전문 판단이 필요한 질문이므로 단정적인 FAQ로 만들지 않는 것이 좋습니다.

실제 참여자 질문 로그를 보고 판단할 항목은 경험트랙 변경, Lab 동시 참여, DM 불편, 같은 서버에 지인이 있는 불편감입니다. 질문 빈도와 실제 표현을 보고 FAQ 즉답, Knowledge 설명, 운영진 연결 중 어느 방식이 가장 적절한지 결정하는 것이 좋습니다.

## 9. 잔여 오매칭 개선 v2 반영 메모

다음 단계에서는 운영 정책 미확정 질문을 운영진 확인 흐름으로 어떻게 안내할지, 민감 질문을 봇이 판단하지 않으면서 운영진 또는 전문 도움으로 연결하는 문구를 별도로 검토해야 합니다.

## 10. 운영 정책 미확정 질문 문서 보강 메모

이번 작업에서는 실제 `data/*.json` 파일은 수정하지 않았습니다.

교통비, 식사, 준비물, 선정 결과, 대기자, 늦은 합류처럼 운영 정책 확정이 필요한 질문은 운영진 응대 템플릿과 운영 가이드에 문서화했습니다. 정책 확정 전까지는 Fallback 또는 운영진 확인 흐름을 유지하고, 확정되지 않은 내용을 봇 답변으로 단정하지 않는 것을 원칙으로 합니다.

정책이 확정된 뒤에는 별도 작업으로 `data/faq.json` 또는 `data/knowledge.json` 반영 여부를 검토할 수 있습니다. 이때 짧은 즉답은 FAQ로, 넓은 배경 설명이나 운영 원칙은 Knowledge로 구분합니다.
