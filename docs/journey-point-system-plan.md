# 프로젝트 리디파인 여정 포인트 시스템 기능개발문서

## 1. 문서 목적

이 문서는 프로젝트 리디파인 디스코드 봇에 자체 여정 포인트 시스템을 도입하기 위한 기능개발 전 기준 문서입니다. 실제 구현을 시작하기 전에 운영 원칙, 명령어 범위, 데이터 구조, 교환 흐름, 운영자 처리 흐름을 정리합니다.

이 문서는 코드를 변경하거나 배포하도록 지시하는 구현 지시서가 아닙니다. 포인트 기능 구현, Discord 명령어 등록, 데이터 파일 추가, 외부 사이트 연동은 후속 검토와 구현 작업에서 별도로 진행합니다.

## 2. 기본 방향

- MEE6는 참여자 환대, 채팅 활동 기반 EXP, 레벨업 용도로만 사용합니다.
- MEE6의 영어 명령어는 참여자에게 적극적으로 안내하지 않습니다.
- 리디파인 봇은 참여자가 쉽게 이해할 수 있도록 한글 명령어 중심으로 운영합니다.
- 포인트 명칭은 우선 `여정 포인트`로 사용하며, 정식 운영 전 운영진이 최종 확정합니다.
- 여정 포인트는 참여를 강제하는 장치가 아니라 청년동 공간 방문과 프로그램 참여를 가볍게 돕는 동기부여 장치입니다.
- 포인트나 랭킹이 부담, 비교, 경쟁 압박으로 느껴지지 않도록 참여 선택권과 운영 안내를 우선합니다.

## 3. MEE6와 리디파인 봇 역할 분리

| 구분 | 담당 기능 | 운영 기준 |
| --- | --- | --- |
| MEE6 | 신규 참여자 환영 메시지, 채팅 활동 기반 EXP, 레벨업, 서버 활성화 보조, 기본 관리 보조 | 환대와 채팅 활동의 가벼운 피드백에 한정하며, 영어 명령어 중심의 별도 포인트 운영은 적극 안내하지 않음 |
| 리디파인 봇 | `/안내`, `/채널안내`, `/질문`, `/공지`, 민감 질문 운영진 알림, 역할 기반 온보딩 안내 | 프로그램 운영 정보와 안전한 문의 연결을 담당함 |
| 리디파인 봇 | 여정 포인트, 체크인, 미션, 인증, 상점, 교환, 포인트 관리, 교환 관리, 포인트 로그 | 한글 명령어로 자체 운영하며 지급, 사용, 취소, 정정 이력을 확인할 수 있도록 설계함 |

MEE6의 EXP나 레벨은 채팅 활동 표시이며, 리디파인 봇의 여정 포인트 잔액 또는 교환 기록과 합산하거나 상호 전환하는 기준으로 사용하지 않습니다.

## 4. 청년동 포인트 전환 방향

- 리디파인 봇은 청년동 포인트 지급 사이트와 직접 연동하지 않습니다.
- 참여자는 보유한 여정 포인트를 사용해 청년동 포인트 전환을 신청할 수 있습니다.
- `/교환` 신청 시 잔액이 충분하면 여정 포인트를 자동 차감하고, 신청을 `pending` 상태로 기록합니다.
- 신청이 접수되면 운영자 채널에 청년동 포인트 지급 요청을 자동으로 알리는 방향으로 설계합니다.
- 운영자는 청년동 포인트 지급 사이트에서 실제 포인트를 지급한 뒤 `/교환관리`로 지급 완료 처리합니다.
- 지급이 불가능한 경우 운영자가 신청을 취소 처리하고, 차감된 여정 포인트를 반환한 뒤 환불 로그를 남깁니다.
- 청년동 포인트는 청년동 내부에서 정한 사용처에서만 사용할 수 있습니다. 예시 사용처는 벤딩머신, 프린트 카드 충전 등입니다.
- 현금 환급, 외부 재화와의 교환, 타인 양도가 가능한 것처럼 안내하거나 운영하지 않습니다.

## 5. 참여자 명령어

아래 출력은 명령어 동작을 논의하기 위한 문서용 예시이며, 현재 구현된 응답이나 확정된 리워드 정책이 아닙니다.

### `/체크인`

| 항목 | 내용 |
| --- | --- |
| 목적 | 참여자가 오늘 청년동 방문 또는 당일 참여를 가볍게 기록하고, 정책에 따라 포인트를 받을 수 있게 함 |
| 사용자 | 참여자 |
| 입력값 | 선택 입력 `내용` |
| 출력 예시 | `오늘의 체크인이 기록됐어요. 지급 포인트: 10P` |
| 운영 주의사항 | 한국 시간 기준 하루 1회만 지급하며, 출석 강요로 보이지 않도록 가벼운 참여 기록으로 안내함 |

### `/미션`

| 항목 | 내용 |
| --- | --- |
| 목적 | 참여자가 오늘 참여 가능한 선택형 활동과 지급 기준을 확인함 |
| 사용자 | 참여자 |
| 입력값 | 없음 |
| 출력 예시 | `미션 ID: mission_reflection / 보상: 10P / 참여는 선택입니다.` |
| 운영 주의사항 | 미션은 부담 없이 선택할 수 있어야 하며, 게시 전에 기간, 보상, 인증 방법, 적립 상한을 공지함 |

### `/인증`

| 항목 | 내용 |
| --- | --- |
| 목적 | 참여자가 완료한 미션에 대해 검토 가능한 인증을 제출함 |
| 사용자 | 참여자 |
| 입력값 | `미션id`, `내용` |
| 출력 예시 | `인증이 접수되었습니다. 운영진 확인 후 승인되면 여정 포인트가 지급됩니다.` |
| 운영 주의사항 | 필요 이상의 개인정보나 사진 제출을 요구하지 않으며, 승인·반려와 중복 제출 기준을 사전에 안내함 |

### `/포인트`

| 항목 | 내용 |
| --- | --- |
| 목적 | 참여자가 자신의 현재 여정 포인트 잔액을 확인함 |
| 사용자 | 참여자 |
| 입력값 | 없음 |
| 출력 예시 | `현재 보유 여정 포인트는 120P입니다. 포인트는 참여를 돕는 선택형 요소입니다.` |
| 운영 주의사항 | 본인의 잔액만 확인하도록 하고 다른 참여자의 잔액이나 순위를 비교하도록 노출하지 않음 |

### `/상점`

| 항목 | 내용 |
| --- | --- |
| 목적 | 현재 신청 가능한 리워드와 필요한 여정 포인트를 조회함 |
| 사용자 | 참여자 |
| 입력값 | 없음 또는 항목 분류 |
| 출력 예시 | `신청 가능 항목: 청년동 포인트 전환권 100P - 필요 여정 포인트 100P / 실제 지급은 운영진 확인 후 처리됩니다.` |
| 운영 주의사항 | 비용, 재고, 신청 한도, 지급 소요 시간을 명확히 알리고 청년동 내부 사용처라는 점을 표시함 |

### `/교환`

| 항목 | 내용 |
| --- | --- |
| 목적 | 참여자가 리워드 또는 청년동 포인트 전환을 신청함 |
| 사용자 | 참여자 |
| 입력값 | `교환 항목`, 필요 시 `수량` |
| 출력 예시 | `청년동 포인트 전환권 100P 신청이 접수되었습니다. 여정 포인트 100P가 차감되었으며 운영진 지급 확인을 기다립니다. 상태: pending` |
| 운영 주의사항 | 차감 전에 항목과 비용을 재확인할 수 있게 하고, 신청 취소·지급 불가 시 환불 처리 기준과 처리 시간을 안내함 |

## 6. 운영자 명령어

운영자 명령어는 권한이 확인된 운영자만 사용할 수 있어야 하며, 일반 참여자가 실행하거나 운영 로그를 조회할 수 없도록 설계해야 합니다.

### `/포인트관리`

| 항목 | 내용 |
| --- | --- |
| 목적 | 운영자가 사유가 있는 수동 지급 또는 차감을 처리함 |
| 사용자 | 권한이 확인된 운영자 |
| 입력값 | `대상 참여자`, `처리 유형(지급/차감)`, `수량`, `사유` |
| 출력 예시 | `처리 완료: 참여자 A / 지급 20P / 사유: 프로그램 참여 인증 승인 / 거래 ID: TX-001` |
| 운영 주의사항 | 모든 조정에 사유와 처리 운영자를 기록하고, 잘못된 처리는 기존 기록 삭제 대신 정정 거래로 남김 |

### `/교환관리`

| 항목 | 내용 |
| --- | --- |
| 목적 | 운영자가 접수된 교환의 실제 지급 완료, 취소, 환불 처리를 기록함 |
| 사용자 | 권한이 확인된 운영자 |
| 입력값 | `신청 ID`, `처리 상태(completed/cancelled/refunded)`, `메모` |
| 출력 예시 | `교환 신청 RD-001을 completed로 처리했습니다. 지급 확인자: 운영자 B` |
| 운영 주의사항 | 실제 지급 확인 후에만 완료 처리하며, 지급 불가 시 취소와 환불 거래가 모두 기록되었는지 확인함 |

### `/인증관리`

| 항목 | 내용 |
| --- | --- |
| 목적 | 운영자가 접수된 미션 인증을 승인 또는 반려 처리함 |
| 사용자 | 권한이 확인된 운영자 |
| 입력값 | `제출id`, `처리(승인/반려)`, 선택 입력 `메모` |
| 출력 예시 | `인증 승인 완료: 제출 ID submission_... / 지급 20P / 거래 ID tx_mission_...` |
| 운영 주의사항 | `pending` 상태만 처리하며, 승인 시 미션의 `rewardPoints`만큼 지급하고 반려 시 포인트를 지급하지 않음 |

### `/포인트로그`

| 항목 | 내용 |
| --- | --- |
| 목적 | 지급, 차감, 교환, 환불 내역을 조회하여 운영 및 정산을 확인함 |
| 사용자 | 권한이 확인된 운영자 |
| 입력값 | `기간`, `참여자` 또는 `거래 유형`, 필요 시 `신청 ID` |
| 출력 예시 | `2026-05 / refund / RD-001 / +100P / 사유: 청년동 포인트 지급 불가에 따른 반환` |
| 운영 주의사항 | 운영에 필요한 최소 정보만 노출하며, 로그 접근 권한과 보관·내보내기 기준을 정함 |

## 7. MVP 구현 우선순위

### 1단계: 기본 교환 운영 흐름

- `/포인트`
- `/상점`
- `/교환`
- `/포인트관리`
- `/교환관리`
- `/포인트로그`

포인트 잔액, 상점, 교환 신청, 수동 지급·차감, 교환 완료 처리와 이력이 먼저 있어야 운영진이 지급부터 정산까지의 흐름을 작은 범위에서 검증할 수 있습니다.

### 2단계: 참여 활동 연계

- `/체크인`
- `/미션`
- `/인증`
- `/인증관리`

체크인, 미션, 인증은 날짜 기준 판정, 중복 지급 방지, 인증 승인과 반려 로직이 필요합니다. MVP v1에서는 `/체크인`이 한국 시간 기준 하루 1회 10P를 자동 지급하고, `/인증`은 즉시 지급하지 않고 `pending` 제출만 생성합니다. 운영자가 `/인증관리`로 승인하면 해당 미션의 `rewardPoints`만큼 `earn` 거래를 남기고, 반려하면 운영 메모만 남기며 포인트는 지급하지 않습니다.

### 3단계: 운영 효율과 정산 보강

- 운영자 채널 알림 버튼
- 지급 완료/취소 버튼
- CSV 또는 스프레드시트 정산
- 중복 지급 방지
- 기간별 리포트

3단계는 반복 처리 효율과 정산 신뢰성을 높이는 범위입니다. 실제 운영량과 오류 유형을 확인한 뒤 우선순위를 조정합니다.

## 8. 여정 포인트 지급 기준 초안

| 지급 가능 활동 | 운영 검토 기준 |
| --- | --- |
| 체크인 | 일일 지급 횟수와 확인 기준을 정함 |
| 오늘의 미션 | 미션별 보상, 기간, 인증 필요 여부를 공지함 |
| 회고 작성 | 공개 범위와 평가가 아닌 참여 인정 기준을 정함 |
| 퀴즈 참여 | 정답 경쟁보다 참여 여부 중심의 지급을 검토함 |
| 프로그램 참여 인증 | 최소한의 확인 정보와 승인 절차를 정함 |
| 운영진 수동 지급 | 사유와 담당 운영자를 로그에 기록함 |
| 특별 이벤트 참여 | 행사별 기간, 보상, 적립 상한을 사전 공지함 |

지급 기준은 과도한 경쟁을 유발하지 않고 참여자의 속도 차이를 존중해야 합니다. 포인트를 참여 강제 장치로 사용하지 않으며, 운영진은 지급 기준과 변경 사항을 사전에 공지합니다. 특정 활동의 반복 적립이 부담이나 불균형을 만들지 않도록 하루 또는 주간 적립 상한을 둘 수 있습니다.

| 프로그램 굿즈 | 재고 확인 후 제공하는 비현금성 리워드 |
| 음료/간식 관련 리워드 | 청년동 운영 범위 안에서 정한 제공 항목 |
| 프린트 카드 충전 관련 리워드 | 청년동 내부 이용과 관련된 제공 항목 |
| 운영진이 정한 비현금성 리워드 | 공지된 기간, 재고, 신청 기준에 따른 항목 |

실제 항목, 필요 포인트, 재고, 월별 신청 한도는 운영진이 확정하여 공지합니다. 청년동 포인트 전환과 관련 리워드는 청년동 내부에서 정한 사용처로 제한합니다. 운영 상황이나 재고, 지급 오류에 따라 신청을 보류하거나 취소하고 포인트를 환불할 수 있습니다. 항목 안내는 현금 또는 외부 재화처럼 사용할 수 있다는 인상을 주지 않도록 작성합니다.

## 10. 교환 상태값

| 상태 | 의미 | 운영 처리 |
| --- | --- | --- |
| `pending` | 신청 완료, 여정 포인트 차감 완료, 청년동 포인트 지급 대기 | 운영자 채널 알림 후 실제 지급 여부 확인 |
| `completed` | 운영자가 청년동 포인트의 실제 지급을 완료함 | 처리자와 완료 시간을 기록 |
| `cancelled` | 지급 불가 또는 오류로 신청이 취소됨 | 환불 필요 여부를 확인하고 사유 기록 |
| `refunded` | 취소 후 차감된 여정 포인트 반환이 완료됨 | 반환 거래 ID와 처리자를 기록 |

MVP에서는 신청 상태로 `pending`, `completed`, `cancelled`를 우선 사용하고, 취소에 따른 반환은 별도의 `refund` transaction log로 남기는 방향을 제안합니다. 추후 운영상 상태 조회가 필요해지면 `refunded` 표시를 명시적인 교환 상태로 확장할 수 있습니다.

## 11. 교환 흐름

### 청년동 포인트 전환 흐름

1. 참여자가 `/상점`으로 청년동 포인트 전환권과 필요한 여정 포인트를 확인합니다.
2. 참여자가 `/교환`으로 청년동 포인트 전환권을 선택해 신청합니다.
3. 봇이 참여자의 여정 포인트 잔액을 확인합니다.
4. 잔액이 충분하면 필요한 여정 포인트를 자동 차감합니다.
5. 교환 신청을 `pending` 상태로 생성합니다.
6. 운영자 전용 채널에 실제 지급이 필요한 신청 알림을 게시합니다.
7. 운영자가 청년동 포인트 지급 사이트에서 실제 포인트를 지급합니다.
8. 운영자가 `/교환관리`로 신청을 `completed` 처리합니다.
9. 거래 및 처리 로그에 완료 기록을 남깁니다.

### 취소 및 환불 흐름

1. 운영자가 재고, 지급 제한, 오류 등의 사유로 지급 불가 상태를 확인합니다.
2. 운영자가 `/교환관리`로 신청을 `cancelled` 처리하고 사유를 기록합니다.
3. 차감되었던 여정 포인트를 참여자 잔액에 반환합니다.
4. 반환 내용을 `refund` transaction으로 기록하여 원 신청과 연결합니다.
5. 필요한 경우 참여자에게 취소 사유와 환불 완료 여부를 안내합니다.

## 13. 저장 방식 후보

| 방식 | 장점 | 유의점 |
| --- | --- | --- |
| JSON 파일 기반 | 구조가 단순하고 설계 확인이나 로컬 MVP를 빠르게 시작하기 쉬움 | 동시 요청, 백업, 정합성, 수정 이력 관리에 취약하여 실제 참여자 정산 운영에는 주의가 필요함 |
| SQLite | 작은 규모에서 트랜잭션과 조회를 비교적 간단히 확보할 수 있음 | Railway와 같은 배포 환경에서 영속 디스크와 백업 방식을 별도로 확인해야 함 |
| PostgreSQL | 동시성, 트랜잭션, 조회와 정산 확장에 적합하고 Railway 환경의 후보가 될 수 있음 | 스키마 관리, 연결 설정, 접근 통제와 백업 운영이 필요함 |
| Google Sheets 연동 | 운영진이 정산 현황을 직접 확인하고 공유하기 쉬움 | API 권한, 동시 업데이트, 감사 로그와 개인정보 노출 범위를 엄격히 관리해야 함 |

설계와 로컬 MVP는 JSON 구조로 시작할 수 있지만, 실제 참여자 운영 전에는 영속 저장소 검토가 필요합니다. 포인트는 정산과 변경 이력이 중요하므로 단순 파일 저장만 운영에 사용할 경우 백업과 동시성 문제가 발생할 수 있습니다. 청년동 운영진의 정산 편의성을 고려하면 Google Sheets 또는 데이터베이스 연동을 검토할 수 있으며, Railway 운영 환경에서는 PostgreSQL 또는 외부 스프레드시트 연동이 후보가 됩니다.

## 14. 운영자 채널 알림 설계

- `/교환` 신청이 발생하면 운영자 전용 채널에 지급 요청 알림을 남깁니다.
- 신청자 표시는 실제 지급 확인에 필요한 최소 정보만 사용하고, 공개 채널에는 신청 정보가 보이지 않도록 합니다.
- 알림에는 리워드명, 필요한 여정 포인트, 신청 상태, 신청 시간, 신청 ID를 표시합니다.
- v1에서는 운영자가 알림을 확인한 뒤 slash command인 `/교환관리`로 완료 또는 취소를 처리합니다.
- 후속 단계에서는 운영자 채널 메시지에 지급 완료/취소 버튼을 붙여 반복 작업을 줄일 수 있습니다.
- 알림 채널은 운영진만 접근 가능한 채널이어야 하며, 처리 권한도 운영자에게만 허용합니다.

## 15. 로그/정산 원칙

- 모든 지급, 차감, 교환, 환불은 transaction log로 기록합니다.
- 기록 오류는 로그를 삭제하기보다 취소 또는 정정 기록을 추가하여 처리 경위를 보존합니다.
- 운영자 수동 지급과 차감에도 반드시 사유와 처리자를 남깁니다.
- 로그에는 날짜, 거래 타입, 사유, 관련 신청 ID와 처리 주체를 저장합니다.
- 추후 CSV 또는 Google Sheets 내보내기 가능성을 고려하여 일관된 필드를 유지합니다.
- 월별 또는 프로그램 종료 시 지급, 사용, 환불, 미처리 신청을 정산할 수 있도록 설계합니다.

| 장기 미처리 신청 | 처리 기한과 주기적 점검 기준을 정해 오래된 `pending`을 확인함 |

## 17. 다음 구현 단계 제안

아래 단계는 이 문서 이후 별도 승인과 개발 작업으로 진행할 후보입니다. `npm run deploy` 필요 여부는 명령어 등록 변경을 배포하려는 시점의 판단 기준이며, 이번 문서 작성 작업에서는 실행하지 않습니다.

| 단계 | 목적 | 위험도 | 수정 예상 파일 | `npm run deploy` 필요 여부 |
| --- | --- | --- | --- | --- |
| 1. 포인트 시스템 데이터 구조 설계 v1 | 잔액, 거래, 상점, 교환의 필드와 저장 정책을 확정함 | 중간: 정산 정합성 및 개인정보 범위 결정 필요 | `data/` 내 신규 포인트 데이터 파일 후보, 데이터 접근 모듈, 설계 문서 | 아니오. 데이터/설계만 확정할 때는 명령어 재등록 없음 |
| 2. `/포인트`, `/상점`, `/교환`, `/포인트관리`, `/교환관리`, `/포인트로그` 1차 구현 | 잔액 확인부터 교환 처리와 로그 조회까지 MVP 운영 흐름을 제공함 | 높음: 권한, 차감/환불 정합성, 중복 처리 오류 가능 | `src/deploy-commands.js`, 명령어 처리 모듈, 데이터 접근 모듈, 포인트 저장 데이터 | 예. 새 slash command 또는 옵션을 등록할 경우 필요 |
| 3. 청년동 포인트 전환 신청 운영자 알림 구현 | `pending` 신청의 실제 지급 누락을 방지하고 운영진 처리 흐름을 연결함 | 중간: 운영자 채널 접근 권한 및 개인정보 노출 주의 | 알림/로깅 처리 모듈, 환경 설정 문서 또는 채널 설정 데이터 후보 | 명령어 구조가 바뀌지 않으면 보통 불필요, 바뀌면 필요 |
| 4. `/체크인`, `/미션`, `/인증` 구현 | 선택형 참여 활동과 승인 기반 포인트 지급을 지원함 | 높음: 중복 지급, 날짜 기준, 인증 개인정보 처리 필요 | `src/deploy-commands.js`, 명령어 처리 모듈, 미션/인증 저장 데이터 | 예. 신규 slash command 등록 필요 |
| 5. CSV 또는 Google Sheets 정산 연동 검토 | 운영진 정산과 기간별 검토를 효율화함 | 높음: 외부 접근 권한, 개인정보, 동시성 및 감사 이력 관리 필요 | 내보내기 또는 외부 연동 모듈, 환경 설정 문서, 운영 문서 | 명령어가 추가 또는 변경될 때만 필요 |

구현을 시작하기 전에는 지급 기준, 교환 가능 항목, 청년동 내부 사용처, 운영자 권한, 미처리 신청 확인 주기를 운영진이 먼저 확정하는 것이 좋습니다.

## 18. 디스코드 내부 운영 관리 MVP v1

이번 MVP v1에서는 별도 웹 페이지나 Google Sheets, PostgreSQL 연동보다 디스코드 봇 내부 운영 기능을 먼저 완성합니다. 운영자는 JSON 파일을 직접 열지 않고 Slash Command로 미처리 건과 운영 상태를 확인하고, 미션과 상점 항목을 조정할 수 있습니다.

- `/운영현황`은 pending 교환 신청, pending 인증 제출, 활성 미션, 활성 상점 항목, 오늘 체크인, 최근 포인트 로그를 요약합니다.
- `/운영현황 종류:교환대기`와 `/운영현황 종류:인증대기`는 운영자가 처리할 ID를 복사할 수 있게 목록을 표시합니다.
- `/미션관리`는 미션 추가, 수정, 활성화, 일시중지, 종료를 지원합니다.
- 새 미션은 기본 `draft`로 생성하고, 운영자가 명시적으로 활성화해야 참여자 `/미션`에 노출됩니다.
- `/상점관리`는 항목 추가, 수정, 활성화, 일시중지, 품절, 숨김을 지원합니다.
- 새 상점 항목은 기본 `paused`로 생성하고, 운영자가 명시적으로 활성화해야 참여자 `/상점`에 노출됩니다.

이 단계의 저장소는 local JSON repository입니다. 실제 운영 규모가 커지거나 정산 감사가 중요해지는 시점에는 Google Sheets 보조 정산 또는 PostgreSQL 같은 영속 저장소를 별도 단계로 검토합니다.

## 19. 운영 데이터 내보내기와 백업

운영 안정화를 위해 Google Sheets 또는 웹 대시보드보다 먼저 `/운영내보내기` 기반 백업 기능을 구현합니다. 운영자는 포인트, 교환, 인증, 미션, 상점 데이터를 요약으로 확인하거나 JSON/CSV 파일로 내려받아 보관할 수 있습니다.

이번 단계의 목적은 local JSON 기반 MVP 운영 중 데이터 유실 위험을 줄이고, 추후 영속 저장소 전환 전에 출력 형식과 운영 루틴을 정리하는 것입니다. Google Sheets 연동, PostgreSQL 연동, 웹 대시보드는 후속 단계에서 운영 필요성과 개인정보 관리 기준을 확인한 뒤 별도로 검토합니다.
