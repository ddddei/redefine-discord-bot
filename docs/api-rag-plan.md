# 프로젝트 리디파인 디스코드 봇 API/RAG 연동 설계안

## 1. 문서 목적

현재 프로젝트 리디파인 디스코드 봇은 `data/faq.json`과 `data/knowledge.json`을 기반으로 답변하는 FAQ/Knowledge 안내 봇입니다.

이 문서는 향후 OpenAI API, Gemini API 또는 RAG 구조를 연결하기 전에 검토해야 할 구조와 운영 원칙을 정리하기 위한 설계안입니다. 지금 당장 API를 연결하거나 코드를 수정하는 문서가 아니며, 현재의 FAQ → Knowledge → Fallback 구조를 유지하면서 안전하게 확장하는 방향을 기준으로 합니다.

## 2. 현재 구조 요약

현재 `/질문` 명령어의 기본 흐름은 다음과 같습니다.

1. 사용자가 `/질문 내용: 궁금한 내용`을 입력합니다.
2. `data/faq.json`에서 먼저 관련 답변을 검색합니다.
3. FAQ에서 찾지 못하면 `data/knowledge.json`에서 프로그램 지식창고를 검색합니다.
4. FAQ와 Knowledge 모두에서 찾지 못하면 fallback 안내를 제공합니다.
5. 답변하지 못한 질문은 설정이 있는 경우 `#봇-질문로그`에 질문 내용 중심으로 기록됩니다.

### 장점

- 답변 근거가 로컬 JSON 데이터에 있어 운영자가 직접 통제할 수 있습니다.
- 예상 질문에 대해 안정적이고 일관된 답변을 제공합니다.
- API 비용이 들지 않습니다.
- 외부 API 장애와 무관하게 기본 안내가 가능합니다.
- 민감한 운영 기준을 운영진이 직접 문장 단위로 관리할 수 있습니다.

### 한계

- 사용자가 FAQ keywords와 다른 표현으로 질문하면 매칭이 어려울 수 있습니다.
- 여러 문서를 조합해 자연스럽게 요약하는 능력은 제한적입니다.
- 질문 의도가 모호할 때 운영진 문의로 넘길지, 기존 안내로 답할지 세밀하게 구분하기 어렵습니다.
- FAQ/Knowledge가 늘어날수록 keywords 관리가 중요해집니다.

## 3. API 연동이 필요한 이유

API 연동은 기존 구조를 대체하기보다, 현재 구조가 답하기 어려운 질문을 보조하기 위해 검토할 수 있습니다.

- 사용자가 정확한 키워드로 묻지 않아도 질문 의도를 더 유연하게 이해하기 위해
- FAQ/Knowledge 내용을 자연스럽게 요약해 답변하기 위해
- 비슷한 여러 항목을 조합해 더 읽기 쉬운 안내를 만들기 위해
- 운영진 문의로 넘길 질문과 봇이 답할 수 있는 질문을 더 부드럽게 구분하기 위해
- Fallback 질문을 분석해 FAQ/Knowledge 보강 후보를 찾기 위해

## 4. API 연동 기본 원칙

API를 붙이더라도 아래 전제를 유지합니다.

- API는 기존 FAQ/Knowledge를 대체하지 않습니다.
- FAQ/Knowledge를 우선 검색합니다.
- API는 마지막 보조 답변 생성 단계로 사용합니다.
- API 답변은 문서 기반 안내를 자연스럽게 정리하는 역할에 가깝습니다.
- 운영진 확인이 필요한 내용은 단정하지 않습니다.
- 일정, 장소, 참여 확정, 권한, 운영 조치처럼 운영 기준이 필요한 질문은 운영진 안내를 기준으로 확인하도록 답합니다.
- 위기 표현, 정신건강, 개인정보, 타인 특정 내용은 자동 답변보다 운영진 확인을 우선합니다.
- 민감한 상황은 운영진 또는 전문기관/긴급 지원 안내로 연결합니다.

## 5. 권장 답변 흐름

```text
사용자 질문
  ↓
FAQ 검색
  ↓
FAQ 매칭 성공 → FAQ 답변
  ↓
FAQ 매칭 실패
  ↓
Knowledge 검색
  ↓
Knowledge 매칭 성공 → Knowledge 답변
  ↓
Knowledge 매칭 실패
  ↓
API 요약/보조 답변
  ↓
API로도 불확실하거나 민감한 질문 → 운영진 문의 안내
  ↓
필요 시 #봇-질문로그 기록
```

권장 흐름의 핵심은 API를 가장 먼저 호출하지 않는 것입니다. FAQ와 Knowledge로 답할 수 있는 질문은 로컬 데이터로 처리하고, API는 fallback 직전 또는 fallback 이후의 보조 단계로 제한합니다.

## 6. RAG 구조 제안

RAG를 도입할 경우 아래 자료를 지식 소스로 사용할 수 있습니다.

- `data/faq.json`: 짧은 질문과 즉답
- `data/knowledge.json`: 프로그램 구조, 운영 원칙, 상세 설명
- `data/notices.json`: 공지 템플릿
- `data/channels.json`: 채널 안내
- `docs/*.md`: 운영 가이드, 공지문 패키지, 문의 대응 템플릿, 문제 상황 대응 가이드 등

초기에는 복잡한 벡터 DB 없이 JSON/문서 기반 검색으로 시작할 수 있습니다.

권장 초기 구조:

1. FAQ와 Knowledge의 기존 검색을 유지합니다.
2. 실패한 경우에만 문서 후보를 간단히 검색합니다.
3. 검색된 후보 문단만 API에 전달합니다.
4. API는 후보 문단 안에서만 답변하도록 제한합니다.
5. 문서에 없는 내용은 운영진 문의로 넘깁니다.

추후 질문량이 늘고 문서가 커지면 벡터 DB, 임베딩, 문서 chunking을 검토할 수 있습니다. 단, 그 단계에서도 익명고민채널이나 DM 내용 같은 민감한 대화는 지식 소스로 자동 수집하지 않습니다.

## 7. 개인정보 및 민감정보 원칙

API/RAG 연동 시 개인정보와 민감정보 처리를 가장 보수적으로 설계합니다.

- 참여자 이름, Discord ID, DM 내용, 익명고민 내용을 무단으로 학습하거나 저장하지 않습니다.
- 익명고민채널 내용을 자동 수집하지 않습니다.
- 봇 질문로그는 현재처럼 질문 내용 중심으로 최소 기록합니다.
- 질문로그에 사용자 ID, 닉네임, 채널 ID 같은 식별자를 불필요하게 남기지 않습니다.
- 위기 표현, 정신건강, 개인정보, 타인 특정 내용은 자동 답변보다 운영진 확인을 우선합니다.
- API 요청에 민감정보를 그대로 보내지 않도록 주의합니다.
- 운영진이 확인해야 할 내용은 API에 넘기기 전에 민감정보 제거 또는 요약 여부를 검토합니다.
- API 제공자 설정, 보관 정책, 로그 정책은 실제 도입 전에 운영진이 확인합니다.

## 8. API가 직접 판단하지 말아야 할 영역

봇과 API가 직접 판단하지 말아야 할 영역은 아래와 같습니다.

- 의료적 판단
- 심리치료 조언
- 법적 판단
- 위기 개입 판단
- 참여자 상태 분류
- 특정 참여자 평가
- 운영진 조치 결정
- 참여 확정 여부 결정
- 징계, 제한, 탈퇴 처리 결정
- 가족 또는 보호자에게 알릴지 여부 판단

이런 질문이 들어오면 "운영진 확인이 필요합니다", "전문기관 또는 긴급 지원이 필요할 수 있습니다"처럼 안전한 안내로 연결해야 합니다.

## 9. 시스템 프롬프트 초안

API를 붙일 때 시스템 프롬프트에는 최소한 아래 원칙이 들어가야 합니다.

```text
당신은 프로젝트 리디파인 디스코드 안내 봇입니다.

프로젝트 리디파인은 준비중·고립·은둔 청년이 자기 속도로 참여할 수 있도록 돕는 프로그램입니다.

답변 원칙:
- 따뜻하고 차분하며 부담 없는 한국어로 답합니다.
- 참여자를 평가하거나 단정하지 않습니다.
- 처음부터 모든 것을 잘해야 한다는 압박을 주지 않습니다.
- 문서에 있는 내용만 바탕으로 답합니다.
- 문서에 없는 내용은 추측하지 않고 운영진 확인이 필요하다고 안내합니다.
- 일정, 장소, 참여 확정, 운영 조치, 권한, 세부 기준은 운영진 공지를 기준으로 확인하라고 답합니다.
- 개인정보를 요구하지 않습니다.
- 참여자 이름, ID, DM 내용, 익명 고민 등 민감정보를 답변에 포함하지 않습니다.
- 위기 표현, 자해, 자살, 위험한 마음, 정신건강 위기, 개인정보 노출, 타인 특정 내용은 자동 답변으로 해결하려 하지 않습니다.
- 위기 상황은 운영진에게 알리고, 필요하면 주변 사람, 보호자, 전문기관, 긴급 지원 도움을 요청하도록 안내합니다.
- 의료적 판단, 심리치료, 법적 판단, 운영진 조치 결정을 대신하지 않습니다.
```

응답 스타일은 짧고 명확하게 유지합니다. API가 긴 설명을 만들기보다, FAQ/Knowledge의 문장을 참여자가 읽기 쉽게 정리하는 역할에 가깝게 둡니다.

## 10. 환경변수 설계 초안

실제 값은 문서나 코드에 직접 쓰지 않습니다. 아래는 이름 제안일 뿐입니다.

- `AI_PROVIDER`
- `OPENAI_API_KEY`
- `GEMINI_API_KEY`
- `AI_MODEL`
- `AI_ENABLED`
- `AI_MAX_TOKENS`
- `AI_LOG_ENABLED`
- `AI_TIMEOUT_MS`
- `AI_FALLBACK_ONLY`

주의사항:

- 실제 API Key는 절대 문서에 쓰지 않습니다.
- 실제 API Key는 코드에 하드코딩하지 않습니다.
- 실제 API Key는 GitHub issue, PR, Discord, 캡처 이미지에 올리지 않습니다.
- Railway Variables 같은 배포 환경변수는 운영자가 직접 관리합니다.
- AI 도구가 Railway Variables를 직접 수정하지 않도록 합니다.

## 11. 비용 관리 원칙

API 비용은 작게 시작하고 끌 수 있게 설계합니다.

- 처음에는 API 호출을 fallback 상황에만 제한합니다.
- 모든 질문을 API로 보내지 않습니다.
- FAQ/Knowledge에서 답을 찾으면 API를 호출하지 않습니다.
- 짧은 답변을 우선합니다.
- `AI_MAX_TOKENS`로 최대 응답 길이를 제한합니다.
- 운영 초기에 사용량을 모니터링합니다.
- 비용이 커지면 `AI_ENABLED=false`로 API 기능을 끌 수 있게 합니다.
- 실패 질문 분석은 배치나 수동 검토로 시작하고, 자동 API 호출은 최소화합니다.
- API 호출 로그를 남기더라도 질문 원문과 민감정보를 과도하게 저장하지 않습니다.

## 12. 단계별 도입 계획

1. 설계 문서 작성
   - API/RAG 연동 목적, 제한 원칙, 민감정보 처리 원칙을 문서로 합의합니다.

2. API 없이 FAQ/Knowledge 품질 개선
   - `docs/knowledge-audit.md` 기준으로 FAQ와 Knowledge 역할을 정리합니다.
   - `npm run test:questions` 결과를 보고 Fallback과 오매칭을 줄입니다.

3. Mock 응답 구조 설계
   - 실제 API 호출 없이 함수 형태와 실패 처리 흐름만 설계합니다.
   - Fallback 상황에서 어떤 문맥을 넘길지 결정합니다.

4. 환경변수 추가
   - 실제 값 없이 변수 이름과 사용 여부만 정리합니다.
   - 운영진이 Railway Variables 관리 방식을 확인합니다.

5. fallback 상황에서만 API 호출
   - FAQ/Knowledge 검색 실패 시에만 API를 호출합니다.
   - 민감한 질문은 API 호출 전에 운영진 문의로 넘깁니다.

6. 운영진 로그와 비용 모니터링
   - API 호출 횟수, 실패 횟수, Fallback 질문 유형을 확인합니다.
   - 비용이 예상보다 크면 `AI_ENABLED`로 끕니다.

7. 실제 운영 후 답변 품질 개선
   - 운영진이 API 답변을 검토합니다.
   - 반복 질문은 API에 맡기기보다 FAQ/Knowledge에 추가합니다.
   - 민감 질문 처리 기준을 지속적으로 보강합니다.

## 13. 구현 시 수정될 가능성이 있는 파일

실제 수정은 이 문서 작업에서 하지 않습니다. 향후 구현 시 수정될 가능성이 있는 파일은 아래와 같습니다.

- `src/handlers.js`
  - `/질문` 처리 흐름에 API 보조 답변 단계를 추가할 수 있습니다.

- `src/search.js`
  - FAQ/Knowledge 검색 결과와 API 후보 문맥 생성 로직을 조정할 수 있습니다.

- `src/data.js`
  - 문서나 JSON 지식 소스를 로드하는 경로가 추가될 수 있습니다.

- `src/embeds.js`
  - API 답변 표시 형식, 제한 문구, 운영진 문의 안내를 조정할 수 있습니다.

- `src/ai.js`
  - API 호출, provider 선택, timeout, fallback 처리용 신규 파일이 생길 수 있습니다.

- `.env.example`
  - 실제 값 없이 필요한 환경변수 이름만 예시로 추가할 수 있습니다.

- `README.md`
  - AI 기능 사용 여부, 환경변수, 운영 주의사항을 문서화할 수 있습니다.

- `docs/operation-guide.md`
  - API 기능을 켜고 끄는 운영 절차와 점검 방법을 추가할 수 있습니다.
