# 프로젝트 리디파인 운영 문제 상황 대응 가이드

봇 오류, 배포 오류, 디스코드 권한 문제, 커뮤니티 안전 문제, 참여자 민감 상황이 발생했을 때 운영자가 빠르게 원인을 파악하고 안전하게 대응하기 위한 문서입니다.

## 1. 기본 대응 원칙

### 상황

봇이나 커뮤니티 운영 중 예상하지 못한 문제가 생겼을 때 공통으로 적용합니다.

### 먼저 확인할 것

- 기술 문제인지, 커뮤니티 안전 문제인지 먼저 구분합니다.
- 참여자에게 보이는 문제인지, 운영진 내부 문제인지 확인합니다.
- 실제 토큰, 실제 채널 ID, 실제 환경변수 값은 공유하지 않습니다.
- `.env` 파일 내용은 캡처하거나 전달하지 않습니다.

### 대응 방법

1. 문제를 재현하거나 확인한 위치를 기록합니다.
2. 최근 수정한 파일이 있는지 확인합니다.
3. 참여자 안전과 개인정보가 걸린 상황이면 기술 확인보다 안전 조치를 먼저 합니다.
4. 혼자 판단하기 어려운 커뮤니티 문제는 운영진 내부 확인 후 대응합니다.
5. 의료적 판단, 심리치료, 법적 판단을 대신하는 표현은 피합니다.

### 복사 가능한 안내문

```text
문제를 알려주셔서 감사합니다. 운영진이 상황을 확인하고 있습니다.

확인되는 대로 필요한 안내를 드리겠습니다. 개인정보나 민감한 내용은 공개 채팅방보다 운영진 문의 채널로 남겨 주세요.
```

## 2. 문제가 생겼을 때 빠른 확인 순서

### 상황

원인이 봇, 데이터, 배포, 권한, 커뮤니티 문제 중 어디에 있는지 아직 모를 때 사용합니다.

### 먼저 확인할 것

```bash
git status --short
git diff --stat
npm run validate:data
npm run test:questions
node --check src/index.js
node --check src/deploy-commands.js
```

### 대응 방법

1. `git status --short`로 수정된 파일 범위를 확인합니다.
2. `git diff --stat`으로 변경 규모를 확인합니다.
3. 데이터 수정이 있었다면 `npm run validate:data`를 먼저 실행합니다.
4. 질문 매칭 문제라면 `npm run test:questions`를 확인합니다.
5. 코드 수정이 있었다면 `node --check`로 문법 오류를 확인합니다.
6. Railway와 로컬 `npm run start`를 동시에 켜면 봇이 중복 실행되어 충돌할 수 있으니 한쪽만 켭니다.

### 복사 가능한 안내문

```text
현재 원인을 확인 중입니다. 봇 응답, 데이터, 배포 상태를 순서대로 점검하고 있습니다.

잠시만 기다려 주세요. 확인 후 다시 안내드리겠습니다.
```

## 3. 봇이 답변하지 않을 때

### 상황

Slash Command를 입력했는데 봇이 응답하지 않거나, 응답이 매우 늦습니다.

### 먼저 확인할 것

- 봇이 온라인 상태인지 확인합니다.
- Railway에서 실행 중인지, 로컬에서 `npm run start`를 켜 둔 상태인지 확인합니다.
- Railway와 로컬 봇을 동시에 켜지 않았는지 확인합니다.
- 최근 코드 수정이 있었다면 문법 오류를 확인합니다.

### 대응 방법

1. `git status --short`로 최근 변경 범위를 확인합니다.
2. 코드 수정이 있었다면 `node --check src/index.js`를 실행합니다.
3. 데이터 수정이 있었다면 `npm run validate:data`를 실행합니다.
4. Railway 로그에서 시작 실패나 로그인 실패가 있는지 확인합니다. 실제 토큰 값은 공유하지 않습니다.
5. 로컬 확인이 필요하면 Railway 실행을 잠시 멈춘 뒤 로컬에서 확인합니다.

### 복사 가능한 안내문

```text
현재 봇 응답 상태를 확인하고 있습니다.

일시적으로 답변이 늦거나 응답하지 않을 수 있어요. 급한 문의는 운영진 문의 채널에 직접 남겨 주세요.
```

## 4. Unknown interaction 오류가 날 때

### 상황

명령어 실행 후 `Unknown interaction` 또는 상호작용 만료 관련 오류가 보입니다.

### 먼저 확인할 것

- 봇 응답이 너무 늦어지는지 확인합니다.
- 같은 봇이 Railway와 로컬에서 동시에 실행 중인지 확인합니다.
- 최근 명령어 처리 코드가 수정되었는지 확인합니다.

### 대응 방법

1. Railway와 로컬 `npm run start`를 동시에 켠 상태라면 하나만 남깁니다.
2. 코드 수정이 있었다면 `node --check src/index.js`를 실행합니다.
3. 오류가 특정 명령어에서만 반복되는지 확인합니다.
4. 참여자에게는 문의 채널을 임시 안내합니다.

### 복사 가능한 안내문

```text
현재 일부 명령어 응답이 정상적으로 표시되지 않는 문제가 있어 확인 중입니다.

급한 내용은 봇 명령어 대신 운영진 문의 채널에 남겨 주세요.
```

## 5. /공지 명령어가 보이지 않을 때

### 상황

운영자가 `/공지` 명령어를 찾지 못하거나 실행할 수 없습니다.

### 먼저 확인할 것

- 운영자 역할과 권한이 맞게 부여되어 있는지 확인합니다.
- 명령어가 보이지 않는 서버나 채널에서 권한 제한이 있는지 확인합니다.
- Slash Command 등록이 필요한 변경을 했는지 확인합니다.

### 대응 방법

1. 먼저 Discord 서버의 운영자 역할/권한을 확인합니다.
2. 특정 채널에서만 안 보이는지, 서버 전체에서 안 보이는지 확인합니다.
3. 데이터만 수정한 경우 일반적으로 `npm run deploy`는 필요 없습니다.
4. `src/deploy-commands.js` 또는 Slash Command 구조를 수정한 경우에만 `npm run deploy`가 필요합니다.
5. 실제 권한이나 서버 설정은 문서만 보고 바로 바꾸지 말고 운영진 내부 확인 후 조정합니다.

### 복사 가능한 안내문

```text
`/공지` 명령어 표시 여부를 확인 중입니다.

먼저 운영자 역할과 채널 권한을 확인한 뒤, 필요한 경우 명령어 등록 상태를 점검하겠습니다.
```

## 6. 새 명령어 또는 선택지가 디스코드에 반영되지 않을 때

### 상황

새 Slash Command, 옵션, 선택지가 Discord에 보이지 않습니다.

### 먼저 확인할 것

- 실제로 Slash Command 구조를 수정했는지 확인합니다.
- 단순 데이터 수정인지, `src/deploy-commands.js` 수정인지 구분합니다.
- 명령어 등록이 완료되었는지 확인합니다.

### 대응 방법

1. 데이터만 수정한 경우 일반적으로 `npm run deploy`는 필요 없습니다.
2. `src/deploy-commands.js` 또는 Slash Command 구조를 수정한 경우에만 `npm run deploy`를 실행합니다.
3. 배포 후 Discord 클라이언트 반영이 늦을 수 있으니 잠시 기다렸다가 다시 확인합니다.
4. 반영 전까지는 기존 명령어와 문의 채널을 안내합니다.

### 복사 가능한 안내문

```text
새 명령어 또는 선택지 반영 상태를 확인 중입니다.

반영 전까지는 기존 명령어나 운영진 문의 채널을 이용해 주세요.
```

## 7. GitHub Actions CI가 실패했을 때

### 상황

Pull request 또는 push 후 GitHub Actions 검증이 실패합니다.

### 먼저 확인할 것

- 실패한 job 이름과 로그의 첫 오류를 확인합니다.
- JSON 검증 실패인지, 질문 매칭 테스트 실패인지, 코드 문법 문제인지 구분합니다.
- 실제 토큰이나 환경변수 값이 로그에 노출되지 않았는지 확인합니다.

### 대응 방법

1. 로컬에서 같은 명령어를 실행합니다.
2. 데이터 오류라면 `npm run validate:data`를 확인합니다.
3. 질문 매칭 문제라면 `npm run test:questions` 결과를 확인합니다.
4. 코드 문법 문제라면 `node --check src/index.js`와 `node --check src/deploy-commands.js`를 확인합니다.
5. 실패 로그는 필요한 부분만 공유하고, 민감 정보는 공유하지 않습니다.

### 복사 가능한 안내문

```text
CI 실패 원인을 확인 중입니다.

로컬에서 같은 검증 명령어를 실행해 재현 여부를 확인한 뒤 수정하겠습니다.
```

## 8. Railway 배포가 실패했을 때

### 상황

Railway에서 새 배포가 실패하거나 봇이 시작되지 않습니다.

### 먼저 확인할 것

- Railway 로그의 첫 오류를 확인합니다.
- 환경변수 이름이 누락되었는지 확인하되 실제 값은 공유하지 않습니다.
- 최근 수정 파일이 코드인지 데이터인지 문서인지 확인합니다.
- Railway와 로컬 `npm run start`가 동시에 켜져 있지 않은지 확인합니다.

### 대응 방법

1. `git status --short`와 `git diff --stat`으로 변경 범위를 확인합니다.
2. 로컬에서 `npm run validate:data`를 실행합니다.
3. 코드 수정이 있었다면 `node --check src/index.js`를 실행합니다.
4. Railway 로그에서 dependency, start command, token, permission 관련 오류를 구분합니다.
5. 실제 토큰이나 `.env` 내용은 절대 공유하지 않습니다.

### 복사 가능한 안내문

```text
현재 배포 상태를 확인하고 있습니다.

배포가 정상화되기 전까지 봇 응답이 늦거나 일시적으로 중단될 수 있습니다. 급한 문의는 운영진 문의 채널에 남겨 주세요.
```

## 9. JSON 수정 후 봇이 이상할 때

### 상황

FAQ, Knowledge, notices, channels, test questions 수정 후 봇 응답이 이상합니다.

### 먼저 확인할 것

- JSON 쉼표, 따옴표, 대괄호가 맞는지 확인합니다.
- 수정한 파일이 `data/*.json`인지 확인합니다.
- 질문 매칭이 바뀐 것인지, 데이터 로드 자체가 실패한 것인지 구분합니다.

### 대응 방법

1. `npm run validate:data`를 실행합니다.
2. 통과하지 않으면 오류가 난 JSON 파일부터 수정합니다.
3. 통과했지만 답변이 이상하면 `npm run test:questions`로 매칭 결과를 봅니다.
4. 데이터만 수정한 경우 일반적으로 `npm run deploy`는 필요 없습니다.
5. 봇 재시작이 필요한 운영 환경인지 확인합니다.

### 복사 가능한 안내문

```text
일부 안내 데이터 반영 상태를 확인 중입니다.

답변이 어색하거나 맞지 않는 경우 운영진 문의 채널에 남겨 주세요. 확인 후 수정하겠습니다.
```

## 10. 질문이 엉뚱한 답변으로 매칭될 때

### 상황

`/질문` 답변이 질문 의도와 다르게 나옵니다.

### 먼저 확인할 것

- 어떤 질문 문장이 어떤 FAQ 또는 Knowledge 항목에 매칭되는지 확인합니다.
- keywords가 너무 넓거나 겹치는지 확인합니다.
- FAQ와 Knowledge 역할이 섞였는지 확인합니다.

### 대응 방법

1. `npm run test:questions`로 현재 매칭 결과를 확인합니다.
2. 반복되는 질문은 `data/test-questions.json`에 추가할지 검토합니다.
3. FAQ는 짧은 즉답, Knowledge는 운영 원칙과 상세 설명으로 역할을 나눕니다.
4. `docs/knowledge-audit.md`를 기준으로 keywords를 보강합니다.
5. 수정 후 `npm run validate:data`와 `npm run test:questions`를 다시 실행합니다.

### 복사 가능한 안내문

```text
봇 답변이 질문 의도와 다르게 나온 점 확인했습니다.

운영진이 질문 매칭을 점검하고, 필요한 경우 FAQ나 지식창고를 보강하겠습니다.
```

## 11. #봇-질문로그에 질문이 기록되지 않을 때

### 상황

봇이 답변하지 못한 질문이 로그 채널에 남지 않습니다.

### 먼저 확인할 것

- 로그 채널 설정이 있는지 확인합니다.
- 봇이 해당 채널에 메시지를 보낼 권한이 있는지 확인합니다.
- 실제 채널 ID나 환경변수 값은 공유하지 않습니다.
- 질문이 실제로 Fallback 처리되었는지 확인합니다.

### 대응 방법

1. 운영 환경의 로그 설정 여부를 확인합니다.
2. Discord에서 봇의 채널 보기/메시지 보내기 권한을 확인합니다.
3. `.env`나 실제 환경변수 값은 열람하거나 공유하지 않습니다.
4. 설정이 없으면 로그 기록은 되지 않을 수 있음을 운영진 내부에 공유합니다.

### 복사 가능한 안내문

```text
봇 질문로그 기록 상태를 확인 중입니다.

로그 설정과 봇 권한을 점검한 뒤, 필요한 경우 운영진 내부에서 조정하겠습니다.
```

## 12. 운영진 전용 채널이 참여자에게 보일 때

### 상황

운영진 전용 채널, 로그 채널, 내부 논의 채널이 참여자에게 보입니다.

### 먼저 확인할 것

- 어떤 참여자 역할에서 채널이 보이는지 확인합니다.
- 채널 권한과 카테고리 권한이 다르게 설정되어 있는지 확인합니다.
- 민감한 내용이나 개인정보가 노출되었는지 확인합니다.

### 대응 방법

1. 즉시 운영진 내부에 공유합니다.
2. 해당 채널에 민감 정보가 있었는지 확인합니다.
3. Discord 권한 변경은 운영진 확인 후 진행합니다.
4. 노출된 정보가 개인정보라면 19번 섹션 기준으로 대응합니다.
5. 참여자에게는 필요한 범위에서만 차분히 안내합니다.

### 복사 가능한 안내문

```text
채널 표시 설정에 문제가 있었는지 운영진이 확인하고 있습니다.

혹시 의도하지 않게 보인 내용이 있다면 외부에 공유하지 말아 주세요. 확인 후 필요한 안내를 드리겠습니다.
```

## 13. 참여자가 불편한 DM을 신고했을 때

### 상황

원치 않는 DM, 반복 연락, 사적인 접근 신고가 들어옵니다.

### 먼저 확인할 것

- 참여자가 지금 추가 연락을 받고 있는지 확인합니다.
- 상대방을 공개 채팅방에서 직접 지목하고 있는지 확인합니다.
- 캡처나 상황 설명이 있는지 확인합니다.

### 대응 방법

1. 신고 접수를 확인하고 참여자에게 혼자 대응하지 않아도 된다고 안내합니다.
2. 가능한 경우 캡처와 대략적인 시간을 요청합니다.
3. 공개 채팅방에서 갈등이 커지지 않도록 문의 채널 또는 DM으로 옮깁니다.
4. 운영진 내부에서 반복성, 위협성, 개인정보 노출 여부를 확인합니다.
5. 필요한 경우 안내, 메시지 정리, 이용 제한 등 조치를 검토합니다.

### 복사 가능한 안내문

```text
불편한 DM을 알려주셔서 감사합니다. 혼자 대응하지 않아도 괜찮습니다.

가능하다면 관련 캡처와 대략적인 상황을 운영진에게 전달해 주세요. 운영진이 확인하고 필요한 안내를 드리겠습니다.
```

## 14. 익명고민채널에 민감한 내용이 올라왔을 때

### 상황

익명고민채널에 자해, 가족 문제, 관계 갈등, 특정인 비난, 개인정보가 포함된 내용이 올라옵니다.

### 먼저 확인할 것

- 위기 표현이 포함되어 있는지 확인합니다.
- 타인을 특정할 수 있는지 확인합니다.
- 개인정보가 포함되어 있는지 확인합니다.
- 익명 답변만으로 안전하게 대응 가능한지 확인합니다.

### 대응 방법

1. 위기 표현이 있으면 18번 섹션으로 대응합니다.
2. 개인정보가 있으면 19번 섹션으로 대응합니다.
3. 타인을 특정하거나 비난하는 내용은 상황 중심으로 다시 안내합니다.
4. 익명 채널만으로 어려운 경우 운영진에게 직접 알려 달라고 안내합니다.
5. 운영진 내부에서 답변 범위와 삭제/정리 필요성을 확인합니다.

### 복사 가능한 안내문

```text
고민을 남겨주셔서 감사합니다.

이 내용은 익명 채널 답변만으로는 안전하게 확인하기 어려울 수 있어요. 가능하다면 운영진 문의 채널이나 운영진이 안내한 DM 방식으로 필요한 만큼만 더 알려 주세요.
```

## 15. 커뮤니티 규칙 위반이 발생했을 때

### 상황

반말, 욕설, 비하, 조롱, 캡처 공유, 과한 친목, 스팸 등이 발생합니다.

### 먼저 확인할 것

- 실수에 가까운지 반복 행동인지 확인합니다.
- 특정 참여자에게 피해가 있는지 확인합니다.
- 공개 대응이 필요한지, 개별 안내가 적절한지 확인합니다.

### 대응 방법

1. 가벼운 실수는 커뮤니티 약속을 다시 안내합니다.
2. 반복되거나 안전을 해치는 행동은 운영진 내부 확인 후 조치합니다.
3. "경고 없이 밴" 같은 강한 표현은 피합니다.
4. "운영진 확인 후 필요한 조치가 있을 수 있습니다"로 안내합니다.
5. 관련 메시지 정리 필요성을 운영진 내부에서 확인합니다.

### 복사 가능한 안내문

```text
리디파인에서는 서로의 속도와 안전을 위해 커뮤니티 약속을 함께 지키고 있습니다.

해당 표현이나 행동은 다른 참여자에게 부담이 될 수 있어 운영진이 안내드립니다. 반복될 경우 운영진 확인 후 필요한 조치가 있을 수 있습니다.
```

## 16. 공개 채팅방에서 갈등이 커질 때

### 상황

공개 채팅방에서 논쟁, 오해, 감정적 대화가 길어집니다.

### 먼저 확인할 것

- 특정인을 향한 공격이 있는지 확인합니다.
- 참여자들이 계속 반응하면서 갈등이 커지는지 확인합니다.
- 공개 채팅방에서 해결 가능한 사안인지 확인합니다.

### 대응 방법

1. 공개 채팅방에서 대화를 잠시 멈추도록 안내합니다.
2. 추가 설명은 운영진 문의 채널로 옮기도록 안내합니다.
3. 필요한 경우 관련 메시지를 정리할지 운영진 내부에서 확인합니다.
4. 특정인을 평가하거나 단정하지 않습니다.
5. 당사자별로 필요한 안내를 분리해 진행합니다.

### 복사 가능한 안내문

```text
현재 대화가 공개 채팅방에서 길어지며 서로에게 부담이 될 수 있어 잠시 멈추겠습니다.

추가로 이야기할 내용은 운영진 문의 채널로 남겨 주세요. 운영진이 확인 후 필요한 안내를 드리겠습니다.
```

## 17. 참여 중단 또는 탈퇴 분위기가 생겼을 때

### 상황

한 명 또는 여러 명이 공개 채팅방에서 그만두고 싶다는 말을 하거나 이탈 분위기가 생깁니다.

### 먼저 확인할 것

- 공개 채팅방에서 개인 사정이 노출되고 있는지 확인합니다.
- 다른 참여자에게 불안이 번지고 있는지 확인합니다.
- 위기 표현이 포함되어 있는지 확인합니다.

### 대응 방법

1. 참여 중단을 고민할 수 있음을 인정합니다.
2. 자세한 사정은 공개 채팅방보다 운영진 문의 채널로 옮기도록 안내합니다.
3. 사유를 강요하지 않습니다.
4. 위기 표현이 있으면 18번 섹션 기준으로 대응합니다.
5. 필요한 경우 운영진 내부에서 후속 연락 방식을 정합니다.

### 복사 가능한 안내문

```text
참여를 계속할지 고민되는 마음이 생길 수 있습니다.

다만 개인 상황이 포함될 수 있으니 공개 채팅방에 자세히 남기기보다 운영진 문의 채널로 알려 주세요. 사유를 길게 설명하지 않아도 괜찮습니다.
```

## 18. 위기 표현이 포함된 메시지가 올라왔을 때

### 상황

"죽고 싶다", "자해하고 싶다", "위험한 마음이 든다", "혼자 감당하기 어렵다" 같은 표현이 올라옵니다.

`/질문`으로 들어온 위기 표현, 자해/자살 언급, 불편한 DM, 반복 연락, 개인정보 노출 등 민감 질문의 자동 알림 설계는 [sensitive-question-alert-plan.md](sensitive-question-alert-plan.md)를 함께 확인합니다. 실제 대응은 이 문서와 운영진 내부 기준을 함께 기준으로 삼습니다.

### 먼저 확인할 것

- 지금 즉시 안전이 걱정되는 표현인지 확인합니다.
- 혼자 있는지, 주변에 도움을 요청할 사람이 있는지 확인이 필요한 상황인지 봅니다.
- 운영진이 혼자 판단하지 않고 내부 확인이 필요한지 확인합니다.

### 대응 방법

1. 공개 채팅방이라면 자극적인 논쟁이 이어지지 않도록 대화를 정리합니다.
2. 운영진 내부에 즉시 공유합니다.
3. 참여자에게 혼자 감당하지 않아도 된다고 안내합니다.
4. 위급하거나 안전이 걱정되는 경우 주변 사람, 보호자, 긴급 지원, 전문기관 도움을 요청하도록 안내합니다.
5. 운영진은 의료적 판단, 심리치료, 법적 판단을 대신하지 않습니다.
6. 운영진이 확정한 기관명, 연락처, 외부 링크가 있다면 내부 기준에 따라 안내합니다.

### 복사 가능한 안내문

```text
지금 마음이 많이 힘든 상태라면 혼자 감당하지 않아도 됩니다.

운영진이 직접 확인하겠습니다. 지금 바로 안전이 걱정되는 상황이라면 디스코드 답변을 기다리지 말고 주변의 신뢰할 수 있는 사람, 보호자, 긴급 지원, 전문기관에 도움을 요청해 주세요.

운영진도 필요한 도움으로 연결할 수 있도록 확인하겠습니다.
```

## 19. 개인정보가 노출되었을 때

### 상황

실명, 연락처, 주소, 건강 정보, 가족 정보, 민감한 개인 사정이 공개 채팅방이나 익명 채널에 올라옵니다.

### 먼저 확인할 것

- 본인 개인정보인지, 타인 개인정보인지 확인합니다.
- 이미 다른 참여자가 반응했는지 확인합니다.
- 삭제 또는 메시지 정리가 필요한지 확인합니다.

### 대응 방법

1. 가능하면 더 이상 공유하지 않도록 안내합니다.
2. 운영진 내부에서 메시지 정리 필요성을 확인합니다.
3. 타인의 개인정보가 포함된 경우 더 신중하게 다룹니다.
4. 캡처나 재공유를 하지 않도록 안내합니다.
5. 필요한 경우 개인 문의 채널로 이동해 후속 안내합니다.

### 복사 가능한 안내문

```text
공개 채팅방에는 실명, 연락처, 주소처럼 민감한 개인정보를 올리지 않는 편이 안전합니다.

해당 내용은 운영진이 확인하겠습니다. 다른 곳에 캡처하거나 공유하지 말아 주세요. 필요한 안내는 운영진 문의 채널로 이어가겠습니다.
```

## 21. 대응 후 기록하기

### 상황

문제를 처리한 뒤 재발 방지와 운영진 공유가 필요합니다.

### 먼저 확인할 것

- 어떤 문제가 있었는지
- 언제, 어디에서 발생했는지
- 참여자 개인정보가 포함되어 있는지
- 어떤 조치를 했는지
- 추가 follow-up이 필요한지

### 대응 방법

1. 운영진 내부 기록 공간에 요약합니다.
2. 개인정보와 실제 채널 ID, 사용자 ID, 토큰 값은 불필요하게 남기지 않습니다.
3. 재발 가능성이 있으면 문서나 FAQ/Knowledge 보강 필요성을 검토합니다.
4. 기술 문제는 실행한 명령어와 결과를 함께 기록합니다.
5. 커뮤니티 안전 문제는 판단 근거와 후속 확인 계획을 남깁니다.

### 복사 가능한 기록 양식

```text
문제 발생 일시:
발견 위치:
문제 유형:
확인한 내용:
실행한 조치:
참여자 안내 여부:
추가 확인 필요:
재발 방지 메모:
```

## 22. 최종 주의사항

- 데이터만 수정한 경우 일반적으로 `npm run deploy`는 필요 없습니다.
- `src/deploy-commands.js` 또는 Slash Command 구조를 수정한 경우에만 `npm run deploy`가 필요합니다.
- `/공지` 명령어가 보이지 않으면 먼저 운영자 역할과 권한을 확인합니다.
- Railway와 로컬 `npm run start`를 동시에 켜면 충돌 가능성이 있습니다.
- `.env`와 실제 토큰은 절대 공유하지 않습니다.
- 실제 채널 ID, 실제 환경변수 값도 문서나 공개 채팅에 적지 않습니다.
- 위기 표현이 있는 경우 운영진이 혼자 판단하지 않고 내부 확인 및 필요한 지원 연결을 검토합니다.
- 운영진은 의료적 판단, 심리치료, 법적 판단을 대신하지 않습니다.
- 참여자에게 안내할 때는 평가하거나 단정하지 않고, 필요한 만큼만 알려 달라는 톤을 유지합니다.
