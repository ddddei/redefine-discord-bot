# DM 대화 완성 운영판 계획서 — 접근 제어·견고성·보존 정책·연습 콘텐츠·운영 런북 (완성 배포판)

DM 대화 연습 기능을 **"이 문서의 전 항목 구현 = 실참여자 상대로 즉시 운영 가능"** 상태로 끌어올리는 전체 명세입니다. 기존 기준 문서 [dm-chat-mvp-plan.md](dm-chat-mvp-plan.md)(v1·1단계·운영 가시성 완료 상태)를 전제로 하며, 이 계획이 끝나면 DM 트랙의 공식 보류 항목(3-b 보존 정책)까지 전부 해소됩니다. 100%(운영 필수: A~D·F)와 150%(연습 콘텐츠: E)를 구분해 두었습니다 — E는 같은 PR에 포함하되, 일정이 급하면 E만 분리 가능한 커밋 구성입니다.

## 0. 완성 정의

1. 리디파인 서버 멤버가 아닌 사용자의 DM에는 응답(AI 호출·기록)하지 않는다
2. 붙여넣기 연타·장애 상황에서도 비용·행이 통제된다 (분당 제한·순차 처리·타임아웃)
3. 2,000자 초과 응답이 유실 없이 전송된다
4. 보존 기간 경과 로그 정리와 참여자 요청 삭제가 스크립트·절차로 동작하고, 첫 안내문이 보존 기간을 고지한다
5. `/운영현황 종류:DM대화`에서 오늘 토큰 사용량을 볼 수 있다
6. 연습 시나리오 6종·연습 정리가 동작한다 (150%)
7. 운영 런북([dm-chat-operation-guide.md](dm-chat-operation-guide.md) 신규)만 보고 신규 운영자가 활성화→일상 운영→사고 대응을 수행할 수 있다
8. `check:release` 통과, 기존 DM 흐름·admin·백업 테스트 무수정 통과 항목과 확장 항목 구분 명시

## 0.1 운영 결정 3건 (이 계획서의 제안 기본값 — 승인 시 함께 확정)

| 결정 | 제안 기본값 | 근거 |
| --- | --- | --- |
| 로그 보존 기간 | **90일** (`DM_CHAT_RETENTION_DAYS=90`, `0`=무기한) | 개인 대화 데이터 최소 보관 원칙과 운영 회고 필요의 절충. 안전 감지 레코드는 예외적으로 180일(운영 보호 목적) |
| 서버 멤버 제한 | **켬** (`DM_CHAT_MEMBER_ONLY=true` 기본) | 비참여자 DM은 비용·악용 통로. `GUILD_ID` 미설정 시에만 제한 없이 동작(개발 환경 배려) |
| 분당 버스트 제한 | **5회/분** (`DM_CHAT_BURST_LIMIT_PER_MINUTE=5`, `0`=해제) | 일 30회 상한만으로는 1분 안에 30회 소진 가능. 정상 대화 속도(분당 2~3회)에 여유 |

## 1. 작업 A — 접근 제어·남용 방지 (100%)

### 1.1 서버 멤버 확인

- `handleDmChatMessage` 게이트에 멤버 확인 추가: `GUILD_ID` 설정 + `DM_CHAT_MEMBER_ONLY !== 'false'`일 때, 발신자가 해당 길드 멤버인지 확인(`client.guilds` 캐시 → miss 시 `members.fetch` 1회, 결과를 인메모리 캐시 10분).
- 비멤버: **조용히 무시하지 않고 1회만** 안내("이 DM 연습은 리디파인 참여자에게 열려 있어요.") 후 이후 침묵(안내 발송 기록은 notices 패턴 재사용). AI 호출·대화 기록 없음. 안전 감지도 하지 않음(참여자가 아니므로 운영 알림 대상 아님 — 런북에 명시).
- 멤버 확인 실패(API 오류)는 **허용 쪽으로 폴백**(기존 사용자 차단 사고 방지) + 콘솔 경고.

### 1.2 분당 버스트 제한

- KST 무관 롤링 60초, 사용자별 `role=user` 메시지 수 기준(로그에서 계산 — 기존 일일 제한과 동일 패턴, 상태 파일 없음).
- 초과 시: 메시지는 저장·로그 전송(가시성 유지), AI 미호출, 고정 안내 "조금 천천히 이야기해요. 잠시 후 다시 보내 주세요." **분당 제한 응답 자체는 1분에 1회만 발송**(안내 도배 방지).
- 민감 감지 메시지는 제한과 무관하게 안전 흐름 전부 수행(기존 원칙 유지 — 어떤 제한도 안전 경로에 우선하지 않는다).

### 1.3 사용자별 순차 처리 (in-flight 가드)

- 같은 사용자의 AI 응답 생성 중 새 메시지 도착 시: 저장·로그는 즉시, AI 호출은 직전 응답 완료 후 순차 실행(사용자별 promise 체인, 인메모리). 서로 다른 사용자는 병렬 유지.
- 목적: 응답 순서 뒤집힘·이중 호출 방지. 재시작 시 초기화 허용.

### 1.4 OpenAI 호출 타임아웃

- `getDmChatReply`의 openai 호출에 30초 타임아웃(AbortController). 초과 시 기존 오류 폴백 경로("답변을 만드는 중에 문제가 생겼어요")로 합류. 재시도는 하지 않는다(참여자가 재발화하는 것이 자연스러움).

## 2. 작업 B — 응답 견고성 (100%)

1. **2,000자 분할 전송**: 응답이 Discord 한도(2,000자)를 넘으면 문장 경계 우선으로 분할해 순차 전송(최대 2조각, 그 이상은 절단 + "…"). `AI_MAX_TOKENS=500` 기준 드물지만 전송 실패는 메시지 유실이므로 방어.
2. **타이핑 표시**: AI 호출 전 `channel.sendTyping()` 1회(실패 무시) — 응답 지연 체감 완화.
3. **연속 오류 경고**: 같은 사용자 아닌 **전역 기준** AI 오류가 10분 내 5회 이상이면 운영 로그 채널에 경고 embed 1회(스로틀) — OpenAI 장애를 운영자가 즉시 인지. `AI_ENABLED=false` 대응은 런북에.

## 3. 작업 C — 보존·삭제 정책 구현 (3-b 해소, 100%)

### 3.1 보존 정리 스크립트 `scripts/cleanup-dm-chat-logs.js`

- 기준: `DM_CHAT_RETENTION_DAYS`(0.1절 기본 90) 경과 메시지 제거. **안전 감지 레코드(`safetyDetection` 존재)는 180일** 적용(별도 env 없이 상수 — 이중 기간을 런북에 명시).
- 기본 **dry-run**(제거 대상 요약만 출력), `--apply`로 실제 정리. 정리 전 해당 파일을 `data/dm-chat-logs.backup-<ts>.json`으로 1회 복사(로컬, 커밋 금지 경로).
- notices·historyResets는 해당 사용자의 메시지가 전부 제거돼도 유지(재고지 방지·초기화 기준점 보존).
- 운영 절차: 백업 자동화가 있으므로 **수동 실행을 공식 절차**로(월 1회, 런북 체크리스트). 자동 스케줄링은 v2(사고 시 복구 창구를 남기는 보수 선택).

### 3.2 참여자 요청 삭제 `scripts/cleanup-dm-chat-logs.js --user <discordId> --apply`

- 같은 스크립트의 사용자 모드: 해당 사용자의 messages·notices·historyResets 전부 제거 + 요약 출력. [production-data-reset-guide.md](production-data-reset-guide.md)에 절차 연결(요청 접수 → 신원 확인 → 실행 → 회신).
- 백업 스냅샷에 남은 과거 데이터의 한계(완전 삭제 아님)를 런북·회신 문구에 정직하게 명시.

### 3.3 첫 안내문 고지 갱신 (notice v2)

- `FIRST_NOTICE`에 보존 기간 1줄 추가: "대화 기록은 90일 뒤 자동 정리되고, 원하면 언제든 삭제를 요청할 수 있어요."
- notices 레코드에 `noticeVersion` 추가(스키마 **version 4**, normalizeData 관용 처리 — 기존 레코드는 v1 취급). `hasNotice`가 버전을 비교해 **기존 사용자에게도 갱신 고지 1회** 발송.
- `DM_CHAT_RETENTION_DAYS`가 90이 아니면 문구의 기간도 env 값으로 렌더(불일치 고지 방지). 무기한(0)이면 "운영 종료 시까지 보관되며 삭제 요청 가능" 문구로 대체.

## 4. 작업 D — 비용 가시성 완성 (100%)

- openai 응답의 `usage`(input/output tokens)를 assistant 로그 레코드에 `tokens: { input, output }`로 저장(없으면 null — mock/폴백).
- `/운영현황 종류:DM대화`에 "오늘 토큰: 입력 X · 출력 Y" 1줄 추가. 금액 환산은 하지 않는다(단가 변동 — 런북에 환산표 링크만).
- `/admin` DM 로그 응답에는 토큰을 노출하지 않는다(운영 요약이면 충분, 응답 최소화).

## 5. 작업 E — 연습 콘텐츠 (150%)

### 5.1 연습 시나리오 6종 (신규 `src/dmChatScenarios.js` — 콘텐츠 상수)

| 트리거(`연습: <이름>`) | 상황 | 시나리오 프롬프트 요지 |
| --- | --- | --- |
| 첫인사 | 처음 보는 또래에게 말 걸기 | 상대 역을 연기하되 반응은 항상 우호적~중립, 부담 주는 되물음 금지 |
| 자기소개 | 모임에서 돌아가며 자기소개 | 짧은 자기소개를 들어주고 좋았던 점 1개 + 살릴 점 1개 |
| 부탁하기 | 사소한 부탁(자리, 물건, 도움) | 거절당하는 전개는 만들지 않음(연습 단계 배려) |
| 거절하기 | 부담스러운 제안 거절 | 상대 역이 가볍게 제안, 어떤 거절이든 수용하고 존중 |
| 잡담 | 날씨·음식·게임 등 소소한 화제 | 화제 전환 예시를 자연스럽게 시범 |
| 면접 | 짧은 아르바이트 면접 문답 | 압박 질문 금지, 답변마다 짚어주기 1개 |

- 정확 일치 트리거: `연습 메뉴`(목록 안내), `연습: <이름>`(시작 — 시작 안내 + 상대 역 첫마디), `연습 끝`(종료 안내 + 자연스러운 마무리 1줄). 시나리오 중에는 developer 프롬프트에 시나리오 지침이 추가된다.
- 상태 저장: `activeScenarios: [{ userId, scenarioId, startedAt }]` (스키마 version 4에 포함, 사용자당 1개, `연습 끝`·`새로 시작`·다음 날(KST)에 자동 해제).
- 공통 지침: 상대 역은 언제나 안전한 반응(조롱·무시·갑작스런 공격성 금지), 3~4턴마다 잘한 점을 짧게 짚기. 안전 감지·일일 제한 등 기존 게이트는 시나리오 중에도 동일 적용.

### 5.2 연습 정리

- 트리거 `오늘 연습 정리`: 오늘(KST) 이 사용자의 대화를 바탕으로 "좋았던 점 1가지 + 다음에 시도해볼 것 1가지"를 2~3문장으로 생성(전용 프롬프트, 일일 제한 카운트에 포함). 오늘 대화가 없으면 "오늘은 아직 연습 기록이 없어요. 편하게 말을 걸어 보세요."
- 평가·점수·등급 표현 금지(배려 원칙) — 프롬프트에 명시.

### 5.3 첫 안내문에 사용법 요약

- `FIRST_NOTICE` 말미에 1줄: "『연습 메뉴』라고 보내면 연습 주제를, 『새로 시작』이라고 보내면 대화를 새로 시작할 수 있어요." (3.3의 notice v2 갱신과 같은 커밋)

## 6. 작업 F — 운영 런북 `docs/dm-chat-operation-guide.md` (신규, 100%)

이 문서만으로 신규 운영자가 운영 가능해야 한다. 목차 확정:

1. **활성화 절차**: env 체크리스트(표) → Railway 설정 → 테스트 계정 확인 5단계
2. **일상 운영**: `/운영현황 종류:DM대화` 읽는 법, `/admin` 필터 사용법, 주간 점검 항목
3. **안전 알림 대응 SOP**: 알림 수신 → 로그 확인 → 판단 기준(키워드 감지는 자동 판단이 아님) → 참여자 연락 원칙 → 기록 방법. 긴급 상황 연락 체계는 운영진 내부 결정 칸
4. **삭제 요청 처리**: 접수 → 확인 → `--user` 스크립트 → 회신 문구 예시(백업 한계 고지 포함)
5. **보존 정리 루틴**: 월 1회 dry-run → 확인 → `--apply`
6. **비용·한도 조정**: 토큰 읽는 법, `DM_CHAT_DAILY_LIMIT`·`AI_MAX_TOKENS` 조정 기준, 모델 단가 확인처
7. **장애 대응**: OpenAI 오류 경고를 받았을 때(§2-3), `AI_ENABLED=false` 일시 중단 절차(기록·안전 알림은 유지됨), 복구 확인
8. **금칙**: `/admin` 쓰기 없음, matchedKeyword 비노출, 로그 파일 직접 편집 금지(스크립트 경유)
