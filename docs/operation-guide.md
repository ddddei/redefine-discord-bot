# 운영 가이드

리디파인 디스코드 안내 봇을 혼자 운영할 때 참고하는 운영 문서입니다.

## 참여자 입장 전 최종 점검 체크리스트

- [운영 전 QA 리허설 시나리오](prelaunch-rehearsal-scenario.md)를 기준으로 테스트 참여자와 운영자 흐름을 1회 이상 끝까지 실행합니다.
- Railway에서 봇 상태가 Online인지 확인합니다.
- 로컬에서 봇이 실행 중이 아닌지 확인합니다.
- 디스코드에서 `/안내`를 실행해 응답을 확인합니다.
- 디스코드에서 `/채널안내`를 실행해 채널 안내가 정상 표시되는지 확인합니다.
- 디스코드에서 `/질문`을 실행해 FAQ 응답이 정상 표시되는지 확인합니다.
- 디스코드에서 `/공지 종류:봇사용안내`를 실행해 공지 템플릿이 정상 표시되는지 확인합니다.
- `#봇-질문로그`에 미응답 질문 로그가 기록되는지 확인합니다.
- 운영진 전용 채널을 참여자가 볼 수 없는지 권한을 확인합니다.
- 봇 사용 안내 공지를 참여자가 보기 쉬운 채널에 고정합니다.
- 리허설 후 테스트 데이터와 실제 운영 데이터를 구분하고, 운영용 미션/상점만 active 상태로 남겼는지 확인합니다.
- `/운영현황`과 `/admin`을 함께 확인해 오늘의 운영 큐, 대기 건, 최근 로그, 활성 미션/상점 수가 같은 흐름을 보여주는지 확인합니다.

## 참여자에게 안내할 기본 명령어

- `/안내`
- `/포인트`
- `/상점`
- `/체크인 내용:오늘의 한마디`
- `/미션`
- `/질문 내용:궁금한 내용`

참여자가 어떤 명령어를 써야 할지 헷갈리면 먼저 `/안내`를 확인해 달라고 안내합니다. `/안내` 허브에서 처음 왔어요, 오늘 뭐 하면 되나요?, 내 포인트, 상점/교환, 미션/인증, 문의하기를 선택해서 볼 수 있으므로 `/교환`과 `/인증` 같은 세부 명령어를 처음부터 외우지 않아도 됩니다.

### `/안내` 허브 안내

`/안내`는 참여자용 메인 허브입니다. 처음 안내 채널을 별도로 만들 경우 [participant-onboarding-notice.md](participant-onboarding-notice.md)의 공지문을 복사해 고정 공지로 활용하고, "먼저 `/안내`를 실행하고 궁금한 내용을 메뉴에서 선택해 주세요"라고 짧게 적어 둡니다.

이 표시는 편의를 위한 안내 기능이며 실제 Discord 권한을 대신하지 않습니다. 실제 역할 부여와 채널 접근 권한은 운영자가 Discord에서 별도로 확인해야 합니다.

### `/채널안내` 역할별 보조 문구

`/채널안내`는 온보딩 역할이 감지되면 역할에 따라 짧은 보조 안내 문구를 다르게 보여줄 수 있습니다. 현재 v1은 채널 목록을 필터링하는 단계가 아니라 안내 문구를 보강하는 단계입니다.

이 문구는 실제 채널 권한이나 노출 범위를 대신하지 않습니다. 실제 역할 부여와 채널 접근 권한은 운영자가 Discord에서 별도로 확인해야 합니다.

## 운영진용 명령어

- `/운영현황`
- `/공지 종류:봇사용안내`
- `/공지 종류:일정안내`
- `/공지 종류:참여리마인드`
- `/공지 종류:준비물`
- `/공지 종류:결석안내`
- `/공지 종류:문의안내`
- `/인증관리 제출id:제출ID 처리:승인`
- `/인증관리 제출id:제출ID 처리:반려 메모:운영 메모`

운영자는 먼저 `/운영현황`으로 전체 상태를 확인합니다. 첫 화면에서 오늘의 운영 큐, 교환 대기, 인증 대기, 오늘 체크인, 오늘 반응 승인, 최근 포인트 로그를 확인한 뒤 드롭다운에서 필요한 메뉴를 선택합니다. 첫 운영 전에는 `첫날 점검`에서 환경변수/채널, active 미션/상점, 대기 건, 예시 데이터 제외, 백업 안내를 함께 확인합니다.

교환 처리는 `/교환관리`, 인증 처리는 `/인증관리`, 포인트 수동 지급과 차감은 `/포인트관리`, 미션과 상점 수정은 `/미션관리`와 `/상점관리`에서 진행합니다. 허브는 처리 위치를 안내하는 점검 화면이며 기존 처리 명령어는 그대로 유지합니다.

`/admin` 첫 화면의 오늘의 운영 큐는 기본 읽기 전용입니다. 별도 쓰기 게이트를 켜면 확인 모달을 거쳐 처리할 수 있으며 Discord 명령과 동일한 `pointsRepository` 및 운영 JSON 경로를 사용하므로 결과가 `/운영현황`과 읽기 API에 즉시 반영됩니다. pending 교환, pending 인증, 오늘 반응 승인/반려, 오늘 포인트 거래, 알림 실패 후속 확인, 오래된 pending 또는 중복 pending 같은 QA 경고를 한곳에 모아 보여줍니다. example/demo/sample 데이터와 2030년대 예시 날짜는 운영 큐에 섞이지 않아야 합니다.

정산이나 운영 종료 후에는 `/운영내보내기`로 요약 또는 파일 백업을 생성합니다. 자세한 허브 사용법은 [operator-dashboard-guide.md](operator-dashboard-guide.md)를 확인합니다.

## 참여 활동 포인트 운영

`/체크인`은 참여자가 하루 1회 가볍게 참여 기록을 남기고 기본 10P를 받는 명령어입니다. 날짜 기준은 한국 시간입니다. 체크인은 출석 압박이나 경쟁 장치가 아니며, 지급 기준과 포인트 수량은 운영진 안내를 우선합니다.

`/미션`은 현재 `active` 상태인 선택형 미션만 짧게 보여줍니다. 본문은 미션명과 다음 행동이 먼저 보이게 구성하고 `M001` 같은 미션 코드는 선택 메뉴와 직접 입력 안내에서만 보조로 사용합니다. 참여자 안내의 기본 흐름은 "미션 인증 채널에 글, 사진, 영상을 올리고 운영진이 ✅ 반응으로 확인하면 포인트가 지급된다"입니다. 선택 메뉴를 사용하면 글 인증 모달이 열리지만, 이는 채널 업로드가 어려운 경우의 보조 흐름으로 설명합니다. 미션은 가능한 범위에서 선택하는 활동으로 안내하고, 모든 참여자가 반드시 수행해야 하는 과제처럼 표현하지 않습니다.

`/인증`은 미션 코드를 몰라도 실행할 수 있으며, 단독 실행 시 `/미션`과 같은 선택 메뉴를 보여줍니다. 미션과 내용을 직접 입력하면 바로 제출하고, 미션만 입력하면 글 인증 모달을 엽니다. 제출은 `pending`으로 저장할 뿐 포인트를 즉시 지급하지 않습니다. 참여자에게는 `/인증`을 기본 방식이 아니라 직접 제출이 필요한 경우의 보조 수단으로 안내합니다. 선택 첨부파일이 있으면 파일명, URL, content type, 크기를 제출 기록에 함께 저장합니다. 제출이 접수되면 `ACTIVITY_REVIEW_CHANNEL_ID` 또는 `LOG_CHANNEL_ID`로 운영자 검토 알림이 전송됩니다. 채널 ID가 없어도 봇은 중단되지 않고 콘솔 경고만 남깁니다.

미션 인증 채널 반응 승인 흐름을 사용할 경우 참여자는 `/인증`을 입력하지 않고 `MISSION_SUBMISSION_CHANNEL_ID`로 지정된 채널에 글, 사진, 영상 인증 메시지를 올립니다. 참여자가 이 채널에 처음 인증 메시지를 올리면 봇은 1회만 짧은 안내를 답글로 남겨 운영진 확인 후 포인트 지급과 개인정보 최소 제출 원칙을 알려줍니다. 운영자는 지급 대상 메시지에 ✅ 반응을 누르고, 지급 대상이 아니면 ❌ 반응을 누릅니다. 봇은 `MISSION_SUBMISSION_CHANNEL_ID` 채널의 `MISSION_APPROVE_EMOJI`와 `MISSION_REJECT_EMOJI` 반응만 처리하며, 기본 지급 포인트는 `MISSION_REACTION_REWARD_POINTS` 값입니다. 같은 메시지는 `messageId` 기준으로 한 번만 처리되어 중복 지급되지 않고, 운영자 권한이 없는 사용자의 반응은 무시됩니다.

반응 승인을 처리할 수 있는 운영자는 `Administrator`, `ManageMessages`, 또는 선택 환경변수 `OPERATOR_ROLE_ID` 역할 보유자입니다. 승인 기록은 `data/reaction-approvals.local.json`에 저장되고, 승인 시 `pointTransactions`에는 `relatedType: "missionReactionApproval"` 지급 거래가 남습니다. 처리 알림은 `ACTIVITY_REVIEW_CHANNEL_ID`가 있으면 해당 채널로, 없으면 `LOG_CHANNEL_ID`로 전송됩니다. 이 로그에는 참여자 DM과 원본 인증 채널 공개 답글이 각각 `전송 완료`, `전송 실패`, `비활성` 중 어떤 상태였는지도 함께 표시됩니다. 원본 인증 채널 공개 답글은 `REACTION_APPROVAL_PUBLIC_REPLY`가 `true`일 때만 남기며 기본값은 `false`입니다. 참여자 DM 알림은 `REACTION_APPROVAL_DM_USER`로 제어하고 기본값은 `true`입니다. DM 전송에 실패해도 포인트 지급, 반려 기록, 포인트 로그는 유지되며 운영자 로그와 `/운영현황`의 `반응 후속 확인`에서 실패 상태를 확인합니다. `MISSION_SUBMISSION_CHANNEL_ID`가 없으면 반응 승인 기능은 동작하지 않고 콘솔 경고만 남습니다.

`/상점`과 `/교환`도 모두 선택형으로 안내할 수 있습니다. `/교환`을 단독 실행하면 `/상점`과 같은 항목 선택 메뉴가 열리고, 신청 코드를 알고 있는 참여자는 `/교환 항목:S001`처럼 직접 입력해도 됩니다. 운영자는 참여자 안내에서 코드보다 항목 이름과 미션 이름을 중심으로 설명해도 됩니다.

상점과 미션 제목은 짧고 명확하게 작성합니다. 참여자 화면에는 코드보다 이름, 목적, 지급 포인트, 인증 방식이 먼저 보이도록 관리하고, 사진이나 영상 인증이 필요한 미션은 운영 전 안내합니다. 상점/미션 본문은 참여자가 선택할 때 필요한 정보만 남기고, 신청 코드와 미션 코드는 보조 정보로만 다룹니다.

운영 전에는 `POINT_REDEEM_CHANNEL_ID`, `ACTIVITY_REVIEW_CHANNEL_ID`, fallback으로 쓸 `LOG_CHANNEL_ID`가 설정되어 있는지 확인합니다. 알림 채널이 없거나 전송 권한이 부족해도 참여자 신청 자체는 막지 않지만, 콘솔에 `[redeem-alert]` 또는 `[submission-alert]` 로그가 남으므로 운영 시작 전 한 번 확인합니다.

실제 운영 전에는 운영용 기본 미션과 상점 항목을 1개 이상 등록해야 합니다. 추천 기본값은 [운영용 기본 미션/상점 설계](operation-default-items-plan.md)를 기준으로 정하고, 등록 절차는 [미션/상점 등록 가이드](mission-shop-setup-guide.md)를 따릅니다. 운영용 미션은 강제 과제가 아니라 참여자가 선택할 수 있는 활동으로 설명하고, 포인트는 경쟁 점수가 아니라 참여 기록이라는 점을 반복해서 안내합니다.

청년동 포인트 전환 항목은 운영 초기에 우선 등록하는 것을 권장합니다. 외부 구독권이나 수량 제한 상품은 실제 제공 가능 여부, 수량, 유효기간, 지급 방식이 확정된 뒤 active로 전환합니다. 확정 전에는 hidden 또는 paused 상태로 두고 참여자에게 노출하지 않습니다.

교환 신청 전에는 포인트와 항목을 확인해 달라는 안내를 보여주고, 신청 후 단순 변심에 따른 취소/환불은 어렵다는 점을 부드럽게 안내합니다. 다만 중복 신청, 시스템 오류, 운영 오류, 잘못된 지급은 운영자 판단으로 `/교환관리`에서 취소 또는 환불완료 처리할 수 있습니다.

운영자는 `/인증관리`로 제출을 승인 또는 반려합니다. 승인 시 미션의 `rewardPoints`만큼 리디파인 포인트가 지급되고 `pointTransactions`에 `earn` 거래가 남습니다. 반려 시 포인트를 지급하지 않으며, 메모에는 참여자를 평가하거나 낙인찍는 표현 대신 필요한 확인 사항만 남깁니다.

인증 내용과 첨부파일에는 과도한 개인정보나 민감한 사적 정보가 담기지 않도록 안내합니다. 첨부파일 URL은 운영자 확인용으로만 사용하고 외부 공유 전 포함 여부를 확인합니다. 필요한 최소 내용만 받고, 세부 지급 기준은 운영진이 공지한 안내를 우선합니다.

## 미응답 질문 로그 운영 방법

`/질문` 명령어가 FAQ에서 답변을 찾지 못하면 `LOG_CHANNEL_ID`가 설정된 경우 `#봇-질문로그`에 질문 내용과 시간이 기록됩니다.

운영 중에는 `#봇-질문로그`를 주기적으로 확인하고, 반복해서 들어오는 질문을 `data/faq.json`에 FAQ로 추가합니다. FAQ로 쓰기에는 넓은 프로그램 설명이나 배경 안내에 가까운 질문은 `data/knowledge.json`에 지식창고 항목으로 추가합니다. 반영한 뒤에는 같은 질문을 `/질문`으로 다시 테스트해 봇이 새 답변을 찾는지 확인합니다.

`/운영현황`의 `FAQ 후보`는 fallback 질문을 반복 횟수별로 묶어 보여주는 읽기 전용 보조 화면입니다. 자동으로 FAQ를 수정하지 않으며, 운영자가 복사해 검토한 뒤 반영합니다.

미응답 질문 로그에는 사용자 이름이나 사용자 ID를 기록하지 않습니다. 운영자는 질문 내용만 보고 FAQ 개선에 활용합니다.

## 민감 질문 알림 운영 주의사항

`/질문`에 민감 표현이 포함되면 FAQ/지식창고 답변보다 운영진 확인 안내가 먼저 표시되고, `SAFETY_ALERT_CHANNEL_ID` 또는 `LOG_CHANNEL_ID`로 운영진 알림이 전송됩니다.

- 민감 질문 알림 채널은 운영진 전용 채널이어야 하며 참여자가 볼 수 없는지 권한을 확인합니다.
- 알림은 키워드 기반 신호이며 자동 판단이 아니므로 운영진 확인이 필요합니다.
- 실제 운영 전 테스트 질문으로 알림 전송 여부를 확인합니다.
- 일반 대화 메시지 감지는 아직 비활성 상태이며 구현하지 않았습니다.

## 운영 정책 미확정 질문 처리 원칙

운영 정책이 확정되지 않은 질문은 `data/faq.json`이나 `data/knowledge.json`에 바로 추가하지 않고, 운영진 확인 후 반영 여부를 결정합니다. 교통비, 식사, 준비물, 선정 결과, 대기자, 늦은 합류처럼 운영 방식, 일정, 선발 상황에 따라 답이 달라질 수 있는 질문은 정책 확정 전까지 Fallback 또는 운영진 문의 흐름을 유지합니다.

참여자에게는 확정되지 않은 내용을 단정하지 않고, 운영진 확인 후 공지 채널 또는 개별 안내를 기준으로 확인하도록 안내합니다. 복사용 문구는 [operator-response-templates.md](operator-response-templates.md)의 운영 정책 미확정 질문 응대 템플릿을 참고합니다.

정책이 확정된 뒤에만 `data/faq.json` 또는 `data/knowledge.json`에 반영합니다. 반영할 때는 짧은 즉답이 필요한 질문은 FAQ로, 배경 설명이나 운영 원칙을 함께 안내해야 하는 질문은 Knowledge로 구분합니다.

## AI fallback 운영 주의사항

- 기본 운영에서는 AI fallback을 꺼둔 상태로 사용합니다.
- 실제 API Key는 문서나 코드에 적지 않고, Railway Variables 또는 로컬 `.env`에서만 관리합니다.
- 민감한 질문, 위기 표현, 개인정보 관련 질문은 AI가 아니라 운영진 확인을 우선합니다.
- 실제 API 연동 전에는 [api-rag-plan.md](api-rag-plan.md)를 먼저 확인합니다.

## 배포/운영 주의사항

- `.env`는 절대 커밋하지 않습니다.
- `.env.example`에는 실제 토큰이나 실제 채널 ID를 넣지 않고 예시값만 넣습니다.
- Railway Variables에는 실제 `DISCORD_TOKEN`, `CLIENT_ID`, `GUILD_ID`, `LOG_CHANNEL_ID` 값을 넣습니다.
- 관리자 웹 대시보드를 사용할 경우 Railway Public Domain을 만든 뒤 `ADMIN_DASHBOARD_ENABLED=true`, `ADMIN_DASHBOARD_PASSWORD`, `ADMIN_DASHBOARD_TITLE`을 설정합니다.
- 알림 채널은 `LOG_CHANNEL_ID`, `ACTIVITY_REVIEW_CHANNEL_ID`, `POINT_REDEEM_CHANNEL_ID` 3종을 운영 채널 구조에 맞게 확인합니다.
- 미션 인증 채널 반응 승인 알림 정책에 맞게 `REACTION_APPROVAL_PUBLIC_REPLY=false`, `REACTION_APPROVAL_DM_USER=true`를 Railway Variables에 추가합니다.
- 로컬에서 `npm run start`로 봇을 켠 상태에서 Railway 봇도 동시에 켜져 있으면 충돌할 수 있습니다.
- FAQ, 지식창고, 공지 템플릿, 채널 안내 데이터만 수정했다면 `npm run deploy`는 필요하지 않습니다.
- Slash Command 구조를 바꾸면 `npm run deploy`로 명령어를 다시 등록해야 합니다.

## 포인트 운영 관리 MVP v1 루틴

운영자는 먼저 `/운영현황`으로 대기 건과 전체 상태를 확인합니다. 요약에는 교환 대기, 인증 대기, 활성 미션, 활성 상점 항목, 오늘 체크인, 최근 포인트 로그가 표시됩니다.

- 교환 대기는 `/운영현황` 드롭다운의 `교환 대기`에서 신청 ID를 확인한 뒤 `/교환관리`로 지급완료, 취소, 환불완료 처리합니다.
- 인증 대기는 `/운영현황` 드롭다운의 `인증 대기`에서 제출 ID를 확인한 뒤 `/인증관리`로 승인 또는 반려 처리합니다.
- 미션은 `/미션관리 작업:추가`로 생성한 뒤 `/미션관리 작업:활성화 미션id:...`를 실행해야 참여자 `/미션`에 노출됩니다.
- 미션을 잠시 내릴 때는 `/미션관리 작업:일시중지`, 종료할 때는 `/미션관리 작업:종료`를 사용합니다.
- 상점 항목은 `/상점관리 작업:추가`로 생성한 뒤 `/상점관리 작업:활성화 항목id:...`를 실행해야 참여자 `/상점`에 노출됩니다.
- 상점 항목의 `paused`, `soldOut`, `hidden` 상태는 참여자에게 노출되지 않습니다.
- 청년동 포인트 전환권은 청년동 내부 사용처에 한정된 운영진 처리 항목으로 안내하며, 현금 환급이나 외부 교환처럼 보이지 않게 관리합니다.

운영 중에는 신청 ID, 제출 ID, 미션 ID, 항목 ID를 복사해 후속 명령에 입력하므로 ID를 잘못 붙여 넣지 않았는지 확인합니다. 운영자 명령은 Manage Messages 또는 Administrator 권한이 있는 사용자만 실행할 수 있어야 하며, 응답은 가능한 한 ephemeral로 확인합니다.

이번 MVP v1은 local JSON repository 기반입니다. `data/*.local.json`은 실제 운영 데이터 파일이므로 커밋하지 않습니다. Google Sheets와 PostgreSQL 연동은 이번 단계에 포함하지 않고 후속 단계에서 검토합니다.

## 관리자 웹 대시보드 운영 루틴

관리자 웹 대시보드 `/admin`은 읽기 전용 점검 화면입니다. 운영자는 `/운영현황`으로 Discord 내부 상태를 확인하고, 브라우저의 `/admin`에서 요약과 목록을 함께 대조합니다.

- `data/*.example.json`의 문서용 더미 데이터는 smoke test와 fallback 설명에만 사용하며, `/포인트로그`, `/운영현황`, `/admin`에서는 실제 운영 데이터처럼 표시하지 않습니다.
- 실제 운영 전 `/admin`에서 `user_example`, `rd_example`, `submission_example`, `tx_example`, 2030년 샘플 날짜 같은 example 데이터가 보이지 않는지 확인합니다.
- `/admin` 상단에 `읽기 전용 · local-json · example 데이터 제외` 안내가 표시되는지 확인합니다.
- 교환, 인증, 포인트, 미션, 상점의 실제 처리는 계속 `/교환관리`, `/인증관리`, `/포인트관리`, `/미션관리`, `/상점관리`에서 진행합니다.
- 대시보드가 비어 있으면 example 데이터가 제외된 정상 상태일 수 있으므로, 운영용 미션과 상점 항목은 Discord 명령어로 등록합니다.
- 운영 전 데이터 정리는 [production-data-reset-guide.md](production-data-reset-guide.md)를 확인합니다.
- Railway 환경변수와 Public Domain 설정은 [railway-env-guide.md](railway-env-guide.md)를 확인합니다.

## 전체 운영 순서

1. 운영 하루 전 [실제 운영 전 QA 체크리스트](prelaunch-qa-checklist.md)로 환경변수, Discord 권한, Slash Command 등록 상태를 확인합니다.
2. 운영 시작 전 [운영 전 QA 리허설 시나리오](prelaunch-rehearsal-scenario.md)를 기준으로 참여자 흐름과 운영자 처리 흐름을 1회 이상 끝까지 테스트합니다.
3. 운영 시작 전 관리자 웹 대시보드를 사용하는 경우 `/admin` 접속과 Basic Auth 인증이 되는지 확인합니다.
4. 운영 시작 전 `/미션관리`, `/상점관리`로 운영용 기본 미션과 청년동 포인트 전환 항목을 등록합니다.
5. 리허설 데이터와 실제 운영 데이터를 구분하고, 테스트 데이터 정리 여부를 결정한 뒤 운영용 미션/상점만 active 상태로 남깁니다.
6. 운영 시작 전 `/운영현황`의 `오늘의 운영 큐` 또는 `/admin`으로 교환 대기, 인증 대기, 활성 미션, 활성 상점 항목을 확인합니다.
7. 참여자에게 먼저 `/안내`를 안내하고, `/포인트`, `/상점`, `/체크인`, `/미션`, `/질문` 사용 흐름을 짧게 설명합니다. `/인증`은 직접 제출이 필요한 경우의 보조 수단으로만 안내합니다.
8. 운영 중에는 `/운영현황` 또는 `/admin`을 기준으로 대기 건을 확인하고 `/인증관리`, `/교환관리`, `/포인트관리`로 필요한 처리를 합니다.
9. 운영 종료 후 `/운영내보내기 종류:전체 형식:JSON`으로 전체 백업을 남깁니다.
10. 정산이나 공유가 필요한 경우 필요한 종류만 CSV로 내려받아 최소 범위로 공유합니다.

## 실제 운영 하루 전 점검

- `npm run check:release`가 통과하는지 확인합니다.
- Railway Variables에 실제 운영 환경변수가 등록되어 있는지 확인합니다.
- 운영자 계정이 `ManageMessages` 또는 `Administrator` 권한으로 운영자 명령어를 볼 수 있는지 확인합니다.
- 일반 참여자 테스트 계정이 운영자 전용 채널과 운영자 명령어에 접근할 수 없는지 확인합니다.
- `data/*.local.json` 운영 데이터 저장 위치와 백업 방식을 확인합니다.
- 문서만 수정한 경우 `npm run deploy`를 실행하지 않습니다. Slash Command 구조 변경이 있을 때만 deploy 필요 여부를 판단합니다.

## 운영 중 확인할 명령어

- `/운영현황`의 `오늘의 운영 큐`: 운영 중 전체 대기 상태를 빠르게 확인합니다.

3. 신청 전 안내 문구와 실제 항목 설명이 서로 어긋나지 않는지 확인합니다.
4. 청년동 포인트 또는 리워드를 실제로 지급합니다.
5. 실제 지급이 끝난 뒤 `/교환관리 처리:지급완료`를 실행합니다.
6. 지급 불가, 중복 신청, 시스템 오류 등 예외 상황이면 `/교환관리 처리:취소` 또는 `처리:환불완료`로 기록하고 메모를 남깁니다.
7. `/포인트로그`에서 교환 차감과 환불 거래가 의도대로 남았는지 확인합니다.

## 인증 제출 처리 루틴

1. `/운영현황`의 `인증 대기`에서 제출 ID와 미션 ID를 확인합니다.
2. 미션 기준, 기간, 중복 승인 여부를 확인합니다.
3. 기준을 충족하면 `/인증관리 처리:승인`을 실행합니다.
4. 보완이 필요하거나 기준에 맞지 않으면 `/인증관리 처리:반려`를 실행하고 필요한 확인 사항만 메모합니다.
5. 승인 후 `/포인트로그`에서 포인트 지급 거래가 남았는지 확인합니다.

## 데이터 내보내기 루틴

- 운영 시작 전: 전체 JSON 백업을 남깁니다.
- 운영 중 큰 정정 전: 현재 상태를 JSON으로 저장합니다.
- 운영 종료 후: 전체 JSON과 필요한 CSV를 저장합니다.
- 외부 공유 전: 사용자 ID, 표시 이름, 인증 내용, 운영 메모가 포함됐는지 확인하고 필요한 범위만 공유합니다.

## 장애 또는 오류 발생 시 확인 순서

1. Railway 서비스가 Online인지 확인합니다.
2. Railway Deploy Logs에서 로그인 오류, 권한 오류, JSON 읽기/쓰기 오류를 확인합니다.
3. Discord에서 봇 권한과 채널 접근 권한을 확인합니다.
4. local JSON 저장 위치와 파일 쓰기 권한을 확인합니다.
5. `npm run validate:data`와 `npm run check:release`로 로컬 검증을 실행합니다.
6. 포인트나 교환 데이터 오류는 기존 기록을 삭제하지 않고 정정 거래와 운영 메모로 복구합니다.

## 운영 데이터 내보내기 및 백업

운영자는 `/운영내보내기`로 포인트, 교환, 인증, 미션, 상점 데이터를 종류별로 확인하거나 백업할 수 있습니다. 응답은 운영자에게만 보이는 ephemeral 응답이며, JSON 또는 CSV 형식은 파일 첨부로 받는 것을 기본으로 합니다.

내보낸 파일에는 사용자 ID, 표시 이름, 인증 내용, 포인트 거래, 운영 메모가 포함될 수 있으므로 공개 채널이나 외부 공간에 공유하지 않습니다. 백업 파일은 안전한 내부 저장소에 보관하고, 공유가 필요할 때는 필요한 종류와 기간만 최소 범위로 전달합니다.

`OPERATION_BACKUP_REMINDER_ENABLED=true`로 설정하면 지정된 KST 시각에 운영 로그 채널로 “운영 종료 전 `/운영내보내기` 확인” 알림만 보냅니다. 자동 백업 파일은 생성하지 않습니다.

자세한 백업 루틴과 보관 주의사항은 [운영 데이터 내보내기 및 백업 가이드](export-and-backup-guide.md)를 확인합니다.

## 신규 입장자 환영 자동화

환영 자동화는 기본 비활성화입니다. 다음 순서로만 켭니다.

1. Discord Developer Portal의 Bot 설정에서 **Server Members Intent**를 활성화합니다.
2. Railway Variables에 `WELCOME_CONSENT_CHANNEL_ID`를 설정하고, 필요하면 `WELCOME_NAMETAG_CHANNEL_ID`, `WELCOME_FALLBACK_CHANNEL_ID`, `WELCOME_REMINDER_HOURS`, `WELCOME_REMINDER_QUIET`를 설정합니다.
3. `WELCOME_ONBOARDING_ENABLED=true`로 바꾸고 Railway 서비스를 재배포합니다.

기능을 중단할 때는 `WELCOME_ONBOARDING_ENABLED=false`로 바꾸고 재배포합니다. 별도 Slash Command 변경이 없으므로 `npm run deploy`는 실행하지 않습니다. 환영 DM·폴백·1회 리마인드 기록은 공통 운영 데이터 경로의 `welcome-onboarding.local.json`에 저장되며, 기본 위치는 `data/welcome-onboarding.local.json`입니다.

## 운영 지연 리마인더

운영 리마인더는 기본 비활성이며 교환·인증·반응 후속 확인의 지연과 active 미션 마감을 운영진 전용 채널에 집계로 안내합니다. 참여자에게 메시지를 보내거나 상태를 자동 변경하지 않습니다. 단일 Railway replica에서 `OPS_REMINDER_ENABLED=true`와 전용 채널·KST 슬롯을 설정한 뒤 사용하며, 중단 시에는 다시 `false`로 바꾸고 재배포합니다. 이력은 공통 운영 데이터 경로의 `ops-reminders.local.json`에 저장되고 자동 백업에 포함됩니다.
