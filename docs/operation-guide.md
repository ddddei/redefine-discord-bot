# 운영 가이드

리디파인 디스코드 안내 봇을 혼자 운영할 때 참고하는 운영 문서입니다.

## 참여자 입장 전 최종 점검 체크리스트

- Railway에서 봇 상태가 Online인지 확인합니다.
- 로컬에서 봇이 실행 중이 아닌지 확인합니다.
- 디스코드에서 `/안내`를 실행해 응답을 확인합니다.
- 디스코드에서 `/채널안내`를 실행해 채널 안내가 정상 표시되는지 확인합니다.
- 디스코드에서 `/질문`을 실행해 FAQ 응답이 정상 표시되는지 확인합니다.
- 디스코드에서 `/공지 종류:봇사용안내`를 실행해 공지 템플릿이 정상 표시되는지 확인합니다.
- `#봇-질문로그`에 미응답 질문 로그가 기록되는지 확인합니다.
- 운영진 전용 채널을 참여자가 볼 수 없는지 권한을 확인합니다.
- 봇 사용 안내 공지를 참여자가 보기 쉬운 채널에 고정합니다.

## 참여자에게 안내할 기본 명령어

- `/안내`
- `/채널안내`
- `/질문 내용:궁금한 내용`
- `/체크인 내용:오늘의 한마디`
- `/미션`
- `/인증 미션id:M001 내용:수행 내용 첨부파일:사진이나 영상`

### `/안내` 역할별 표시

`/안내`는 온보딩 역할이 감지되면 역할에 맞는 안내 문구 일부를 추가로 표시할 수 있습니다. 역할이 없거나 감지되지 않으면 공통 안내만 표시됩니다.

이 표시는 편의를 위한 안내 기능이며 실제 Discord 권한을 대신하지 않습니다. 실제 역할 부여와 채널 접근 권한은 운영자가 Discord에서 별도로 확인해야 합니다.

### `/채널안내` 역할별 보조 문구

`/채널안내`는 온보딩 역할이 감지되면 역할에 따라 짧은 보조 안내 문구를 다르게 보여줄 수 있습니다. 현재 v1은 채널 목록을 필터링하는 단계가 아니라 안내 문구를 보강하는 단계입니다.

이 문구는 실제 채널 권한이나 노출 범위를 대신하지 않습니다. 실제 역할 부여와 채널 접근 권한은 운영자가 Discord에서 별도로 확인해야 합니다.

- `/공지 종류:봇사용안내`
- `/공지 종류:일정안내`
- `/공지 종류:참여리마인드`

## 참여 활동 포인트 운영

`/체크인`은 참여자가 하루 1회 가볍게 참여 기록을 남기고 기본 10P를 받는 명령어입니다. 날짜 기준은 한국 시간입니다. 체크인은 출석 압박이나 경쟁 장치가 아니며, 지급 기준과 포인트 수량은 운영진 안내를 우선합니다.

`/미션`은 현재 `active` 상태인 선택형 미션만 짧게 보여줍니다. 본문은 미션명, 지급 포인트, 인증 방식 중심으로 구성하고 `M001` 같은 미션 코드는 선택 메뉴와 직접 입력 안내에서만 보조로 사용합니다. 선택 메뉴를 사용하면 글 인증 모달이 열리고, 사진이나 영상 인증은 `/인증`의 `첨부파일` 옵션으로 받습니다. 미션은 가능한 범위에서 선택하는 활동으로 안내하고, 모든 참여자가 반드시 수행해야 하는 과제처럼 표현하지 않습니다.

`/인증`은 제출을 `pending`으로 저장할 뿐 포인트를 즉시 지급하지 않습니다. 글로 남길 수 있는 미션은 `/미션`에서 선택해 제출하고, 사진이나 영상이 필요한 경우 `/인증`에서 첨부파일을 함께 올리도록 안내합니다. 선택 첨부파일이 있으면 파일명, URL, content type, 크기를 제출 기록에 함께 저장합니다. 제출이 접수되면 `ACTIVITY_REVIEW_CHANNEL_ID` 또는 `LOG_CHANNEL_ID`로 운영자 검토 알림이 전송됩니다. 채널 ID가 없어도 봇은 중단되지 않고 콘솔 경고만 남깁니다.

운영자는 `/인증관리`로 제출을 승인 또는 반려합니다. 승인 시 미션의 `rewardPoints`만큼 여정 포인트가 지급되고 `pointTransactions`에 `earn` 거래가 남습니다. 반려 시 포인트를 지급하지 않으며, 메모에는 참여자를 평가하거나 낙인찍는 표현 대신 필요한 확인 사항만 남깁니다.

인증 내용과 첨부파일에는 과도한 개인정보나 민감한 사적 정보가 담기지 않도록 안내합니다. 첨부파일 URL은 운영자 확인용으로만 사용하고 외부 공유 전 포함 여부를 확인합니다. 필요한 최소 내용만 받고, 세부 지급 기준은 운영진이 공지한 안내를 우선합니다.

## 미응답 질문 로그 운영 방법

`/질문` 명령어가 FAQ에서 답변을 찾지 못하면 `LOG_CHANNEL_ID`가 설정된 경우 `#봇-질문로그`에 질문 내용과 시간이 기록됩니다.

운영 중에는 `#봇-질문로그`를 주기적으로 확인하고, 반복해서 들어오는 질문을 `data/faq.json`에 FAQ로 추가합니다. FAQ로 쓰기에는 넓은 프로그램 설명이나 배경 안내에 가까운 질문은 `data/knowledge.json`에 지식창고 항목으로 추가합니다. 반영한 뒤에는 같은 질문을 `/질문`으로 다시 테스트해 봇이 새 답변을 찾는지 확인합니다.

미응답 질문 로그에는 사용자 이름이나 사용자 ID를 기록하지 않습니다. 운영자는 질문 내용만 보고 FAQ 개선에 활용합니다.

## 민감 질문 알림 운영 주의사항

`/질문`에 민감 표현이 포함되면 FAQ/지식창고 답변보다 운영진 확인 안내가 먼저 표시되고, `SAFETY_ALERT_CHANNEL_ID` 또는 `LOG_CHANNEL_ID`로 운영진 알림이 전송됩니다.

- 민감 질문 알림 채널은 운영진 전용 채널이어야 하며 참여자가 볼 수 없는지 권한을 확인합니다.
- 알림은 키워드 기반 신호이며 자동 판단이 아니므로 운영진 확인이 필요합니다.
- 실제 운영 전 테스트 질문으로 알림 전송 여부를 확인합니다.
- 일반 대화 메시지 감지는 아직 비활성 상태이며 구현하지 않았습니다.

## 운영 정책 미확정 질문 처리 원칙

운영 정책이 확정되지 않은 질문은 `data/faq.json`이나 `data/knowledge.json`에 바로 추가하지 않고, 운영진 확인 후 반영 여부를 결정합니다. 교통비, 식사, 준비물, 선정 결과, 대기자, 늦은 합류처럼 운영 방식, 일정, 선발 상황에 따라 답이 달라질 수 있는 질문은 정책 확정 전까지 Fallback 또는 운영진 문의 흐름을 유지합니다.

참여자에게는 확정되지 않은 내용을 단정하지 않고, 운영진 확인 후 공지 채널 또는 개별 안내를 기준으로 확인하도록 안내합니다. 복사용 문구는 [operator-response-templates.md](operator-response-templates.md)의 운영 정책 미확정 질문 응대 템플릿을 참고합니다.

정책이 확정된 뒤에만 `data/faq.json` 또는 `data/knowledge.json`에 반영합니다. 반영할 때는 짧은 즉답이 필요한 질문은 FAQ로, 배경 설명이나 운영 원칙을 함께 안내해야 하는 질문은 Knowledge로 구분합니다.

## AI fallback 운영 주의사항

- 기본 운영에서는 AI fallback을 꺼둔 상태로 사용합니다.
- 실제 API Key는 문서나 코드에 적지 않고, Railway Variables 또는 로컬 `.env`에서만 관리합니다.
- 민감한 질문, 위기 표현, 개인정보 관련 질문은 AI가 아니라 운영진 확인을 우선합니다.
- 실제 API 연동 전에는 [api-rag-plan.md](api-rag-plan.md)를 먼저 확인합니다.

## FAQ 수정 루틴

1. `data/faq.json`을 수정합니다.
2. 데이터 구조와 JSON 문법을 확인합니다.

```bash
npm run validate:data
```

3. 로컬에서 FAQ/지식창고 질문 매칭 결과를 확인합니다.

```bash
npm run test:questions
```

4. Fallback 질문은 이후 FAQ 또는 지식창고 보강 재료로 모아 둡니다.
5. 디스코드에서 `/질문 내용:수정한 질문 예시`를 실행해 답변을 테스트합니다.
6. 변경 내용을 확인합니다.

```bash
git status
git diff
```

7. 문제가 없으면 커밋하고 푸시합니다.

```bash
git add .
git commit -m "FAQ 업데이트"
git push
```

8. Railway에서 자동 재배포가 완료되고 봇이 Online 상태인지 확인합니다.

## 지식창고 수정 루틴

1. `data/knowledge.json`을 수정합니다.
2. 각 항목에 `id`, `title`, `keywords`, `summary`, `content`가 있는지 확인합니다.
3. 운영진 확인이 필요한 내용, 일정, 참여 확정 여부, 정신건강·위기 판단은 단정하지 않고 문의 채널이나 운영진 안내로 연결되도록 작성합니다.
4. 데이터 구조와 JSON 문법을 확인합니다.

```bash
npm run validate:data
```

5. 로컬에서 FAQ/지식창고 질문 매칭 결과를 확인합니다.

```bash
npm run test:questions
```

6. 디스코드에서 `/질문 내용:수정한 지식창고 질문 예시`를 실행해 답변을 테스트합니다.
7. FAQ 답변이 먼저 검색되고, FAQ에 없을 때 지식창고 답변이 표시되는지 확인합니다.

## 공지 템플릿 수정 루틴

1. `data/notices.json`을 수정합니다.
2. 데이터 구조와 JSON 문법을 확인합니다.

```bash
npm run validate:data
```

3. 디스코드에서 수정한 종류의 `/공지`를 실행합니다.
4. 공지 문구, 줄바꿈, 링크, 안내 대상이 의도대로 표시되는지 확인합니다.

## 채널 안내 수정 루틴

1. `data/channels.json`을 수정합니다.
2. 데이터 구조와 JSON 문법을 확인합니다.

```bash
npm run validate:data
```

3. 디스코드에서 `/채널안내`를 실행합니다.
4. 채널 이름, 설명, 분류가 실제 디스코드 서버 구조와 맞는지 확인합니다.

## 커밋 전 자동 검증 확인

커밋 전에는 로컬에서 기본 검증을 먼저 실행합니다.

```bash
node --check src/index.js
node --check src/deploy-commands.js
npm run validate:data
npm run test:questions
```

push 또는 pull request를 올린 뒤에는 GitHub의 Actions 탭이나 PR 하단 checks 영역에서 `CI` 결과가 성공인지 확인합니다. 실패한 경우 실패한 단계의 로그를 보고 수정한 뒤 다시 push합니다.

## 배포/운영 주의사항

- `.env`는 절대 커밋하지 않습니다.
- `.env.example`에는 실제 토큰이나 실제 채널 ID를 넣지 않고 예시값만 넣습니다.
- Railway Variables에는 실제 `DISCORD_TOKEN`, `CLIENT_ID`, `GUILD_ID`, `LOG_CHANNEL_ID` 값을 넣습니다.
- 로컬에서 `npm run start`로 봇을 켠 상태에서 Railway 봇도 동시에 켜져 있으면 충돌할 수 있습니다.
- FAQ, 지식창고, 공지 템플릿, 채널 안내 데이터만 수정했다면 `npm run deploy`는 필요하지 않습니다.
- Slash Command 구조를 바꾸면 `npm run deploy`로 명령어를 다시 등록해야 합니다.

## 포인트 운영 관리 MVP v1 루틴

운영자는 먼저 `/운영현황`으로 대기 건과 전체 상태를 확인합니다. 요약에는 교환 대기, 인증 대기, 활성 미션, 활성 상점 항목, 오늘 체크인, 최근 포인트 로그가 표시됩니다.

- 교환 대기는 `/운영현황 종류:교환대기`에서 신청 ID를 확인한 뒤 `/교환관리`로 지급완료, 취소, 환불완료 처리합니다.
- 인증 대기는 `/운영현황 종류:인증대기`에서 제출 ID를 확인한 뒤 `/인증관리`로 승인 또는 반려 처리합니다.
- 미션은 `/미션관리 작업:추가`로 생성한 뒤 `/미션관리 작업:활성화 미션id:...`를 실행해야 참여자 `/미션`에 노출됩니다.
- 미션을 잠시 내릴 때는 `/미션관리 작업:일시중지`, 종료할 때는 `/미션관리 작업:종료`를 사용합니다.
- 상점 항목은 `/상점관리 작업:추가`로 생성한 뒤 `/상점관리 작업:활성화 항목id:...`를 실행해야 참여자 `/상점`에 노출됩니다.
- 상점 항목의 `paused`, `soldOut`, `hidden` 상태는 참여자에게 노출되지 않습니다.
- 청년동 포인트 전환권은 청년동 내부 사용처에 한정된 운영진 처리 항목으로 안내하며, 현금 환급이나 외부 교환처럼 보이지 않게 관리합니다.

운영 중에는 신청 ID, 제출 ID, 미션 ID, 항목 ID를 복사해 후속 명령에 입력하므로 ID를 잘못 붙여 넣지 않았는지 확인합니다. 운영자 명령은 Manage Messages 또는 Administrator 권한이 있는 사용자만 실행할 수 있어야 하며, 응답은 가능한 한 ephemeral로 확인합니다.

이번 MVP v1은 local JSON repository 기반입니다. `data/*.local.json`은 실제 운영 데이터 파일이므로 커밋하지 않습니다. Google Sheets, PostgreSQL, 웹 대시보드는 이번 단계에 포함하지 않고 후속 단계에서 검토합니다.

## 전체 운영 순서

1. 운영 하루 전 [실제 운영 전 QA 체크리스트](prelaunch-qa-checklist.md)로 환경변수, Discord 권한, Slash Command 등록 상태를 확인합니다.
2. 운영 시작 전 `/운영현황 종류:요약`으로 교환 대기, 인증 대기, 활성 미션, 활성 상점 항목을 확인합니다.
3. 참여자에게 `/안내`, `/채널안내`, `/질문`, `/포인트`, `/상점`, `/체크인`, `/미션`, `/인증` 사용 흐름을 안내합니다.
4. 운영 중에는 `/운영현황`을 기준으로 대기 건을 확인하고 `/인증관리`, `/교환관리`, `/포인트관리`로 필요한 처리를 합니다.
5. 운영 종료 후 `/운영내보내기 종류:전체 형식:JSON`으로 전체 백업을 남깁니다.
6. 정산이나 공유가 필요한 경우 필요한 종류만 CSV로 내려받아 최소 범위로 공유합니다.

## 실제 운영 하루 전 점검

- `npm run check:release`가 통과하는지 확인합니다.
- Railway Variables에 실제 운영 환경변수가 등록되어 있는지 확인합니다.
- 운영자 계정이 `ManageMessages` 또는 `Administrator` 권한으로 운영자 명령어를 볼 수 있는지 확인합니다.
- 일반 참여자 테스트 계정이 운영자 전용 채널과 운영자 명령어에 접근할 수 없는지 확인합니다.
- `data/*.local.json` 운영 데이터 저장 위치와 백업 방식을 확인합니다.
- 문서만 수정한 경우 `npm run deploy`를 실행하지 않습니다. Slash Command 구조 변경이 있을 때만 deploy 필요 여부를 판단합니다.

## 운영 중 확인할 명령어

- `/운영현황 종류:요약`: 운영 중 전체 대기 상태를 빠르게 확인합니다.
- `/운영현황 종류:교환대기`: 실제 지급이 필요한 교환 신청 ID를 확인합니다.
- `/운영현황 종류:인증대기`: 검토가 필요한 인증 제출 ID를 확인합니다.
- `/포인트로그`: 지급, 차감, 교환, 환불, 정정 로그를 확인합니다.
- `/운영내보내기 종류:요약`: 백업 전 전체 건수와 대기 건수를 확인합니다.

## 교환 신청 처리 루틴

1. `/운영현황 종류:교환대기`에서 신청 ID와 항목을 확인합니다.
2. 신청 항목, 비용, 참여자, 재고, 지급 가능 여부를 확인합니다.
3. 청년동 포인트 또는 리워드를 실제로 지급합니다.
4. 실제 지급이 끝난 뒤 `/교환관리 처리:지급완료`를 실행합니다.
5. 지급 불가, 중복 신청, 시스템 오류 등 예외 상황이면 `/교환관리 처리:취소` 또는 `처리:환불완료`로 기록하고 메모를 남깁니다.
6. `/포인트로그`에서 교환 차감과 환불 거래가 의도대로 남았는지 확인합니다.

## 인증 제출 처리 루틴

1. `/운영현황 종류:인증대기`에서 제출 ID와 미션 ID를 확인합니다.
2. 미션 기준, 기간, 중복 승인 여부를 확인합니다.
3. 기준을 충족하면 `/인증관리 처리:승인`을 실행합니다.
4. 보완이 필요하거나 기준에 맞지 않으면 `/인증관리 처리:반려`를 실행하고 필요한 확인 사항만 메모합니다.
5. 승인 후 `/포인트로그`에서 포인트 지급 거래가 남았는지 확인합니다.

## 데이터 내보내기 루틴

- 운영 시작 전: 전체 JSON 백업을 남깁니다.
- 운영 중 큰 정정 전: 현재 상태를 JSON으로 저장합니다.
- 운영 종료 후: 전체 JSON과 필요한 CSV를 저장합니다.
- 외부 공유 전: 사용자 ID, 표시 이름, 인증 내용, 운영 메모가 포함됐는지 확인하고 필요한 범위만 공유합니다.

## 장애 또는 오류 발생 시 확인 순서

1. Railway 서비스가 Online인지 확인합니다.
2. Railway Deploy Logs에서 로그인 오류, 권한 오류, JSON 읽기/쓰기 오류를 확인합니다.
3. Discord에서 봇 권한과 채널 접근 권한을 확인합니다.
4. local JSON 저장 위치와 파일 쓰기 권한을 확인합니다.
5. `npm run validate:data`와 `npm run check:release`로 로컬 검증을 실행합니다.
6. 포인트나 교환 데이터 오류는 기존 기록을 삭제하지 않고 정정 거래와 운영 메모로 복구합니다.

## 운영 데이터 내보내기 및 백업

운영자는 `/운영내보내기`로 포인트, 교환, 인증, 미션, 상점 데이터를 종류별로 확인하거나 백업할 수 있습니다. 응답은 운영자에게만 보이는 ephemeral 응답이며, JSON 또는 CSV 형식은 파일 첨부로 받는 것을 기본으로 합니다.

내보낸 파일에는 사용자 ID, 표시 이름, 인증 내용, 포인트 거래, 운영 메모가 포함될 수 있으므로 공개 채널이나 외부 공간에 공유하지 않습니다. 백업 파일은 안전한 내부 저장소에 보관하고, 공유가 필요할 때는 필요한 종류와 기간만 최소 범위로 전달합니다.

자세한 백업 루틴과 보관 주의사항은 [운영 데이터 내보내기 및 백업 가이드](export-and-backup-guide.md)를 확인합니다.
