# 관리자 웹 대시보드 MVP 설계 문서

## 1. 문서 목적

이 문서는 프로젝트 리디파인 디스코드 봇의 운영 효율을 높이기 위한 **관리자 웹 대시보드 MVP** 설계 문서이다.

현재 봇은 디스코드 안에서 참여자 안내, 포인트 확인, 상점/교환, 미션 확인, 미션 인증, 운영 현황 조회 등을 지원하고 있다. 참여자용 `/안내` 허브와 운영자용 `/운영현황` 허브를 통해 기본적인 흐름은 정리되었지만, 운영자 입장에서 전체 상태를 한눈에 파악하기에는 Discord 채팅형 UI의 한계가 있다.

따라서 본 문서는 향후 구현할 관리자 웹 대시보드의 목표, 범위, 화면 구성, 데이터 구조, 보안 방식, 단계별 확장 방향을 정리하는 것을 목적으로 한다.

---

## 2. 현재 구조 요약

### 2.1 참여자용 기능

현재 참여자는 주로 아래 흐름으로 봇을 사용한다.

* `/안내`로 전체 사용법 확인
* `/체크인`으로 오늘 상태 기록
* `/미션`으로 참여 가능한 미션 확인
* 미션 인증 채널에 글/사진/영상 업로드
* 운영자가 ✅ 반응으로 확인하면 여정 포인트 지급
* `/포인트`로 보유 포인트 확인
* `/상점` 또는 `/교환`으로 교환 가능한 항목 확인
* `/질문` 또는 운영진 문의 채널로 문의

### 2.2 운영자용 기능

현재 운영자는 Discord 명령어를 통해 아래 기능을 사용할 수 있다.

* `/운영현황` : 전체 운영 요약 확인
* `/포인트관리` : 포인트 수동 지급/차감
* `/교환관리` : 교환 신청 확인 및 처리
* `/인증관리` : `/인증` 명령어 기반 제출 확인 및 처리
* `/포인트로그` : 포인트 지급/사용 로그 확인
* `/미션관리` : 미션 추가/상태 변경
* `/상점관리` : 상점 항목 추가/상태 변경
* `/운영내보내기` : 운영 데이터 CSV/JSON 내보내기

### 2.3 현재 한계

Discord 안에서 운영자 기능을 제공하는 것은 빠른 확인에는 유용하지만, 다음과 같은 한계가 있다.

* 여러 정보를 한 화면에 배치하기 어렵다.
* 표, 카드, 상태 배지, 필터, 검색 UI 구현이 제한적이다.
* 대기 건, 최근 로그, 미션/상점 상태를 한눈에 보기 어렵다.
* 운영자가 매번 명령어와 드롭다운을 반복해서 확인해야 한다.
* 실제 운영 중에는 “처리해야 할 항목”과 “참고용 로그”가 섞여 보일 수 있다.
* 장기 운영 시 데이터 백업과 정산 흐름이 더 명확하게 필요하다.

## 3. 관리자 웹 대시보드의 목표

관리자 웹 대시보드의 목표는 Discord 봇을 대체하는 것이 아니라, **운영자가 전체 상태를 한눈에 보고 판단할 수 있는 보조 화면**을 제공하는 것이다.

### 3.1 핵심 목표

* 운영 현황을 한 화면에서 요약한다.
* 교환 대기, 인증 대기, 최근 포인트 로그를 빠르게 확인한다.
* 미션과 상점의 활성 상태를 확인한다.
* 반응 승인 기록과 포인트 지급 기록을 구분해 확인한다.
* 운영 데이터 내보내기와 백업 필요성을 안내한다.
* 향후 승인/반려/수정 등 운영 액션을 웹에서 처리할 수 있도록 확장 가능한 구조를 마련한다.

### 3.2 운영 원칙

* 참여자 경험은 Discord 안에서 유지한다.
* 운영자 확인과 관리 편의성은 웹 대시보드로 보완한다.
* 초기 MVP는 읽기 전용으로 시작한다.
* 포인트 지급, 교환 승인, 미션 수정 같은 쓰기 기능은 후속 단계에서 검토한다.
* 현재 JSON 기반 저장소의 한계를 고려해, 장기적으로 Google Sheets 또는 DB 연동을 검토한다.

## 4. MVP 범위

### 4.1 이번 MVP에 포함할 것

관리자 웹 대시보드 MVP는 우선 **읽기 전용 대시보드**로 구현한다.

포함 범위:

* 관리자 로그인 또는 간단한 비밀번호 보호
* 운영 요약 카드
* 교환 대기 목록
* 인증 대기 목록
* 최근 포인트 로그
* 미션 상태 요약
* 상점 상태 요약
* 반응 승인 기록
* 운영 데이터 내보내기 안내
* 운영 체크리스트

### 4.2 이번 MVP에 포함하지 않을 것

초기 MVP에서는 아래 기능을 구현하지 않는다.

* 웹에서 교환 승인/거절/완료 처리
* 웹에서 인증 승인/반려 처리
* 웹에서 포인트 수동 지급/차감
* 웹에서 미션 생성/수정/삭제
* 웹에서 상점 항목 생성/수정/삭제
* 참여자용 공개 페이지
* 일반 랜딩페이지
* 모바일 앱
* Google Sheets 실시간 연동
* PostgreSQL 전환
* 사용자별 상세 통계 대시보드
* 관리자 계정별 권한 관리

## 5. 화면 구성 설계

### 5.1 관리자 홈 화면

관리자 홈 화면은 운영자가 가장 먼저 보는 화면이다.

표시 항목:

* 전체 사용자 수
* 총 포인트 거래 수
* 오늘 포인트 거래 수
* 오늘 지급 포인트 합계
* 교환 대기 수
* 인증 대기 수
* 활성 미션 수
* 활성 상점 항목 수
* 오늘 반응 승인 수
* 최근 백업/내보내기 안내

화면 예시:

```txt
[운영 요약]

사용자 12명
오늘 포인트 거래 8건
오늘 지급 포인트 240P
교환 대기 2건
인증 대기 1건
활성 미션 3개
활성 상점 항목 4개
오늘 반응 승인 5건
```

### 5.2 처리 필요 영역

운영자가 가장 먼저 확인해야 할 항목을 별도 영역으로 보여준다.

구성:

* 교환 대기
* 인증 대기
* 최근 반응 승인
* 이상 로그 또는 주의 항목

초기 MVP에서는 상세 처리 버튼 없이 목록만 보여준다.

### 5.3 교환 대기 목록

표시 항목:

* 신청 시각
* 신청자
* 교환 항목명
* 필요 포인트
* 현재 상태
* 신청 ID
* 처리 안내

초기 MVP 처리 안내:

```txt
처리는 Discord에서 /교환관리 명령어를 사용해 주세요.
```

### 5.4 인증 대기 목록

표시 항목:

* 제출 시각
* 제출자
* 미션명
* 지급 예정 포인트
* 첨부파일 여부
* 상태
* 제출 ID

주의:

* `/인증` 명령어로 제출된 pending 항목 중심으로 표시한다.
* 미션 인증 채널에서 ✅ 반응으로 처리된 항목은 반응 승인 기록에서 확인한다.

### 5.5 최근 포인트 로그

표시 항목:

* 거래 시각
* 사용자
* 타입
* 포인트 변화량
* 잔액
* 사유
* 출처

타입 예시:

* earn
* spend
* refund
* manual
* mission_reaction_approval

### 5.6 미션 상태

표시 항목:

* 전체 미션 수
* active 미션 수
* draft 미션 수
* paused 미션 수
* 최근 등록 미션
* 포인트 지급 기준

초기 MVP에서는 수정 기능을 제공하지 않는다.

처리 안내:

```txt
미션 생성과 상태 변경은 Discord에서 /미션관리 명령어를 사용해 주세요.
```

### 5.7 상점 상태

표시 항목:

* 전체 상점 항목 수
* active 항목 수
* paused 항목 수
* hidden 항목 수
* 재고 제한 항목
* 최근 등록 항목

처리 안내:

```txt
상점 항목 생성과 상태 변경은 Discord에서 /상점관리 명령어를 사용해 주세요.
```

### 5.8 반응 승인 기록

표시 항목:

* 처리 시각
* 참여자
* 처리자
* 상태
* 지급 포인트
* 원본 메시지 링크
* DM 알림 여부
* 공개 답글 여부

상태 예시:

* approved
* rejected

### 5.9 운영 데이터 내보내기 안내

초기 MVP에서는 웹에서 직접 파일을 다운로드하기보다, 현재 Discord 명령어 사용법을 안내한다.

안내 예시:

```txt
운영 데이터 백업은 Discord에서 /운영내보내기 명령어를 사용해 주세요.

예시:
- /운영내보내기 종류:포인트 형식:CSV
- /운영내보내기 종류:교환 형식:JSON
- /운영내보내기 종류:인증 형식:JSON
- /운영내보내기 종류:전체 형식:JSON
```

## 6. 데이터 구조

### 6.1 현재 저장 방식

현재 프로젝트는 MVP 단계에서 local JSON 파일 기반으로 운영 데이터를 저장한다.

예상 데이터:

* users
* pointTransactions
* redemptions
* missions
* submissions
* shopItems
* reactionApprovals

### 6.2 현재 방식의 장점

* 구현이 빠르다.
* 외부 DB 없이 Railway에서 바로 실행 가능하다.
* 초기 테스트와 소규모 운영에 적합하다.
* 데이터 구조를 빠르게 바꾸기 쉽다.

### 6.3 현재 방식의 한계

* 장기 운영 시 데이터 안정성이 낮을 수 있다.
* Railway 배포/재시작/파일 시스템 정책에 따라 데이터 유지가 불안정할 수 있다.
* 여러 인스턴스가 동시에 실행될 경우 동기화 문제가 생길 수 있다.
* 웹 대시보드에서 쓰기 기능을 추가할수록 충돌 관리가 필요하다.
* 정산과 백업을 수동으로 관리해야 한다.

### 6.4 향후 저장소 확장 방향

장기적으로 아래 중 하나를 검토한다.

#### A. Google Sheets 연동

장점:

* 운영자가 익숙하게 확인 가능
* 정산과 공유가 쉬움
* 별도 관리자 페이지 없이도 데이터 확인 가능

한계:

* API 인증과 권한 관리 필요
* 실시간 처리에는 적합하지 않을 수 있음
* 데이터 구조가 복잡해지면 관리가 어려워질 수 있음

#### B. PostgreSQL 연동

장점:

* 장기 운영에 안정적
* 관계형 데이터 관리에 적합
* 관리자 웹 대시보드와 잘 맞음
* 필터/검색/통계 확장 가능

한계:

* 초기 설계와 마이그레이션 비용 발생
* DB 관리 필요
* 운영자가 직접 데이터를 보기에는 Sheets보다 어렵다

#### C. SQLite + Persistent Volume

장점:

* 구현 난이도가 비교적 낮음
* local JSON보다 안정적
* MVP에서 DB 구조로 넘어가는 중간 단계로 활용 가능

한계:

* 배포 환경의 persistent volume 설정 필요
* 장기 확장성은 PostgreSQL보다 낮음

## 7. API 설계 초안

초기 웹 대시보드는 읽기 전용 API만 제공한다.

### 7.1 인증

```txt
GET /admin
```

관리자 페이지 진입.

보호 방식:

* ADMIN_DASHBOARD_ENABLED=true일 때만 활성화
* ADMIN_DASHBOARD_PASSWORD 환경변수로 접근 보호
* 초기 MVP에서는 단일 비밀번호 방식 사용

### 7.2 운영 요약 API

```txt
GET /api/admin/summary
```

반환 데이터 예시:

```json
{
  "usersCount": 12,
  "pointTransactionsCount": 120,
  "todayPointTransactionsCount": 8,
  "todayEarnedPoints": 240,
  "pendingRedemptionsCount": 2,
  "pendingSubmissionsCount": 1,
  "activeMissionsCount": 3,
  "activeShopItemsCount": 4,
  "todayReactionApprovalsCount": 5
}
```

### 7.3 교환 대기 API

```txt
GET /api/admin/redemptions?status=pending
```

### 7.4 인증 대기 API

```txt
GET /api/admin/submissions?status=pending
```

### 7.5 포인트 로그 API

```txt
GET /api/admin/point-transactions?limit=20
```

### 7.6 미션 상태 API

```txt
GET /api/admin/missions
```

### 7.7 상점 상태 API

```txt
GET /api/admin/shop-items
```

### 7.8 반응 승인 기록 API

```txt
GET /api/admin/reaction-approvals?limit=20
```

## 8. 보안 설계

### 8.1 초기 MVP 보안 방식

초기 MVP는 단일 관리자 비밀번호 방식으로 보호한다.

환경변수:

```env
ADMIN_DASHBOARD_ENABLED=false
ADMIN_DASHBOARD_PASSWORD=
```

정책:

* 기본값은 비활성화
* 비밀번호가 없으면 관리자 페이지 비활성화
* 운영자만 URL을 알고 접근
* 민감한 개인정보는 화면에 과도하게 표시하지 않음

### 8.2 주의사항

* 관리자 페이지 URL을 참여자에게 공개하지 않는다.
* 관리자 비밀번호를 GitHub에 커밋하지 않는다.
* `.env.example`에는 placeholder만 작성한다.
* 실제 개인정보, 토큰, 채널 ID는 코드에 하드코딩하지 않는다.
* 장기적으로는 계정 기반 로그인 또는 OAuth 도입을 검토한다.

## 9. 기술 구현 방향

### 9.1 같은 봇 프로젝트 안에 웹 서버 추가

초기 MVP에서는 별도 프로젝트를 만들지 않고 기존 봇 프로젝트 안에 간단한 웹 서버를 추가하는 방향을 우선 검토한다.

장점:

* 기존 repository helper를 재사용할 수 있다.
* Railway 서비스 하나로 배포 가능하다.
* 현재 JSON 데이터 구조를 바로 읽을 수 있다.
* 구현 범위가 작다.

주의:

* 봇 프로세스와 웹 서버가 같은 Node 프로세스에서 동작하게 되므로 에러 처리가 중요하다.
* 웹 서버 오류가 봇 전체 종료로 이어지지 않게 해야 한다.
* 포트 설정은 Railway 환경변수 `PORT`를 사용한다.

### 9.2 예상 파일 구조

```txt
src/
  adminServer.js
  adminDashboard.js
  adminApi.js
  adminAuth.js
  pointsRepository.js
  pointsStore.js

public/
  admin/
    index.html
    admin.css
    admin.js
```

또는 프론트엔드 빌드 없이 서버에서 간단한 HTML을 반환하는 방식도 가능하다.

초기 MVP에서는 과도한 프레임워크 도입 없이, Express 또는 Node 기본 http 서버 기반으로 시작하는 것을 검토한다.

### 9.3 Railway 배포 고려

필요 환경변수:

```env
ADMIN_DASHBOARD_ENABLED=true
ADMIN_DASHBOARD_PASSWORD=운영자_비밀번호
PORT=Railway가 제공
```

주의:

* Discord bot 실행과 웹 서버 실행이 동시에 가능해야 한다.
* 현재 start script를 변경할 경우 Railway 배포에 영향이 없는지 확인해야 한다.
* health check가 필요한 경우 `/health` endpoint를 추가할 수 있다.

## 11. MVP 완료 기준

관리자 웹 대시보드 MVP는 아래 조건을 만족하면 완료로 본다.

* `/admin` 페이지에 접근할 수 있다.
* 관리자 비밀번호 없이 접근할 수 없다.
* 운영 요약 수치가 표시된다.
* 교환 대기 목록이 표시된다.
* 인증 대기 목록이 표시된다.
* 최근 포인트 로그가 표시된다.
* 미션 상태가 표시된다.
* 상점 상태가 표시된다.
* 반응 승인 기록이 표시된다.
* 데이터가 없을 때도 화면이 깨지지 않는다.
* 봇의 기존 Discord 명령어가 정상 작동한다.
* Railway 배포 후 봇과 웹 페이지가 동시에 동작한다.
* `.env.example`에 필요한 환경변수 placeholder가 정리되어 있다.
* README와 운영 문서에 관리자 대시보드 사용법이 정리되어 있다.

## 11.1 v1 구현 상태

관리자 웹 대시보드 MVP v1은 기존 봇 프로젝트 안에 Node 기본 `http` 서버로 구현한다.

구현 범위:

* `ADMIN_DASHBOARD_ENABLED=true`이고 `ADMIN_DASHBOARD_PASSWORD`가 있을 때만 `/admin`을 활성화한다.
* `/admin` 페이지와 `/api/admin/*` endpoint는 HTTP Basic Auth로 보호한다.
* 운영 요약 카드, 교환 대기, 인증 대기, 최근 포인트 로그, 미션 상태, 상점 상태, 반응 승인 기록을 표시한다.
* 내보내기는 웹 다운로드가 아니라 Discord `/운영내보내기` 사용법을 안내한다.
* 운영 전/중/후 체크리스트를 표시한다.

제외 범위:

* 웹에서 승인, 거절, 완료, 포인트 지급/차감, 미션/상점 수정을 처리하지 않는다.
* Google Sheets와 PostgreSQL 연동은 하지 않는다.
* 새 Slash Command는 추가하지 않는다.

## 13. 결론

현재 Discord 봇은 참여자 경험과 기본 운영 기능을 충분히 지원하는 단계까지 확장되었다. 다만 운영자 입장에서는 Discord 채팅형 UI만으로 전체 상태를 한눈에 파악하기 어렵다.

따라서 다음 단계에서는 Discord 내부 기능을 계속 복잡하게 확장하기보다, **읽기 전용 관리자 웹 대시보드 MVP**를 별도로 추가하는 것이 적절하다.

초기 대시보드는 운영자가 현재 상태를 빠르게 확인하는 용도로 제한하고, 실제 승인/거절/수정 기능은 후속 단계에서 검토한다. 이를 통해 현재 봇 구조의 안정성을 유지하면서도 운영 편의성을 크게 높일 수 있다.
