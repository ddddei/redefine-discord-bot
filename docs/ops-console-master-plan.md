# 운영 완성판 마스터 플랜 — 100%→150% 운영 편의 로드맵 (2026-07-05)

> **2026-07-11 현행화:** 웹게임 읽기 섹션(PR #66), 서버 리플레이 검증(PR #67), 운영 데이터 안전화(PR #74), DM 실운영 준비(PR #75), 미니게임 랭킹 3구간(PR #76), Discord `/게임지급` 반자동 지급(PR #77), handlers 모듈 분할(PR #78)이 코드 기준 완료됐습니다. `/admin`은 아직 읽기 전용이며, 이제 Phase 1 쓰기 기능을 `feat/admin-console-write-v1`에서 착수합니다. Phase 1은 참여자 DM 발송까지 확장하지 않고 상태 변경·2중 인증·감사 추적을 먼저 완성합니다.

## 1. 문서 목적

이 문서는 프로젝트 리디파인 봇을 **"100% 운영 가능"에서 "150% 운영 편의" 수준**으로 끌어올리기 위한 마스터 계획서다. 현재 운영자는 거의 모든 확인·처리를 Discord 안에서 수행하고 있고, `/admin` 웹 대시보드는 읽기 전용 보조 화면에 머물러 있다. 이 문서는:

1. **100% 기준선**: 지금 당장 운영에 필요한 잔여 항목을 확정하고,
2. **운영 관리 웹 콘솔**: 읽기 전용 대시보드를 **처리(쓰기)까지 가능한 운영 콘솔**로 확장하는 결정과 설계를 담고,
3. **150% 후보**: 운영 데이터가 쌓인 뒤 착수할 자동화·품질 항목을 우선순위와 함께 정리한다.

기존 문서와의 관계: [next-work-roadmap-2026-07.md](next-work-roadmap-2026-07.md)(전수 점검 백로그)가 항목의 출처이고, [admin-dashboard-mvp-plan.md](admin-dashboard-mvp-plan.md)(읽기 전용 MVP 설계)를 이 문서가 **명시적으로 개정**한다. 작업 방식은 로드맵 9절 표준(계획서 → 승인 → 지시서 → 구현 → 리뷰 → PR)을 따른다.

> **중요한 범위 결정**: 기존 금기 조항("admin 대시보드를 쓰기 가능하게 만들지 않는다")은 **이 문서 승인으로 해제**된다. 단, 3단계 안전장치(6절: env 게이트·감사 로그·확인 단계)를 동반하는 조건부 해제다. CLAUDE.md / AGENTS.md의 해당 조항도 콘솔 v1 머지 시 함께 갱신한다.

## 2. 현황 진단 — 왜 웹 콘솔인가

### 2.1 지금의 운영 흐름 (전부 Discord 안)

| 운영 작업 | 현재 수단 | 불편 지점 |
| --- | --- | --- |
| 대기 건 파악 | `/운영현황 종류:교환대기·인증대기` | 종류별로 명령 반복, 한눈에 안 보임 |
| 교환 처리 | `/교환관리 상태변경` | 대상 찾기 → 드롭다운 → 확인, 건당 여러 단계 |
| 인증 승인 | 채널 ✅ 반응 or `/인증관리` | 반응 방식은 빠르지만 누락 추적이 어려움 |
| 포인트 지급/정정 | `/포인트관리` | 사유 입력·이력 대조를 채팅으로 |
| 미션/상점 상태 | `/미션관리`, `/상점관리` | 전체 상태 조망 불가 |
| 웹게임 flagged | `/admin` 웹게임 섹션 | 읽기·검증 현황 확인 가능(PR #66·#67) |
| 주간 랭킹 보상 | 수동 지급 루프 | 매주 반복 수작업 |

### 2.2 `/admin` 대시보드의 현재 자산

이미 갖춰진 것 — 재사용 가능:

- HTTP Basic Auth([adminAuth.js](../src/adminAuth.js)) + 정적 프런트(public/admin, 빌드 없음)
- 운영·포인트·미션·DM·웹게임 읽기 API와 대시보드 섹션
- DM 안전 확인 큐 최소 목록과 웹게임 랭킹·flagged·오늘의 도전·공동 목표·응원 통계
- 예시 데이터 제외, 원자 저장, 공통 영속 경로, strict preflight, 백업 manifest

즉 "운영 관리 웹페이지"는 제로부터가 아니라 **기존 읽기 대시보드에 처리 버튼을 얹는 확장**이다. 참여자 경험은 계속 Discord 안에 유지하고, 운영자 처리만 웹으로 보완한다(기존 MVP 원칙 3.2 유지).

## 3. 목표 수준 정의

- **100% = 필수 운영 가능**: 론칭 시나리오의 모든 운영 작업이 문서화된 수단으로 사고 없이 가능. 문서-구현 불일치 없음.
- **120% = 운영 편의**: 반복 작업이 웹 콘솔 한 화면에서 처리되고, 놓치기 쉬운 시점(마감·지연)을 시스템이 먼저 알려줌.
- **150% = 반자동 운영**: 검증(리플레이)·지급(랭킹 보상)·응답(AI 폴백)이 반자동화되어 운영자는 승인 판단만 수행.

## 5. Track 1 — 운영 관리 웹 콘솔 v1 (핵심 트랙, 120% 목표)

### 5.1 설계 원칙

1. **참여자 접점은 Discord 유지** — 콘솔은 운영자 전용. 참여자에게 보이는 알림/DM은 기존 경로 그대로.
2. **모든 상태 변경은 `pointsRepository.js` 경유** — 콘솔이라고 예외 없음(절대 금기 유지). 콘솔 API는 Discord 핸들러가 쓰는 것과 **같은 저장 함수**를 호출한다. 웹 전용 저장 로직 신설 금지.
3. **Discord와 콘솔의 동시 운영 안전** — 처리 시점 재검증(이미 처리된 건이면 409 응답), 원자 저장 유지.
4. **빌드 없는 정적 프런트 유지** — 프레임워크 도입 없이 현행 public/admin 방식 그대로 확장.
5. **모든 쓰기는 감사 로그를 남긴다** (6절).

### 5.2 Phase 1 — 처리 큐 + 쓰기 액션 4종 [우선순위 상 / 크기 중]

**화면**: 대시보드 첫 화면을 "오늘의 처리 큐"로 재편 — 교환 대기 N건·인증 대기 N건·flagged 기록 N건·후속 확인 N건을 카드로 묶고, 각 건에 처리 버튼을 단다.

**쓰기 API (POST, 전부 Basic Auth + 쓰기 게이트 뒤)**:

| 액션 | 엔드포인트 | 대응하는 기존 Discord 경로 |
| --- | --- | --- |
| 교환 상태 변경 (지급완료/취소/환불) | `POST /api/admin/redemptions/:id/status` | `/교환관리 상태변경` |
| 인증 승인/반려 (+포인트 지급) | `POST /api/admin/submissions/:id/decision` | `/인증관리`, ✅ 반응 |
| 포인트 지급/정정 (사유 필수) | `POST /api/admin/points/adjust` | `/포인트관리` |
| 미션/상점 상태 토글 | `POST /api/admin/missions/:id/status`, `POST /api/admin/shop-items/:id/status` | `/미션관리`, `/상점관리` |

**Discord 알림 연동**: Phase 1에서는 운영 로그 채널 알림만 선택적으로 지원하고, 실패해도 상태 변경을 되돌리지 않는다. 참여자 DM/채널 알림은 상태 변경 트랜잭션과 알림 재시도 계약을 함께 설계해야 하므로 이번 범위에서 제외한다. 운영자는 기존 Discord 안내 흐름을 계속 사용하며, 참여자 알림 자동화는 별도 후속 계획으로 다룬다.

**프런트 UX**: 각 액션은 확인 모달(대상 요약 + 사유 입력) → 실행 → 결과 토스트 + 큐 갱신. 실패(이미 처리됨 등)는 명확한 한국어 안내.

### 5.3 Phase 2 — 웹게임 운영 액션 [우선순위 상 / 크기 소~중 / E-1 선행]

## 6. 보안 설계 (쓰기 도입의 전제 조건)

읽기 전용일 때는 Basic Auth로 충분했지만 쓰기는 다르다. 콘솔 v1에 다음을 **필수 동반**한다:

1. **`ADMIN_WRITE_ENABLED=true` env 게이트** — 기본 off. off면 모든 쓰기 API가 403, 프런트도 버튼 숨김. 사고 시 즉시 읽기 전용 복귀 가능.
2. **감사 로그** — `ADMIN_AUDIT_DATA_PATH` → `OPERATION_DATA_DIR/admin-audit.local.json` → `data/admin-audit.local.json` 우선순위로 해석한다. 원자 저장·백업 manifest 대상이며 시각·액션·대상·사유·결과·요청 출처를 기록한다. 로그가 무한히 커지지 않도록 최근 1,000건으로 제한한다.
3. **확인 단계** — 모든 쓰기는 프런트 확인 모달 + 서버 측 현재 상태 재검증(이미 처리된 건 409).
4. **쓰기 토큰(필수)** — Basic Auth 유지에 더해 `ADMIN_WRITE_TOKEN`과 `X-Admin-Write-Token` 헤더가 모두 있어야 한다. `ADMIN_WRITE_ENABLED=true`여도 토큰이 미설정이면 서버는 쓰기를 활성화하지 않고 503으로 거부한다. 비밀번호 유출 단독으로는 쓰기 불가하다.
5. **요청 안전성** — JSON 본문 크기를 제한하고, 사용자 입력을 스키마별로 검증하며, CORS를 열지 않는다. 응답은 `Cache-Control: no-store`로 캐시를 막고 비밀값은 응답·감사 로그에 기록하지 않는다.
6. 기존 원칙 유지: 예시 데이터 제외, discordId는 admin 한정 노출, HTTPS는 Railway 종단에 위임.
