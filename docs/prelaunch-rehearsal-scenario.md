# 운영 전 QA 리허설 시나리오

실제 참여자를 받기 전에 운영자 계정과 테스트 참여자 계정으로 전체 흐름을 한 번 끝까지 점검하는 문서입니다. 이 문서는 운영자가 순서대로 따라 하는 리허설 절차이며, 코드 기능 변경이나 Slash Command 추가, 운영 데이터 자동 생성을 전제로 하지 않습니다.

## 1. 문서 목적

- 참여자 입장에서 `/안내`부터 교환 신청까지의 흐름이 자연스러운지 확인합니다.
- 운영자 입장에서 반응 승인, 포인트 로그, 교환 처리, 관리자 대시보드, 내보내기 흐름을 확인합니다.
- Railway 환경변수, Discord 권한, 채널, 운영용 미션/상점 상태를 실제 운영 기준으로 점검합니다.
- 리허설 데이터와 실제 운영 데이터를 구분하고, 운영 시작 전 정리 항목을 남깁니다.

## 2. 리허설 전체 목표

- 테스트 참여자 계정으로 `/안내 -> /미션 -> /체크인 -> 인증 업로드 -> /포인트 -> /상점 -> /교환` 흐름을 1회 이상 완료합니다.
- 운영자 계정으로 `✅ 반응 승인 -> /포인트로그 -> /운영현황 -> /admin -> /교환관리 -> /운영내보내기` 흐름을 1회 이상 완료합니다.
- `/admin` 읽기 전용 대시보드에서 요약 카드, 대기 목록, 최근 로그, 미션/상점 상태, 반응 승인 기록을 확인합니다.
- `/운영내보내기`로 리허설 후 백업 가능 여부를 확인합니다.
- 운영 시작 전 테스트 데이터 정리 여부와 운영용 active 항목만 남았는지 판단합니다.

## 3. 준비물

- 운영자 계정 1개
- 테스트 참여자 계정 1개
- 미션 인증 채널
- 운영 로그 채널
- 교환 신청 알림 채널
- 관리자 웹 대시보드 URL
- Railway Variables 접근 권한
- Discord 개발자 모드
- 운영용 미션/상점 등록 기준 문서

## 4. 테스트 계정 준비

- 테스트 참여자 계정이 일반 참여자 권한만 가지고 있는지 확인합니다.
- 운영자 전용 채널, 운영 로그 채널, 교환 알림 채널을 볼 수 없어야 합니다.
- `/안내`, `/포인트`, `/상점`, `/교환`, `/체크인`, `/미션`, `/인증`을 실행할 수 있어야 합니다.
- 미션 인증 채널에 글, 사진, 영상 메시지를 올릴 수 있어야 합니다.
- DM 수신 가능 상태로 먼저 테스트하고, 필요하면 DM 차단 상태에서도 `/포인트`로 결과를 확인합니다.

## 5. 운영자 계정 준비

- 운영자 계정이 `ManageMessages` 또는 `Administrator` 권한을 가지고 있는지 확인합니다.
- `OPERATOR_ROLE_ID`를 사용하는 경우 운영자 계정에 해당 역할이 있는지 확인합니다.
- 운영자 계정은 미션 인증 채널에서 반응을 추가할 수 있어야 합니다.
- 운영자 계정은 `/운영현황`, `/포인트관리`, `/교환관리`, `/인증관리`, `/포인트로그`, `/미션관리`, `/상점관리`, `/운영내보내기`를 사용할 수 있어야 합니다.
- 일반 참여자 테스트 계정으로 운영자 명령어가 실행되지 않는지 확인합니다.

## 6. 채널 준비

- `MISSION_SUBMISSION_CHANNEL_ID`: 참여자가 인증 글, 사진, 영상을 올리는 미션 인증 채널입니다.
- `LOG_CHANNEL_ID`: 기본 운영 로그와 fallback 알림 채널입니다.
- `ACTIVITY_REVIEW_CHANNEL_ID`: 미션 인증 검토와 반응 승인/반려 처리 로그 채널입니다.
- `POINT_REDEEM_CHANNEL_ID`: 교환 신청과 처리 알림 채널입니다.

채널별 봇 권한을 확인합니다.

- 미션 인증 채널: `View Channel`, `Read Message History`, `Add Reactions`, `Send Messages`
- 운영 로그 채널: `View Channel`, `Send Messages`
- 교환 알림 채널: `View Channel`, `Send Messages`
- 운영자 전용 채널: 일반 참여자 접근 차단

## 7. Railway 환경변수 확인

Railway Variables 또는 운영 `.env`에서 아래 값을 확인합니다. 실제 토큰, 비밀번호, 채널 ID는 문서에 적지 않습니다.

- `DISCORD_TOKEN`
- `CLIENT_ID`
- `GUILD_ID`
- `LOG_CHANNEL_ID`
- `MISSION_SUBMISSION_CHANNEL_ID`
- `ACTIVITY_REVIEW_CHANNEL_ID`
- `POINT_REDEEM_CHANNEL_ID`
- `MISSION_REACTION_REWARD_POINTS`
- `MISSION_APPROVE_EMOJI`
- `MISSION_REJECT_EMOJI`
- `REACTION_APPROVAL_PUBLIC_REPLY`
- `REACTION_APPROVAL_DM_USER`
- `ADMIN_DASHBOARD_ENABLED`
- `ADMIN_DASHBOARD_PASSWORD`
- `ADMIN_DASHBOARD_TITLE`

권장 리허설 기준:

- `REACTION_APPROVAL_PUBLIC_REPLY=false`: 인증 채널에 승인/반려 공개 답글을 남기지 않습니다.
- `REACTION_APPROVAL_DM_USER=true`: 승인/반려 후 참여자 DM 알림을 보냅니다.
- `ADMIN_DASHBOARD_ENABLED=true`: 관리자 대시보드를 리허설에서 확인합니다.
- `ADMIN_DASHBOARD_PASSWORD`: 운영용 비밀번호가 비어 있지 않아야 합니다.

## 8. 관리자 대시보드 접속 확인

1. Railway Public Domain이 생성되어 있는지 확인합니다.
2. 브라우저에서 `https://Railway-도메인/admin`으로 접속합니다.
3. Basic Auth가 표시되는지 확인합니다.
4. 올바른 비밀번호로 접속했을 때 대시보드가 열리는지 확인합니다.
5. 잘못된 비밀번호로 `/admin`과 `/api/admin/summary` 접근 시 401 응답이 반환되는지 확인합니다.
6. 상단에 읽기 전용, local JSON, example 데이터 제외 안내가 보이는지 확인합니다.

`/admin`은 읽기 전용입니다. 승인, 반려, 지급, 차감, 미션/상점 수정은 Discord 명령어로 처리합니다.

## 9. 운영용 기본 미션 등록

리허설에서는 아래 3개를 최소 active 미션 후보로 등록합니다. 실제 명령어 옵션명은 Discord 자동완성과 현재 `/미션관리` 화면 기준으로 조정합니다.

### 미션 1. 첫 인사 남기기

- 권장 포인트: 20P
- 상태: active
- 인증 방식: 지정 채널에 첫 인사 작성 또는 미션 인증 채널 업로드
- 테스트 목적: 참여자가 처음 말을 걸 수 있는지 확인

### 미션 2. 오늘의 체크인

- 권장 포인트: 10P
- 상태: active
- 인증 방식: `/체크인`
- 테스트 목적: 하루 1회 체크인과 포인트 지급 흐름 확인

### 미션 3. 미션 인증 글/사진 남기기

- 권장 포인트: 30P
- 상태: active
- 인증 방식: 미션 인증 채널에 글/사진 업로드 후 운영자 ✅ 승인
- 테스트 목적: 반응 승인, 포인트 지급, DM 알림 확인

등록 후 확인:

- `/미션관리 작업:목록`에서 상태가 active인지 확인합니다.
- 참여자 계정으로 `/미션`을 실행해 미션 ID보다 미션명이 먼저 이해되는지 확인합니다.
- `/admin`에서 활성 미션 수가 등록한 active 미션 수와 맞는지 확인합니다.

## 10. 운영용 기본 상점 등록

리허설에서는 아래 항목 1개만 active로 두는 것을 권장합니다.

### 상점 1. 청년동 포인트 전환 100P

- 필요 포인트: 100P
- 유형: `youthCenterPoint`
- 상태: active
- 재고: 제한 없음
- 테스트 목적: 참여자가 상점 확인과 교환 신청을 이해하는지 확인

추가 후보는 참고로만 확인하고 초기 리허설에서는 hidden 또는 paused 상태를 권장합니다.

- 청년동 포인트 전환 300P
- 프린트 카드 충전권
- 밀리의 서재 구독권
- 왓챠 구독권

등록 후 확인:

- `/상점관리 작업:목록`에서 상태가 active인지 확인합니다.
- 참여자 계정으로 `/상점`을 실행해 항목명이 먼저 보이는지 확인합니다.
- `/admin`에서 활성 상점 항목 수가 등록한 active 항목 수와 맞는지 확인합니다.

## 11. 참여자 흐름 테스트

테스트 참여자 계정으로 아래 순서를 진행합니다.

1. `/안내`를 실행합니다.
2. 드롭다운에서 처음 안내를 확인합니다.
3. 드롭다운에서 오늘 할 일을 확인합니다.
4. `/미션`을 실행합니다.
5. 미션 목록을 확인합니다.
6. `/체크인`을 실행합니다.
7. `/포인트`를 실행합니다.
8. 미션 인증 채널에 테스트 글 또는 사진을 업로드합니다.
9. 운영자 승인 후 DM 수신 여부를 확인합니다.
10. `/포인트`를 다시 실행합니다.
11. `/상점`을 실행합니다.
12. `청년동 포인트 전환 100P` 항목을 확인합니다.
13. `/교환`을 실행합니다.
14. 교환 신청 전 주의 문구를 확인합니다.
15. 교환 신청을 완료합니다.

확인 기준:

- `/안내`만 보고 다음 행동을 알 수 있어야 합니다.
- `/미션`에서 미션 ID보다 미션명이 먼저 이해되어야 합니다.
- 미션 인증 채널에 글이나 사진을 올리는 흐름이 어렵지 않아야 합니다.
- DM 문구가 차갑거나 과하게 딱딱하지 않아야 합니다.
- `/포인트`에서 승인 후 잔액이 바로 확인되어야 합니다.
- `/상점`에서 항목 설명이 너무 길지 않아야 합니다.
- `/교환` 신청 전 안내가 위협적으로 보이지 않아야 합니다.
- 신청하지 않기를 선택한 경우 포인트가 차감되지 않아야 합니다.

## 12. 미션 인증 반응 승인 테스트

운영자 계정으로 미션 인증 채널의 테스트 참여자 인증 메시지를 확인합니다.

1. 지급 대상 메시지에 `MISSION_APPROVE_EMOJI` 기준 ✅ 반응을 추가합니다.
2. 원본 인증 채널에 공개 답글이 남지 않는지 확인합니다.
3. `ACTIVITY_REVIEW_CHANNEL_ID` 또는 `LOG_CHANNEL_ID`에 승인 처리 로그가 남는지 확인합니다.
4. 같은 메시지에 다시 ✅를 눌러도 중복 지급되지 않는지 확인합니다.
5. 지급 대상이 아닌 테스트 메시지에는 `MISSION_REJECT_EMOJI` 기준 ❌ 반응을 눌러 반려 기록만 남는지 확인합니다.
6. 운영자 권한이 없는 테스트 계정의 ✅ 또는 ❌ 반응은 무시되는지 확인합니다.

## 13. 포인트 확인 테스트

- 참여자 계정으로 승인 전후 `/포인트` 잔액을 비교합니다.
- 운영자 계정으로 `/포인트로그`를 실행해 `missionReactionApproval` 관련 지급 기록을 확인합니다.
- `/운영현황`의 최근 포인트 로그에서 같은 거래가 보이는지 확인합니다.
- DM이 오지 않아도 포인트 지급과 로그 기록이 유지되는지 확인합니다.

## 14. 상점/교환 신청 테스트

1. 참여자 계정으로 `/상점`을 실행합니다.
2. active 상태의 `청년동 포인트 전환 100P` 항목만 노출되는지 확인합니다.
3. `/교환`을 실행하고 선택 메뉴에서 항목을 고릅니다.
4. 신청 전 주의 문구를 확인합니다.
5. 신청 완료 후 포인트가 차감되고 신청이 pending 상태로 남는지 확인합니다.
6. `POINT_REDEEM_CHANNEL_ID` 또는 `LOG_CHANNEL_ID`에 교환 신청 알림이 남는지 확인합니다.
7. `/admin`의 교환 대기 수가 증가하는지 확인합니다.

필요하면 `/교환 항목:S001`처럼 신청 코드 직접 입력 호환도 함께 확인합니다.

## 15. 운영자 처리 테스트

운영자 계정으로 아래 순서를 진행합니다.

1. `/운영현황`에서 교환 대기와 최근 포인트 로그를 확인합니다.
2. `/admin`에서 교환 대기 목록을 확인합니다.
3. 실제 지급을 완료했다고 가정한 뒤 `/교환관리`로 지급완료 처리합니다.
4. 예외 상황 테스트가 필요하면 별도 테스트 신청을 만들고 `/교환관리`로 취소 또는 환불완료를 기록합니다.
5. `/포인트로그`에서 교환 차감, 환불, 정정 거래가 의도대로 남는지 확인합니다.
6. `/운영현황`을 다시 실행해 교환 대기 수가 줄었는지 확인합니다.
7. `/admin`을 새로고침해 교환 대기 수와 목록이 갱신되는지 확인합니다.

## 16. 관리자 대시보드 확인 테스트

`/admin`에서 아래 항목을 확인합니다.

- 사용자 수가 테스트 참여자 기준으로 반영되는지
- 오늘 포인트 거래 수가 증가하는지
- 오늘 지급 포인트가 반영되는지
- 교환 대기 수가 교환 신청 후 증가하는지
- 교환 처리 후 대기 수가 줄어드는지
- 활성 미션 수가 등록한 미션 수와 맞는지
- 활성 상점 항목 수가 등록한 상점 수와 맞는지
- 오늘 반응 승인 수가 증가하는지
- 최근 포인트 로그가 최신순으로 보이는지
- `user_example`, `rd_example`, `submission_example`, `tx_example`, 2030년 샘플 날짜 같은 example 데이터가 보이지 않는지
- 승인, 거절, 수정 버튼이 없고 Discord 명령어로 처리하라는 안내가 보이는지

## 17. 운영 데이터 내보내기 테스트

1. `/운영내보내기 종류:요약 형식:요약`으로 전체 수량을 확인합니다.
2. `/운영내보내기 종류:전체 형식:JSON`으로 전체 백업을 받습니다.
3. 필요한 경우 `/운영내보내기 종류:포인트 형식:CSV` 또는 `/운영내보내기 종류:교환 형식:CSV`를 받습니다.
4. 내보낸 파일에 사용자 ID, 표시 이름, 인증 내용, 운영 메모가 포함될 수 있음을 확인합니다.
5. 백업 파일 보관 위치와 접근 권한을 운영자 내부 기준으로 정합니다.

## 18. 실패 시 확인할 것

### `/안내`가 안 뜨는 경우

- 봇이 Online 상태인지 확인합니다.
- Slash Command가 운영 서버에 등록되어 있는지 확인합니다.
- Slash Command 구조 변경이 있었는지 확인합니다.
- 구조 변경이 있었다면 `npm run deploy` 필요 여부를 판단합니다. 문서만 수정한 경우 deploy를 실행하지 않습니다.

### 반응 승인으로 포인트가 지급되지 않는 경우

- `MISSION_SUBMISSION_CHANNEL_ID`가 실제 인증 채널 ID와 맞는지 확인합니다.
- 운영자에게 `ManageMessages`, `Administrator`, 또는 `OPERATOR_ROLE_ID` 권한이 있는지 확인합니다.
- 참여자 본인이 자기 메시지에 ✅를 누른 것은 아닌지 확인합니다.
- 대상 메시지가 봇 또는 MEE6 메시지가 아닌지 확인합니다.
- `MISSION_APPROVE_EMOJI` 값이 실제 승인 반응과 같은지 확인합니다.
- Railway 재배포가 완료되었는지 확인합니다.
- `/포인트로그`와 운영 로그 채널에 오류나 중복 처리 기록이 있는지 확인합니다.

### DM이 오지 않는 경우

- `REACTION_APPROVAL_DM_USER=true`인지 확인합니다.
- 참여자가 서버 DM을 차단하지 않았는지 확인합니다.
- 포인트 지급 자체는 되었는지 `/포인트`와 `/포인트로그`로 확인합니다.
- DM 실패가 포인트 지급이나 반려 기록을 막지 않는지 확인합니다.

### `/admin`이 안 열리는 경우

- Railway Public Domain이 생성되었는지 확인합니다.
- `ADMIN_DASHBOARD_ENABLED=true`인지 확인합니다.
- `ADMIN_DASHBOARD_PASSWORD`가 설정되어 있는지 확인합니다.
- `/admin` 경로로 접속했는지 확인합니다.
- Basic Auth 비밀번호가 맞는지 확인합니다.
- `ADMIN_DASHBOARD_TITLE`은 제목 표시용이며 인증 실패의 원인이 아닌지 구분합니다.

### 교환 알림이 안 오는 경우

- `POINT_REDEEM_CHANNEL_ID`가 설정되어 있는지 확인합니다.
- 교환 알림 채널이 없으면 `LOG_CHANNEL_ID` fallback이 있는지 확인합니다.
- 봇이 해당 채널에 메시지를 보낼 수 있는지 확인합니다.
- 참여자 포인트가 부족해서 신청 자체가 접수되지 않은 것은 아닌지 확인합니다.

### 관리자 대시보드에 데이터가 안 보이는 경우

- example 데이터는 제외되는 것이 정상인지 확인합니다.
- 실제 운영용 미션/상점이 active 상태인지 확인합니다.
- 테스트 데이터가 local JSON에 저장되었는지 확인합니다.
- Railway와 로컬이 서로 다른 데이터 저장 위치를 보고 있는지 확인합니다.
- `data/*.local.json`이 커밋 대상이 아닌 운영 데이터 파일임을 확인합니다.

## 19. 실제 운영 전 정리할 것

- `data/*.example.json`은 삭제하지 않습니다.
- `data/*.local.json`은 커밋하지 않습니다.
- 테스트 참여자 포인트를 초기화할지 결정합니다.
- 테스트 교환 신청을 지급완료, 취소, 환불완료 중 하나로 처리하거나 운영 전 정리합니다.
- 테스트 미션 인증 기록을 남길지 삭제할지 운영 기준으로 판단합니다.
- 운영용 미션만 active로 남깁니다.
- 운영용 상점만 active로 남깁니다.
- hidden, paused, soldOut 항목이 참여자에게 노출되지 않는지 확인합니다.
- `/admin`에서 example/test 데이터가 운영 데이터처럼 보이지 않는지 확인합니다.
- `/운영내보내기`로 리허설 후 백업을 저장합니다.
- 운영 시작 전 최종 공지와 참여자 안내 문구를 준비합니다.

## 20. 최종 운영 가능 판단 기준

아래 항목이 모두 충족되면 실제 운영 시작 가능으로 판단합니다.

- 참여자 계정으로 `/안내`, `/미션`, `/포인트`, `/상점`, `/교환`이 자연스럽게 작동합니다.
- `/안내`만 보고 참여자가 다음 행동을 이해할 수 있습니다.
- 미션 인증 채널 업로드 후 운영자 ✅ 승인으로 포인트가 지급됩니다.
- DM 알림이 오거나, DM 차단 상태에서도 `/포인트`로 결과 확인이 가능합니다.
- 교환 신청이 pending 상태로 남고 운영자가 `/교환관리`로 처리할 수 있습니다.
- `/운영현황`과 `/admin`에서 상태 변화가 확인됩니다.
- `/운영내보내기`로 데이터 백업이 가능합니다.
- 관리자 대시보드에 example 데이터가 운영 데이터처럼 보이지 않습니다.
- 테스트 데이터 정리 여부가 결정되어 있고 실제 운영용 미션/상점만 active 상태입니다.
- 운영자 1명이 참여자 흐름과 운영자 처리 흐름을 말로 설명할 수 있습니다.
- 참여자에게 안내할 최소 공지 문구가 준비되어 있습니다.
