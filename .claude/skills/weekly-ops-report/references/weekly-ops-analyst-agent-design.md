# 주간 운영 분석 에이전트(weekly-ops-analyst) 설계서

**상태: 설계 초안 (2026-07-12, 미커밋) — 승인 후 스킬/스케줄로 이관**

## 0. 봇과의 역할 분담 (설계의 전제)

봇에는 이미 주간 운영 리포트 v1이 있다(`src/adminServer.js`의 `/api/admin/weekly-report`,
자동 발송 `WEEKLY_OPS_REPORT_ENABLED`, 계획서 `docs/weekly-ops-report-v1-plan.md`).
**숫자 집계와 Discord 발송은 봇의 책임이고, 이 에이전트는 그 위의 해석 계층이다.**

| 책임 | 봇 (weekly-ops-report v1) | 에이전트 (weekly-ops-analyst) |
|---|---|---|
| 주간 숫자 집계 | ✅ 단일 진실 (`buildWeeklyOpsReportFromRepository`) | ❌ 직접 집계 금지, 봇 결과만 소비 |
| Discord 채널 발송 | ✅ (주차별 원자 선예약) | ❌ 발송하지 않음 |
| 추세·전주 대비 해석 | ❌ | ✅ 4주 비교, 이상 신호 |
| 권고 액션 도출 | ❌ | ✅ 우선순위 1~3개 |
| 조용한 실패 감시 | 부분 (발송 이력) | ✅ 데이터 품질 체크 전담 |

## 1. 역할 정의, 입력과 출력

**역할**: 매주 월요일 오전, 직전 완료 주(KST 월~일)의 운영 데이터를 해석해
운영자가 **5분 안에 읽고 다음 행동을 정할 수 있는** 분석 리포트를 만든다.
참여자 평가·순위 도구가 아니라 누락된 운영 업무와 이상 신호를 찾는 내부 도구다
(v1 계획서 1절의 원칙을 그대로 계승).

**입력** (전부 읽기 전용):
- `/api/admin/weekly-report?weekOffset=-1` — 직전 완료 주 (필수)
- `weekOffset=-2 ~ -5` — 추세 비교용 4주 (선택, 실패 시 생략 가능)
- `/api/admin/summary`, `/api/admin/webgames` — 현재 대기 큐·flagged 기록
- 지난주 머지된 PR 목록 (`gh pr list --state merged`) — "지난주 무엇이 바뀌었나" 맥락
- 이전 리포트 아카이브 (`docs/ops-reports/` 최신 파일) — 전주 권고 액션 이행 확인

**출력**:
1. 분석 리포트 마크다운 1건 → `docs/ops-reports/weekly-YYYY-MM-DD.md` (주 시작일 기준)
2. 채팅 요약 (TL;DR 3줄 + 권고 액션) — 운영자에게 직접 보고
3. 이상 신호가 있으면 에스컬레이션 블록 (4절 조건)

## 2. 필요한 도구/데이터 소스와 접근 방법

| 소스 | 접근 방법 | 주의 |
|---|---|---|
| admin API | `curl -u` + `$ADMIN_USERNAME:$ADMIN_PASSWORD` (env에서 읽기, 프롬프트/리포트에 값 노출 금지) | GET만 사용. POST(`/weekly-report/send` 포함) 호출 금지 |
| 실행 위치 | 기본: 배포된 Railway URL. 로컬 폴백: `preview_start`로 서버 기동 후 localhost | 로컬 폴백 시 로컬 `data/*.local.json` 기준임을 리포트에 명시 |
| GitHub | `gh pr list --state merged --search "merged:>=<주시작일>"` | 실패해도 리포트 진행 (맥락 절만 생략) |
| 아카이브 | `docs/ops-reports/` 파일 읽기/쓰기 | git 미커밋 상태로 두고 커밋은 사람이 결정 |

새 인프라·의존성 없음. 봇 코드 무수정.

## 3. 단계별 실행 순서 (재시도 규칙 포함)

**재시도 일반 규칙**: 네트워크성 오류(연결 거부·타임아웃·5xx)만 5초 간격 2회 재시도.
4xx(401/400)는 재시도 무의미 → 즉시 에스컬레이션. 한 단계가 3회 실패해도
필수 소스가 아니면 해당 절을 "수집 실패"로 표기하고 계속 진행한다 (부분 리포트 > 무 리포트).

1. **사전 점검**: `weekly-report?weekOffset=-1` 1회 호출로 인증·연결 확인.
   401 → 중단, 에스컬레이션 (비밀번호 교체 이슈일 가능성 — 리허설 메모 참조).
2. **수집**: weekOffset -1(필수), -2~-5(선택), summary, webgames, 지난주 PR, 직전 아카이브.
3. **정합성 검사** (하나라도 걸리면 리포트 상단에 ⚠️ 데이터 품질 경고):
   - 응답의 주 시작일 == 직전 월요일(KST)인가
   - 필수 필드(참여자 수, 체크인, 인증 상태별, 포인트 합계, 교환 상태별)가 존재하는가 (스키마 변경 감지)
   - example/demo/sample 흔적이 없는가
4. **추세 계산**: 4주 창으로 참여자 수, 체크인 수, 인증 승인율, 포인트 순증(지급−차감),
   교환 대기 건수, 지연 신호 건수의 전주 대비 방향(▲▼—)과 %.
5. **이상 신호 스캔**: 4절 에스컬레이션 조건 + 6절 조용한 실패 체크 전부 실행.
6. **리포트 작성**: 7절 프롬프트의 고정 템플릿으로 작성, 아카이브 저장.
7. **보고**: 채팅에 TL;DR + 권고 액션 + (있으면) 에스컬레이션 블록. **발송·커밋·상태 변경은 하지 않는다.**

## 4. 사람에게 에스컬레이션해야 하는 조건

리포트를 만들다 아래를 발견하면 리포트 최상단에 `🚨 확인 필요` 블록으로 올리고,
해당 항목은 해석하지 말고 사실만 적는다:

- **필수 소스 접근 불가** (401, 연결 거부 3회) — 리포트 생성 자체 중단
- **참여자 수 0 또는 전주 대비 50% 이상 급감** — 집계 회귀인지 실제 이탈인지 에이전트가 판별 불가
- **주간 리포트 발송 이력에 `failed`** — v1은 자동 재시도하지 않으므로 사람이 수동 처리해야 함
- **example 레코드가 실데이터 응답에 노출** — CLAUDE.md 금기 위반, 코드 회귀
- **flagged 웹게임 기록 존재** — 부정 의심은 사람 판정 사안
- **지연 신호(교환·인증 임계 초과)가 2주 연속 증가** — 운영 인력 문제일 수 있음
- 에이전트 판단 원칙: **해석·권고까지만.** 포인트·교환·발송·env 등 상태를 바꾸는 행동은 어떤 경우에도 하지 않는다.

## 5. 기억할 것(메모리) vs 매번 새로 확인할 것

| 기억한다 (아카이브/스킬 문서에 축적) | 매번 새로 확인한다 (캐시 금지) |
|---|---|
| 리포트 템플릿과 지표 정의 | 모든 숫자 (지난 실행의 숫자 재사용 금지) |
| 임계값 (급감 50%, 지연 2주 연속 등) | API 응답의 필수 필드 존재 (스키마는 바뀔 수 있다) |
| 운영자 해석 피드백 ("이 지표는 무시해도 됨" 등) | 지난주 머지 PR 목록 |
| 특이 주간 기록 (이벤트 주, 방학 등 — 급감 오탐 방지) | env·채널·배포 상태에 대한 가정 |
| 전주 권고 액션 (이행 여부 추적용) | 아카이브 파일 존재 여부 (첫 실행일 수 있다) |

원칙: **데이터는 기억하지 않고, 해석 규칙만 기억한다.** 특이 주간·피드백은
`docs/ops-reports/analyst-notes.md` 한 파일에 누적한다 (에이전트가 매 실행 시 읽음).

## 6. 성공 지표 + 조용히 망가지는 실패를 잡는 체크

**성공 지표**:
- 월요일 오전 정해진 시각까지 리포트 도착률 (4주 이동 100% 목표)
- 권고 액션 이행률 — 다음 주 리포트가 전주 권고의 이행 여부를 확인해 스스로 측정
- 운영자가 리포트만 읽고 추가 질문 없이 행동 가능한가 (질문 발생 = 템플릿 개선 신호 → analyst-notes.md에 기록)

**조용한 실패 체크** (매 리포트의 "데이터 품질" 각주 절에 결과를 항상 표기 — "이상 없음"도 명시):
1. 참여자·거래 수가 0인가 → 집계 필터 회귀 의심
2. 4주 숫자가 전부 동일한가 → 파일 미갱신/캐시 의심
3. 주 시작일이 기대값과 다른가 → 시간대(KST) 버그
4. 필수 필드 누락 → API 스키마 변경 (스킬 문서 갱신 필요 신호)
5. 아카이브에 같은 주 파일이 이미 있는가 → 스케줄 중복 실행 (덮어쓰지 말고 `-rerun` 접미사로 저장 후 보고)
6. 백업·발송 이력이 비어 있는가 → env 꺼짐 vs 고장 구분해 보고
7. **월 1회 메타 체크**: 사람이 리포트 지표 1개를 골라 원본(`/운영현황` 또는 콘솔 화면)과 수동 대조 — 에이전트가 매월 첫 리포트에 "이번 주는 수동 대조 주입니다" 리마인더를 넣는다

## 8. 스킬/스케줄 자동화로 옮기는 방법 (제안)

**1단계 — 프로젝트 스킬로 (권장 시작점)**: `.claude/skills/weekly-ops-report/SKILL.md`에
7절 프롬프트를 본문으로, 이 설계서를 `references/`로 넣는다. 운영자가 월요일에
`/weekly-ops-report` 한 번 치는 반자동 운영으로 2~3주 돌려 템플릿·임계값을 튜닝한다.
sandwich-review 스킬의 테스트 방식대로 **결함 주입 테스트**(가짜 401, 참여자 0 응답)로
에스컬레이션이 작동하는지 먼저 검증한다.

**2단계 — 스케줄 자동화**: 수동 운영이 2주 연속 무수정 통과하면 `/schedule`로
매주 월요일 09:00 KST 반복 작업을 등록한다 (하위 모델 지정 가능 — Sonnet 권장,
숫자 해석이 단순해지면 Haiku 시험). 스케줄 프롬프트는 "스킬 `/weekly-ops-report` 실행" 한 줄로
유지해 로직이 스킬 한 곳에만 존재하게 한다. 주의: 스케줄 에이전트가 admin API에
