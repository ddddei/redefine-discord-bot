# 구현물 대조 리뷰 + 검증 루틴

구현이 계획서/지시서대로 됐는지 검증한다. 핵심 원칙: **구현자의 보고를 믿지 말고 직접 실행해서 확인한다.**

## 1단계 — diff 범위 확인

- `git diff main --stat`: 변경 파일이 지시서의 "수정 가능 파일 목록" 안에만 있는가.
- 관련 없는 최근 머지 PR의 파일·연동(wiring)이 지워지지 않았는지 grep으로 확인 (리베이스·충돌 해소가 있었다면 필수).

## 2단계 — 계획서 대조 리뷰

계획서/지시서의 작업 항목을 하나씩 짚으며 diff와 대조한다. 항목별로 "일치 / 미흡(수정 지시) / 계획에 없는 추가(사유 확인)"로 판정. 특히:
- 저장 로직이 `pointsRepository.js`를 경유하는가 (직접 JSON 쓰기 금지)
- example 데이터가 실데이터 화면에 노출되지 않는가
- 사용자 노출 문구의 톤이 기존 문서와 일치하는가

## 3단계 — 검증 사다리 (아래 순서대로, 실패하면 수정 후 그 단계부터 재실행)

1. `node --check <변경된 각 .js>` — 문법
2. 신규 스모크 테스트 개별 실행: `node scripts/test-<이름>.js`
3. 건드린 모듈의 기존 스모크 테스트 개별 실행 (회귀)
4. `npm run check:release` — 전체 게이트. 신규 테스트가 게이트 출력에 실제로 나타나는지 확인 (등록 누락 감지).
5. **웹 노출 변경이면 브라우저 QA**: 계획서의 수동 QA 절을 실제 서버를 띄워 수행 — 정상 경로, 무효 입력(상태 무변화 확인), 375px 모바일 뷰포트, 시드 결정성(해당 시), curl로 무인증 401·경로 탈출(`../../.env`) 404.
6. 데이터 형태가 바뀌었으면 4종 세트 확인: `pointsRepository.js` + example fixture + 검증/스모크 테스트 + 문서.

## 4단계 — 커밋·PR 정리

- 논리 단위로 커밋 분리 (feat/test/docs).
- main에 직접 있으면 feature 브랜치를 만들어 옮긴다 (트렁크+PR 관례).
- 계획서 단계에서 열린 PR이 이미 있으면 새 PR 대신 그 PR 제목·본문을 갱신한다.
- PR 본문: 변경 내용 / 이유 / 리뷰어 참고(포맷 불변·롤백 방법) / 테스트 결과. 한국어.

## 5단계 — 보고 (한국어, 항상 포함)

- 리뷰 결과: 수정 지시 건수와 내용 (0건이면 0건이라고 명시)
- 검증 결과: 실행한 명령과 통과 여부 (출력에서 확인한 사실만)
- **머지 후 후속 조치**: `deploy-commands.js` 변경 시 "`npm run deploy` 필요, 실행 전까지의 증상"까지 명시. 없으면 "후속 조치 없음".
- 롤백 방법 한 줄
- 커밋/푸시/PR 상태 명시 ("푸시는 아직 안 했습니다" 등)
- 다음 단계 제안 1~2개

## 잘 작동하는지 확인하는 테스트

1. **결함 주입 테스트**: 정상 구현물에 일부러 결함을 심고(예: check-release.js 등록 누락, 지시서 밖 파일 수정, example 필터 제거) 하위 모델에게 이 스킬로 리뷰시킨다. 3건 중 3건을 잡아야 통과.
2. 검증 사다리 각 단계의 **명령 실행 증거**(출력 인용)가 보고에 있는지 확인 — "통과했습니다"라는 말만 있고 출력 근거가 없으면 실패.
3. 머지 후 후속 조치 판정 테스트: deploy-commands.js를 건드린 diff와 안 건드린 diff를 각각 주고, `npm run deploy` 필요 여부를 정확히 판정하는지 본다.
