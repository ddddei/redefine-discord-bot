# 기능 계획서 작성

구현 전에 승인받는 계획서를 만든다. 이 저장소의 워크플로는 **계획서 승인 → 구현(코덱스/샌드위치) → 리뷰 → PR**이며, 계획서가 이 체인의 첫 관문이다.

## 절차

1. **형식 기준 확보**: 기존 계획서를 1개 이상 읽고 형식을 따른다. 기준 문서: `docs/admin-dashboard-mvp-plan.md`, `docs/dm-chat-mvp-plan.md`. 해당 디렉터리의 `AGENTS.md`도 먼저 읽는다.
2. **실코드 분석**: 계획서의 모든 주장(함수 존재 여부, 수정 위치, 깨질 테스트)은 grep/Read로 실제 코드에서 확인한 것만 적는다. 추측으로 함수명을 지어내지 않는다.
3. **계획서 작성** — 아래 장 구성을 전부 포함:
   - **배경/문제**: 왜 지금 이 작업인가. 착수 게이트가 있으면 0절에 명시 (예: "종반 도달 참여자가 없으면 보류").
   - **전체 구조**: 모듈 흐름 다이어그램, 저장 스키마(version 규칙 포함), 환경변수 표(확정분/추가 예정분 구분).
   - **접근 방식**: 원칙 목록 (안전 우선, 보수적 기본값=기능 게이트 기본 off, 단계별 독립 PR, 기존 구조 재사용, 개인정보 최소화, 문서 동시 갱신).
   - **단계별 계획**: 단계마다 수정 파일 목록 명시. 단계는 독립적으로 롤백 가능해야 한다.
   - **성공 기준**: S1~Sn 번호. 전부 "테스트 또는 수동 확인으로 판정 가능"하게 쓴다. 판정 불가능한 기준(예: "안정적으로 동작")은 금지.
   - **제약 조건**: CommonJS·무의존성, pointsRepository 경유 저장, admin 읽기 전용 등 이 저장소의 금기(CLAUDE.md 참조). **금기를 깨야 하는 계획이면 별도 절로 뽑아 명시적 승인을 요청**하고, 대신 안전장치(env 게이트·감사 로그·확인 절차)를 묶는다.
   - **위험/롤백**: 위험별 대응 표. 모든 변경은 env 게이트 또는 단일 커밋 revert로 복구 가능하게 설계한다.
   - **범위 제외**: 이번에 안 하는 것과 그 이유를 명시 (재론 방지).
4. **운영 영향 명시**: `deploy-commands.js` 변경 여부 → 머지 후 `npm run deploy` 필요 여부를 계획서에 반드시 적는다.
5. **인덱스 갱신**: `docs/README.md`에 한 줄 추가.
6. **커밋하지 않는다**. 구현 브랜치에서 구현과 함께 커밋된다.

## 보고 형식

한국어로: 설계 요약(결정 사항 중심) → **사용자 결정이 필요한 값 목록**(기본값 제안 포함) → 다음 단계("승인해 주시면 지시서 작성/구현 시작"). 커밋 안 했음을 명시.

## 잘 작동하는지 확인하는 테스트

1. 작은 기능 요청 하나를 골라 하위 모델에게 이 스킬로 계획서를 쓰게 한다.
2. 채점 기준 (전부 통과해야 함):
   - [ ] 위 8개 장이 모두 있는가
   - [ ] 성공 기준이 전부 판정 가능한 문장인가 (각 항목에 "무엇을 실행해서 무엇이 보이면 통과"가 있는가)
   - [ ] 계획서에 등장하는 함수명·파일 경로를 grep했을 때 실제로 존재하는가 (환각 0건)
   - [ ] 롤백 방법이 env 게이트 또는 단일 revert인가
   - [ ] `npm run deploy` 필요 여부가 명시돼 있는가
   - [ ] 금기(CLAUDE.md 안티패턴) 위반이 있다면 승인 요청 절이 있는가
3. 가장 강한 테스트: 그 계획서를 **다른 컨텍스트 없는 새 세션**에 주고 "이대로 구현해줘"라고 했을 때 질문 없이 착수 가능한지 본다.

## 참조

판단 기준(착수 게이트, PR vs 직접 푸시, 리베이스, 배포 후속 조치, 보고 형식)은 `docs/judgment-checklist.md`를 따른다.
