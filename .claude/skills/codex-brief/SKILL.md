# 코덱스 구현 지시서 작성

승인된 계획서를 받아, **다른 컨텍스트 없이 지시서 하나만 보고 구현이 끝나는** 문서를 만든다. 지시서의 품질 기준은 "구현자가 질문할 일이 없는가"이다.

## 절차

1. **형식 기준 확보**: 기존 지시서를 1개 읽는다 (예: `prompts/codex/admin-console-write-v1.md`, `dm-chat-hardening-v1.md`).
2. **실코드 재확인**: 지시서에 적을 함수 시그니처, 재사용할 기존 함수 이름, 깨질 기존 테스트의 `파일:줄` 위치를 grep으로 실제 확인한다. 계획서 작성 시점 이후 코드가 바뀌었을 수 있다.
3. **지시서 작성** — 고정 구성:
   - **목표** (1~2문장) / **참고 문서** (계획서·AGENTS.md 경로) / **전제** (선행 PR, 브랜치명 `feat/<이름>`)
   - **구현 원칙**: 저장은 반드시 `pointsRepository.js` 경유, CommonJS, 기존 패턴 미러링 대상 명시 (예: "adminServer.js의 정적 서빙 4곳을 미러링").
   - **수정 가능 파일 목록**: 이 목록 밖의 파일은 건드리지 않는다고 못박는다.
   - **작업 1~N**: 작업마다 신규/수정 파일, 함수 시그니처, 기대 동작. 사용자에게 보이는 문구는 예시 문구를 지시서에 직접 적는다 (톤 일관성).
   - **깨질 기존 테스트**: `파일:줄`과 갱신 방향을 명시. "유지할 단언"과 "갱신할 단언"을 구분.
   - **신규 테스트**: `scripts/test-<이름>.js` 케이스 목록(입력→기대값)과 `check-release.js` 등록 지시.
   - **검증 명령**: `node --check`, 개별 스모크, `npm run check:release`.
   - **완료 후 요약 항목**: 구현자가 보고할 체크리스트.
4. **재론 금지 항목**: 이미 결정된 정책(지급 규칙, 보존 정책 등)은 "재론 없이 이대로"라고 못박아 구현자가 다시 설계하지 않게 한다.
5. **커밋하지 않는다** (구현 브랜치에서 함께 커밋). 단, 지시서만 main에 문서 커밋하는 기존 관례를 따르는 경우는 사용자에게 확인.

## 잘 작동하는지 확인하는 테스트

1. 지시서를 **계획서·대화 맥락 없이** 새 세션(하위 모델)에 투입해 구현시킨다.
2. 채점 기준:
   - [ ] 구현자가 되묻지 않고 완주했는가 (질문 발생 = 지시서 결함, 해당 항목 보강)
   - [ ] `npm run check:release` 통과
   - [ ] diff가 "수정 가능 파일 목록" 안에만 있는가
   - [ ] 지시서의 테스트 케이스 목록이 전부 신규 테스트에 구현됐는가
3. 리뷰 단계(sandwich-review 스킬)에서 "계획서 대조 리뷰 결과 수정 지시 0건"이 나오면 지시서가 충분히 구체적이었다는 뜻. 수정 지시가 2건 이상 반복되는 유형이 있으면 그 유형을 지시서 템플릿에 추가한다.

## 참조

판단 기준(착수 게이트, PR vs 직접 푸시, 리베이스, 배포 후속 조치, 보고 형식)은 `docs/judgment-checklist.md`를 따른다.
